## 1. Problem Statement（财务经理视角）

### 1.1 我今天的工作流断在哪

我每月的工作节律是：关账后出单店利润表 → 做 Actual vs Budget 差异分析 → 更新滚动预测 → 给管理层出三表视角的经营汇报 → 用同一套模型回答「如果租金涨 5% / 如果关掉这家店，全年利润和现金流怎么变」。今天系统把我卡在三处：

1. **没有一张完整的单店利润表。** `/store-360` 有四墙 EBITDA 卡片和诊断桥，`/performance` 有门店排行，但它们是**指标卡**，不是**报表**：我看不到一张从营业收入逐行走到门店营业利润、可以按科目展开、可以 Actual/Budget/Prior Year 并排、可以导出给区域经理签认的利润表。四墙 EBITDA 是利润表里的**一行**，不能替代整张表。
2. **没有三表模型。** 全库检索确认：系统内不存在资产负债表、不存在完整利润表、不存在间接法现金流量表（`fpna_plan_lines` 是扁平的经营口径行——revenue / gross_profit / labor_cost / fixed_rent / variable_rent / non_lease_cost / four_wall_ebitda / cash_flow / capex / net_debt——没有 BS 科目、没有科目树、没有勾稽）。集团要「明年月度资金计划 + 预测资产负债表」时，我只能回 Excel。而 Excel 模型的通病——公式被改、版本满天飞、数字没出处——正是这个产品本来要消灭的东西。
3. **版本治理建好了，但治理的对象是「行」，不是「模型」。** `fpna_plan_versions` 的状态机（draft → review → approved → official → retired）、冻结、谱系、三条口径版本线（assumption / exchange_rate / metric_definition）都很完整，但它管的是计划行数据；没有一个「三表模型」对象承载假设 → 计算 → 勾稽 → 发布的完整链路。

### 1.2 为什么这件事值得现在做

- IFRS 16 计量引擎已经能源源不断产出 ROU、租赁负债、利息、折旧的 roll-forward——这是三表模型里**最容易做错**的一块（先付/后付、变量租金费用化、修改与重估）。系统已经有唯一权威答案，模型应该**消费它**，而不是让每个财务经理在 Excel 里各自重造一遍（再造出来的大概率是错的）。
- store-day 事实层 + `retail-kpi-v1` 语义层给了收入、毛利、人工、占用成本的可信 Actual 区——三表模型最难的「Actual 从哪来」已经解决。
- WorkingPaper 底座（全 Certified 单元格、lint、xlsx/docx 导出、Review Gate）意味着「AI 帮忙填数和出报表」有一条**已被验证的合规路径**可以复用，不需要发明新机制。
- 这是财务经理、FP&A、财务 BP 三个角色**共同**的最高频交付物。做它一个，三个角色同时受益。

| 能力 | 状态 | 证据 |

## 2. 目标与非目标

### 2.1 目标

1. 交付一个**独立的单店利润表页面**：完整科目结构、多版本并排、双口径（经营 / IFRS 16）并列、可自定义、可导出、可下钻到事实来源。
2. 交付一个**法人级三表财务模型**：利润表、资产负债表、现金流量表三表联动，月度粒度，历史区只读 + 预测区可编，全部期间过勾稽校验才可发布。
3. 交付**受治理的自定义能力**：报表模板（科目树、公式行、格式）、保存视图、模板版本化与共享——自定义发生在版本化的模板对象内，不是自助 SQL。
4. 交付 **AI 填数与报表生成**：AI 产出假设建议草稿（人工确认后生效）与报表底稿（全 Certified 单元格），Actual 区由确定性引擎自动填充、不经 AI。
5. 全程满足五条底线与既有口径纪律（§8），全部结论继续保持 `unvalidated`（无真实 POS/ERP 联调、无客户验证）。

### 2.2 非目标（明确不做）

- **不做法定报表与法定合并**：无抵销分录、无少数股东权益、无合并报表准则合规承诺。三表模型是**管理口径**模型，输出 basis 永远标注 Working / Scenario / Forecast，**永不进入 Official 过账链路**（底线 5）。
- **不做自助 SQL / 自由指标 / 自由看板**：沿用《PRD_财务BP与FPA岗位支撑补齐方案》§6 的既有决定。本 PRD 的自定义是「受治理的模板自定义」，边界见 §5.3 与 §11 风险 2。
- **不做税务明细模型**：所得税用有效税率假设（含简单亏损结转开关），不做递延税资产/负债明细、不做纳税调整明细。
- **不做小时级/实时粒度**：最细月度（单店利润表可读 store-day 做日/周视图，但模型期间粒度为月）。
- **不改动 IFRS 16 计量引擎的任何口径**：模型只读消费其输出；发现口径问题走计量引擎自身的修正流程，模型侧不做「补丁式重算」。
- **不让 AI 计算任何会计金额**：AI 只建议假设值、组织语言、编排工具；所有金额由确定性引擎产生（沿用《FP&A与Finance_BP经营决策及AI辅助需求清单》§3.2 与 ADR-0025）。

| 用户 | 在本 PRD 里的高频工作 | 产品需要支持的结果 |
|---|---|---|
| 财务经理（本人） | 月度单店利润表签发；向管理层汇报三表；租金谈判的财务影响评估 | 单店利润表页、三表模型工作台、勾稽全绿的发布门禁、带公式的导出 |

## 4. 口径与命名（对齐 CONTEXT.md，先读这一节再读需求）

1. **双口径并列，永不混用。** 本 PRD 所有报表与模型同时维护两套口径，任何一行都必须声明自己属于哪一套：
   - **经营口径（operating basis）**：占用成本 = Occupancy Cost（基本租金 + 服务费 + 当期变量租金），不出现 ROU 折旧与租赁利息。这是 BP 与门店运营的语言。
   - **IFRS 16 口径（ifrs16 basis）**：不出现租金费用行，代之以 ROU 折旧与租赁负债利息（来自计量引擎）。这是对外财务报告的语言。
   - 两个 EBITDA 因此不同：IFRS 16 口径 EBITDA 高于经营口径（租金被移到了折旧与利息）。**报表上并排展示、各自标签，禁止在同一合计路径里混行。**
2. **Scenario ≠ Forecast ≠ Budget。** 三表模型的情景输出（baseline/upside/downside/custom）沿用 `fpna_plan_versions.scenario_type` 语义与 `fpna-version-lifecycle` spec：Scenario 永不冒充正式计划或实际；Actual 不落可编辑版本，只来自只读事实层。
3. **模型计算全部在后端。** 沿用「指标在后端计算，前端不得重算评分或排序」的纪律并扩展到：前端不得重算任何模型行、任何勾稽校验。自定义公式行也由后端引擎求值（§6.3）。
4. **不用 0 填补缺失。** 某期间某行缺数据：该行该期显示缺失与原因（Decision Ready 语义），合计行降级为 partial 并标注，**不得静默按 0 计入**。
5. **币种不隐式合并。** Currency Partition 是默认视图；折算走 `currencytranslation` 服务的显式第二视图，任何位置必须能看到 exchange_rate_version 与类型。
6. **命名沿用既有词汇**：Occupancy Cost、Store Contribution、Contribution Bridge、Fact Coverage、Decision Ready、Source Envelope、Data Classification、Action Proposal。新增术语只加三个（定义见 §6）：**Statement Template**（报表模板）、**Model Run**（模型批次）、**Tie-out Check**（勾稽校验）。
7. **AI 相关纪律原样继承**：Assist Mode；AI 不猜折现率；`scope_denied` 不得软化；系统事实 / 确定性计算 / 人工输入 / AI 推断四层分离（`fpna_decision_memos` 已有此结构，模型报表沿用）。

## 5. 需求清单（五批，编号 S1–S5）

> 批次编号不代表严格排期；建议顺序与依赖见 §7。每条批次的「验收标准」是批次验收的最低集，产品级验收（可演示的一条用户路径）在登记任务时补充，沿用 P0–P5 的做法。

### S1 — 单店利润表页（独立功能页）

**目标**：给财务经理与 BP 一张「能签认、能导出、能下钻」的门店利润表。新路由 `/store-pnl`，导航新增入口（不动既有入口，沿用 AppLayout 与 DESIGN.md 全部约束）。

**功能需求**：

- [ ] S1-1 科目结构按附录 D 的参考结构默认内置：营业收入 → 营业成本 → 毛利 → 门店直接费用（人工/营销/水电等）→ 经营占用成本 → **门店贡献（Store Contribution，经营口径）** → 分摊与其他 → **四墙 EBITDA**；IFRS 16 口径区并列：ROU 折旧、租赁负债利息 → **门店营业利润（IFRS 16 口径）**。
- [ ] S1-2 期间视图：日 / 周 / 月 / 季 / 年聚合（数据源为 store-day 事实，聚合规则遵循 `retail-kpi-v1`：流量跨日求和、面积等存量不跨日求和）；日历期语义复用 P1 的期间规范模块（`retailperiod` / `periodutil`），支持「上月」「2026-07」「2026-Q3」。
- [ ] S1-3 版本并排：Actual / Budget / Forecast / Prior Year 任意两列对比 + 差异额 + 差异率 + 达成率；Budget/Forecast 数据来自 `fpna_plan_versions` / `fpna_plan_lines`（store 粒度），Actual 只读来自事实层。
- [ ] S1-4 双口径切换与同屏并列两种模式；每个口径区固定展示 basis 标签。
- [ ] S1-5 每行可下钻：金额 → 构成（如占用成本 → 合同级拆分：基本租金/服务费/变量租金）→ 来源事实（Source Envelope：source_system / import_batch_id / fact_version / as_of_at / data_classification）。
- [ ] S1-6 同群对比列：可选在当前期间旁显示 Peer Cohort 中位数与所在分位（复用 `retailcohort`，样本不足或跨币种时显式降级，不出数字）。
- [ ] S1-7 多店汇总模式：按区域/品牌/法人聚合同一张表；混币种按 Currency Partition 分区展示，不加总。
- [ ] S1-8 导出：CSV + **带公式 XLSX**（合计行、差异列、达成率列均为活公式，复用 P1 导出模块的列/公式描述符与口径头）；导出文件带 Working/模拟标识与 basis 标签。
- [ ] S1-9 自定义：行显隐、行分组折叠、自定义公式行（如「其他费用率 = 其他可控成本 ÷ 营业收入」）——公式行能力受 §5.3 的模板治理约束；个人视图可保存（§5.3 S3-5）。
- [ ] S1-10 数据状态诚实呈现：Fact Coverage 不足、Source Conflict、混币、模拟数据、数据质量未评估——一律 `classifyDataState` / StateBlock 呈现，`decision_ready=false` 时明确给原因；**缺失行不显示为 0**。

**验收标准**：

- [ ] 财务经理能在三次点击内从门店利润表的任一行到达该行的来源事实与批次。
- [ ] 同一张表的经营口径与 IFRS 16 口径并列时，两个 EBITDA 并排展示且各自带口径标签；不存在把租金费用与 ROU 折旧加进同一合计的路径（有测试锁定）。
- [ ] Actual 列与 store-day 事实聚合的差异为 0（容差 0.05 舍入），不一致时进入 `fpna_data_quality_items` 而非静默调平。
- [ ] 导出的 XLSX 打开后合计行与差异列是活公式，口径头（数据分类、数据集版本、as_of、公式版本、期间、basis）完整。
- [ ] 预算覆盖不足 / 样本不足 / 混币种时显式降级，不输出看似完整的对比列。

### S2 — 三表财务模型（法人级）

**目标**：FP&A Analyst 在系统内搭建、运行、校验、发布一套月度三表模型，回答「全年利润、资金、资产负债结构怎么变」。新路由 `/financial-model`（工作台形态：模型列表 / 模型详情 / 假设面板 / 勾稽校验 / 发布与导出）。

**功能需求**：

- [ ] S2-1 模型范围：法人（legal_entity）级、月度期间、单币种（法人本位币）；历史区（Actual，默认最近 24 个月可配）+ 预测区（默认未来 36 个月可配），Actual 冻结线（actual cutoff period）显式可见。
- [ ] S2-2 三表结构默认内置：利润表（IS）、资产负债表（BS）、现金流量表（CF，间接法），附表含营运资本附表、长期资产附表（PP&E/装修）、**租赁附表（ROU 与租赁负债 roll-forward，直接引用计量引擎输出，模型不自算）**。全部结构以 Statement Template 承载（§5.3），默认模板只是模板的一个出厂版本。
- [ ] S2-3 输入来源（全部带版本与溯源）：
  - 收入/毛利/人工/占用成本 Actual：store-day 事实经 `retail-kpi-v1` 聚合；
  - 租金与付款计划预测：合同 + 付款计划（事件驱动重算后的最新版本）；
  - ROU / 租赁负债 / 利息 / 折旧：IFRS 16 计量引擎（含新增合同与已录入事件的影响）；
  - CAPEX 计划：`fpna_plan_lines.capex` / `capex_category`（新开店可引用 `/pre-deal` 评估结果为草稿，遵循 Action Proposal 语义）；
  - 期初 BS：受控模板导入（Trial Balance 或期初科目余额模板），带 Source Envelope。导入向导先过**三道闸**再接受数据：① 期初表自身平衡校验（资产−负债−权益=0，容差 ±0.01，逐历史期间）；② 历史各期口径一致性校验（科目标准化归并规则随导入模板版本化，杂项并入「其他流动资产/负债」等汇总行，不允许各期间各归各的）；③ 期初租赁负债与 ROU 同计量引擎该法人同期余额的逐合同勾稽，不符进 `fpna_data_quality_items` 并**阻止该模型运行**——期初带病，后面每一期都是错的。**未提供期初 BS 时，IS 与 CF（简化直接法补充视图）仍可用，BS 与间接法 CF 整体降级为不可判定并说明原因**——不按期初全 0 编造一张「平衡」的 BS；
  - 税率、股利、借款、营运资本天数等：假设面板（§5.3 S3-2，落 `fpna_assumption_versions`）。
- [ ] S2-4 预测驱动：收入侧支持 SSSG + 新店爬坡曲线 + 门店增减计划三种驱动方式的组合；费用侧支持比率法（占收入%）、增长率法、合同驱动法（租金）、天数法（营运资本）。每个驱动的取值是一个**有来源、有版本、有责任人的假设**，不是埋在公式里的常数。
- [ ] S2-5 模型运行（Model Run）：一键重算整个模型，产出按「行 × 期间」的结果集 + 勾稽校验结果集（附录 B 全量执行）。运行是异步 Run（可查进度、可取消），输入快照、模型定义版本、数据版本、假设版本全部随 run 留痕；**相同输入与版本重跑必须得到相同结果**。
- [ ] S2-6 勾稽门禁：附录 B 的 T1–T16 全部通过（或仅有经批准的容差内残差）的 run 才允许「发布」为 Working basis 的报表产物；任何勾稽失败在 UI 标红、给差异金额与定位，**禁止用插值/轧差项调平**（不留 plug，与 Contribution Bridge「残差显式保留」的纪律一致）。
- [ ] S2-7 版本与情景：模型输出可按 scenario_type（baseline/upside/downside/custom）保存为版本化结果集，与 `fpna_plan_versions` 谱系打通（一次模型发布可同时生成/更新对应 forecast/scenario 版本的行）；情景间对比用 Contribution Bridge 呈现，残差显式。
- [ ] S2-8 循环引用政策：默认**期初余额法**计息（利息按期初债务/期初租赁负债计算），从机制上消除循环；如未来引入平均余额法，必须是模型定义的显式开关 + 迭代上限 + 收敛阈值，并在报表上标注所用方法。
- [ ] S2-9 导出：三表 + 附表导出为带公式 XLSX（活公式、口径头、basis 标签、模拟标识）；支持按月/季/年折叠的展示视图导出。

**验收标准**：

- [ ] Golden 模型：固定输入（固定 seed 模拟数据集 + 固定合同组合 + 固定假设集）跑一次模型，三表输出与预期值逐项一致（自动化对数，先例为 `retailkpi` testdata 与 IFRS 16 回归）。
- [ ] 附录 B 每条勾稽公式至少有一个「故意破坏后必然报错」的反向测试（勾稽测试不是恒真断言）。
- [ ] 缺期初 BS 时 BS/CF 降级为不可判定并给出原因，IS 不受影响；不存在「期初全 0 的假平衡表」路径（有测试锁定）。
- [ ] 期初导入三道闸各有反向测试：期初表不平、归并规则跨期不一致、期初租赁负债/ROU 与计量引擎余额不符——三者均阻止运行，给出差异定位并进数据质量队列。
- [ ] 租赁附表数字与计量引擎输出逐期一致（容差 0）；模型侧不存在第二套租赁负债计算逻辑（架构测试约束）。
- [ ] 相同输入重跑结果一致；修改假设产生新版本而非覆盖；勾稽失败的 run 无法发布为 Working 产物。

### S3 — 受治理的自定义能力（模板、公式行、视图）

**目标**：满足「很强的自定义功能」的诉求，同时守住口径不漂移的底线。自定义的载体是**版本化的 Statement Template 对象**，不是自由查询。

**功能需求**：

- [ ] S3-1 **Statement Template（报表模板）**：科目树（至少三级：分组 / 科目 / 明细行）、行类型（`input` 手工输入 / `link` 数据源绑定 / `formula` 公式行 / `subtotal` 小计 / `check` 校验行）、行属性（口径 basis、符号约定、单位缩放、小数位、负数显示方式、是否参与合计）。模板带版本号，**版本一经使用即冻结，修改产生新版本**（与 plan version 纪律一致）。
- [ ] S3-2 **假设面板**：模型全部硬输入集中在假设面板，落 `fpna_assumption_versions`（已有：assumption_key / category / value / unit / source / owner / effective_from~to / version / status）。来源分层必须显式：合同事实 / 系统政策 / 管理层假设 / **AI 建议**四类，AI 建议只能是 draft 状态（§5.4）。
- [ ] S3-3 **公式行语言（白名单 DSL，不是 SQL）**：支持行间引用（同行其他期间 `lag(x, n)` / 同期其他行）、四则运算、常用聚合（sum/avg/min/max）、条件（if）、比率（带除零保护）。**禁止任意 SQL、禁止跨法人引用、禁止引用未登记的数据源**。公式解析与求值全部在后端（§6.3），非法公式在模板保存时拒绝并给出位置。
- [ ] S3-4 模板治理：创建（Editor）、复核（Reviewer）、批准（Approver）三态；法人内共享 / 个人草稿两种可见性；模板可复制（复制产生新版本谱系）；删除仅限从未被使用的草稿。
- [ ] S3-5 **保存视图（Saved Views）**：期间范围、版本组合、口径模式、行显隐、筛选（区域/品牌/门店）可保存为命名视图，支持设为个人默认与法人内共享；视图不改数据，只改呈现。
- [ ] S3-6 自定义行与官方指标的隔离：模板内的自定义公式行必须带「模型内自定义，未经指标治理」标识；若某自定义行需要跨页面复用（如进经营脉搏 KPI 网格），必须走 `fpna_metric_definitions` 登记为治理指标——**不允许模板公式行直接升格为全站指标**。
- [ ] S3-7 格式自定义：金额单位（元/千/万/百万，仅显示层缩放，存储不缩放）、负数显示（负号/括号/红色）、行缩进与加粗、合计行样式；格式定义随模板版本走，导出 XLSX 时随带。

**验收标准**：

- [ ] 模板版本冻结后任何编辑请求被拒绝并提示创建新版本；历史 run 仍按旧版本模板复演出原结果。
- [ ] 公式 DSL 的非法输入（语法错误、引用不存在的行、跨法人引用、SQL 关键字）在保存时被拒绝并定位到行。
- [ ] 自定义公式行在 UI 与导出文件中都带「未经指标治理」标识。
- [ ] 视图共享后，接收方打开看到的是同一呈现配置，且其数据范围仍受自己的 Data Scope 约束（视图不搬运权限）。

### S4 — AI 填数与报表生成

**目标**：把「搭模型 80% 的时间花在找数、填数、调格式」这件事交给 AI 做初稿，人只做确认与判断。全部能力运行在 Assist Mode，沿用工具分级（Read / Simulation / Draft-Action）与治理中间件链（ADR-0019 Addendum A）。

**功能需求**：

- [ ] S4-1 **模型读取与试算工具（新增，Read / Simulation 级）**：`fpna.statement_model.read`（读取模型定义、版本、run 结果、勾稽状态，权限与法人范围过滤复用既有 scoped reader 模式）与 `fpna.statement_model.evaluate`（无副作用试算：给定假设草稿跑一遍模型返回结果，不落库、不覆盖任何版本——与 Retail Scenario「只评估，不落库」的语义一致）。两个工具注册进 `internal/agenttools/tools/`，实现状态以代码为准。
- [ ] S4-2 **假设建议（Draft 级）**：AI 基于历史事实（同店/同群趋势、季节指数、合同条款、已批准的关联假设）给出驱动参数建议，产出为 `fpna_assumption_versions` 的 **draft + source=ai_suggestion**，每条附：建议值、依据引用（具体 Tool 调用与数据范围）、置信度（由覆盖率/样本量/规则强度推导，沿用 P3-35 的来源化纪律）、与现行有效值的差异。**人确认后才转 approved 生效；AI 无 approved 路径。**
- [ ] S4-3 **批量初稿填数**：对空白模型/模板，AI 按「历史 run-rate + 季节性 + 已登记假设」一次性给出整版假设草稿，按区（收入/费用/营运资本/CAPEX/税务）分块呈现供逐块确认；缺失输入（如无历史的新店）显式列出「无法建议项」并说明原因，**不编造**。
- [ ] S4-4 **差异解释**：模型版本间或 Actual vs Budget 的差异，AI 调用确定性差异桥（Contribution Bridge）拿到归因金额后撰写管理层解释草稿；金额只能来自确定性服务，解释不了的部分输出「残差/证据不足」，不得补全原因（沿用 AI-002 纪律）。确认后的解释进 `fpna_decision_memos` 的四层结构（系统事实/确定性计算/人工输入/AI 叙述）。
- [ ] S4-5 **报表生成（WorkingPaper 新构建器）**：新增 `internal/workingpaper/finmodel` 构建器与 `fpna.working_paper.finmodel.generate` 工具（LevelDraft + Review Gate，对标 s1/retail 先例）：模型 run 结果 → 全 Certified 单元格（nil 跳格不填 0、覆盖不足/多币种/模拟标识一一进 DataGaps）→ lint 门 → xlsx/docx 导出（`GET /ai/chat/artifacts/:id/export`）。封面页含：模型定义版本、模板版本、数据版本、假设版本、汇率版本、basis、生成时间与生成人。
- [ ] S4-6 **红线原样生效**：AI 不猜折现率（缺失即触发 human-in-the-loop）；10 项 protected_measures 永不出自 Tier B；`scope_denied` 保持原因不改写；AI 推断内容全程标识；写入类工具（假设草稿、底稿生成）带幂等键、过 Review Gate、进审计日志；自然语言不得绕过法人/门店/区域/品牌数据范围。

**验收标准**：

- [ ] AI 建议的假设在未人工确认前不参与任何模型正式运行（有测试：draft 假设不影响 run 输出）。
- [ ] 每条 AI 假设建议都能打开其依据（具体工具调用、数据范围、期间），无依据的建议不得出现。
- [ ] 低覆盖/小样本场景下建议置信度下降；证据不足时 AI 明确说「无法建议」而不是给数。
- [ ] 生成的报表底稿每个单元格 provenance 到 Certified 源（工具调用/系统事实），模拟数据单元格带标识；lint 失败不产出 artifact。
- [ ] 越权请求（跨法人门店、无权限区域）返回 `scope_denied` 原文原因，Agent 回答不得改写成「没有数据」。

### S5 — 集团合并视图与折算衔接（依赖 F3-c 已落地的 `currencytranslation`）

**目标**：多法人/多币种集团的月度合并视图（管理口径，非法定合并）。

- [ ] S5-1 跨法人模型汇总：集团视图 = 各法人模型 run 的按期间汇总，**只在用户有权限的法人集合上汇总**，无权限法人显示为「无权限」而非省略（跨法人汇总不得泄露无权限明细）。
- [ ] S5-2 折算第二视图：多币种汇总必须选择 exchange_rate_version（closing / average 类型显式），折算视图任何位置常驻汇率版本条；原币种 Currency Partition 视图保持默认。
- [ ] S5-3 不做抵销：内部往来/内部交易抵销不在本期范围，集团视图固定展示「管理口径汇总，未抵销内部交易」声明。

**验收标准**：

- [ ] 未选汇率版本时集团视图不出现任何跨币种合计数字。
- [ ] 汇总结果与逐法人明细勾稽（ties_out），差异为 0（容差 0.05）。
- [ ] 无权限法人在汇总中的处理方式有测试锁定（不泄露、不静默省略）。

## 6. 数据与计算架构决策（方向性；接口与接缝细节归配套 CodebaseDesign）

### 6.1 新增对象（三张核心表 + 两张结果表，命名方向）

| 对象 | 职责 | 关键字段方向 |
|---|---|---|
| `fin_statement_templates` | 报表模板（科目树 + 行类型 + 公式 + 格式），版本化、冻结后不可变 | legal_entity_id、name、version、status（draft/review/approved/retired）、rows JSONB（含行类型/公式/格式/basis）、created_by、审批留痕 |
| `fin_model_definitions` | 模型定义：范围（法人/期间/冻结线）、绑定模板版本、政策参数（利息分类政策、税率政策引用、计息方法=期初余额法）、数据源绑定版本 | legal_entity_id、template_version、actual_cutoff_period、policy JSONB、source_bindings JSONB、version |
| `fin_model_runs` | 一次模型运行的批次头：输入快照、全部版本线、状态、勾稽总状态 | model_definition_version、data_version、assumption_version、exchange_rate_version、metric_definition_version、data_classification、status、tie_out_status |
| `fin_model_run_lines` | 运行结果：行 × 期间 × 值 + provenance（来源类型：fact_aggregate / contract_schedule / ifrs16_engine / assumption / formula） | run_id、row_key、period、value、provenance JSONB |
| `fin_model_tie_outs` | 勾稽校验明细：check_code（T1–T16）、expected、actual、diff、status、失败定位 | run_id、check_code、period、expected、actual、diff、status |

全部对象带 `legal_entity_id`（底线 1）、幂等键（底线 4）、来源字段（底线 3）；schema 变更同时交付增量迁移与 `db/init/01_init.sql` 空库版本（双交付纪律，沿用 P0–P5 决策 21）。

### 6.2 分层与单一权威源

- **租赁数字只有一个权威源：IFRS 16 计量引擎。** 模型通过只读接缝消费其 roll-forward；模型侧禁止出现第二套租赁负债/ROU 计算（架构测试约束，验收见 S2）。
- **经营 Actual 只有一个权威源：`retail-kpi-v1` 语义层。** 模型 Actual 区的收入/毛利/人工/占用成本经它聚合，不私自从事实表重算（HARD-011 的指标注册收敛方向一致）。
- **前端零计算。** 模型行求值、勾稽校验、模板公式 DSL 解析全部在后端；前端只渲染与交互（沿用「前端不得重算」纪律）。

### 6.3 公式 DSL 的治理定位

公式 DSL 是**模板内的计算便利**，不是第二套指标语义层：它只能引用模板内行与已登记假设，输出只在模型/报表上下文有效；跨页面复用必须走 `fpna_metric_definitions` 登记（S3-6）。这条边界防止「每个财务经理一套口径」的 Excel 病在系统里复发。

### 6.4 复用而非新造的清单

| 需求 | 复用对象 |
|---|---|
| 版本状态机、冻结、谱系、ties_out 对比 | `fpna_plan_versions` + `fpna-version-lifecycle` spec 语义 |
| 假设库与来源分层 | `fpna_assumption_versions`（扩 source 枚举 `ai_suggestion`） |
| 数据质量降级队列 | `fpna_data_quality_items` |
| 报表产物登记 | `fpna_report_artifacts` |
| 经营口径现金流与 CAPEX | `cashplan` 服务、`fpna_plan_lines.capex` |
| 折算 | `currencytranslation` 服务（显式第二视图纪律） |
| 带公式 XLSX / CSV / 口径头 | P1 平台导出模块 |
| AI 底稿生成 | WorkingPaper 协议 + lint + s1/retail 构建器先例 |
| AI 工具治理 | ADR-0019 Addendum A 中间件链全链（TenantScope → CapabilityCheck → ProtectedMeasure → BudgetGuard → IdempotencyGuard → ReviewGate） |
| 日历期语义 | `retailperiod` / `periodutil` |
| 差异归因 | Contribution Bridge（`retailscenario` / `margindecomposition` 既有实现） |

## 8. 非功能需求与五条底线映射

| 底线 | 本 PRD 内的具体化 |
|---|---|
| 1 跨法人隔离 | 全部新对象带 `legal_entity_id` 行级过滤；公式 DSL 禁止跨法人引用；AI 工具走 TenantScope；`scope_denied` 保留原因；S5 汇总只在授权法人集合上进行 |
| 2 模拟/正式区分 | run 与结果行带 `data_classification`（production/simulated/mixed），贯穿 DB、API、导出、UI；模拟模型结果带标识且**永不进 Official 过账链**；同 seed 重跑可复演 |
| 3 来源追溯 | 每个结果单元格带 provenance（来源类型 + 具体引用 + 数据版本）；run 记录四条版本线（数据/假设/模型定义/汇率）；期初 BS 导入带来源信封 |
| 4 重复导入保护 | 模型运行、假设写入、底稿生成、期初导入全部带幂等键；重放不产生第二条 |
| 5 IFRS 16 正式台账隔离 | 模型只读消费计量引擎输出；三表模型与 AI 路径对 IFRS 16 正式表**零写入**（前后计数 e2e 证据，先例 MAX-009） |

其他非功能：

- **性能**：单法人 60 个月 × 约 200 行的模型全量重算目标 < 10 秒（异步 Run）；利润表页常用来回 < 3 秒（沿用既有 NFR）。
- **审计**：模板/假设/模型定义/发布/导出的新增、修改、审批、冻结全部进审计日志（关键动作日志沿用既有清单）。

## 9. Testing Decisions

- **好测试的标准沿用**：只测外部行为（接口契约），从模块接口 seam 驱动，不跨模块测实现细节。
- **Golden 模型对数**：固定 seed 数据集 + 固定合同组合 + 固定假设集 → 三表输出逐项对数（先例：`retailkpi` testdata 单测、IFRS 16 回归 `make ifrs16-regression`）。模型定义或公式引擎的任何变更必须重跑 Golden。
- **勾稽反向测试**：附录 B 每条公式至少一个「故意破坏必然红」的用例；勾稽测试恒真是本模块最典型的假绿风险。
- **公式 DSL**：语法/非法引用/跨法人/SQL 关键字的拒绝路径；除零保护；`lag` 跨期间边界（首期间无 lag 值 → 缺失而非 0）。
- **降级路径**：缺期初 BS、覆盖不足、混币种、Source Conflict、模拟标识——逐条有测试，断言「显式降级 + 原因」而非「返回空」。
- **AI**：draft 假设不进正式 run；无依据建议不出现；lint 失败无 artifact；越权 `scope_denied` 原文保留；依据引用可打开（先例：aiagent/agenttools 零售测试、retail_paper_sanctity 评测 category）。
- **集成**：真实 PostgreSQL 集成测试沿用 `TEST_DATABASE_URL` 模式；IFRS 16 零写入 e2e（前后计数）；每批完成跑通 `cd core-service && GOCACHE=$(pwd)/.gocache go test ./... && go vet ./...` 与 `cd ../web && npm run type-check && npm run build && npm test`；IFRS 16 计量参考值不变。
- **产品级验收**：每批登记一条可演示路径。建议：S1 = 「从门店利润表任一行三击到达来源事实并导出带公式 XLSX」；S2 = 「Golden 模型全勾稽通过后发布 Working 产物」；S4 = 「AI 给出整版假设草稿 → 人逐块确认 → 生成全 Certified 报表底稿并导出 xlsx」。

## 11. 风险与开放问题

1. **「很强的自定义」与「口径不漂移」的张力是本 PRD 最大的产品决策点。** 本文给出的解法是「受治理的模板自定义 + 公式 DSL 白名单 + 自定义行未经治理标识」（§5.3、§6.3）。评审时需要产品负责人确认这条线划得是否够（或过紧）。开放问题：公式 DSL 是否允许引用其他模板行（建议首版不允许）？自定义行数量是否设上限（建议设，防爆模板）？
2. **期初 BS 的数据可得性。** 没有 GL 联调前，期初 BS 依赖客户手工导入模板——数据质量直接决定 BS/CF 可用性。缓解已升格为门禁：缺期初即显式降级、导入三道闸（自平衡、归并口径一致、租赁余额对计量引擎勾稽）见 S2-3 及其验收标准。
3. **双口径并存对非会计用户有认知门槛。** 两个 EBITDA、两个「租金」并存，UI 必须持续标注 basis；培训材料与页内口径说明随 S1 交付（复用 DataTrustBar 的口径位）。
4. **S3 先行会占用 S2 工期**，但不先行必然返工（§7）。排期评审时不要为了早见三表而砍模板底座。
5. **AI 批量填数的采纳质量控制**：批量建议一旦「一键全收」就架空了人工确认。设计上逐块确认为必选路径，「全部接受」需二次确认并整块留痕（谁、何时、基于哪个依据版本）。
6. **全部结论仍为 `unvalidated`**：无真实 POS/ERP/GL 联调、无客户验证；本 PRD 不改变这一定性。Golden 对数证明「算得对且可复演」，不证明「口径被客户财务负责人认可」——后者依赖 DEMO 环节的外部纠偏（《AI_文档索引与现行决策》§6）。
7. **新增两个 Agent Tool 需要按现行流程登记**：descriptor + 治理中间件链全链 + 评测用例（建议新增 `finmodel_sanctity` category）；工具实现状态以代码为准，本文不构成实现承诺。

## 附录 A：三表财务模型标准搭建步骤（12 步）

> 每一步给「做什么 / 关键纪律 / 本系统落点」。这是财务经理搭三表模型的行业标准流程，也是 S2 引擎设计的验收参照——系统的建模向导应引导用户按此顺序走完。

**Step 1｜定目的、使用者与范围，并标准化历史数据。** 单店复盘、法人资金计划、集团汇报是三种模型，别混建；明确法人范围、本位币、使用者。随后收集并标准化历史数据：提取过去 3–5 年（或系统内可得期间）的历史报表，做科目标准化归并（杂项并入「其他流动资产/负债」等汇总行，归并规则版本化，保证历史各期口径一致），**先校验历史各期 BS 自身平衡再开建**——历史表自身不平，模型的期初就是错的。**落点**：`fin_model_definitions` 的范围字段；`legal_entity_id` 即隔离边界；期初导入向导（S2-3）。

**Step 2｜定时间轴与粒度。** 月度列；历史区（Actual）与预测区（Forecast）分色分区；Actual 冻结线显式。预测长度按用途定（资金计划 12–18 个月，续租/闭店评估覆盖剩余租期，集团预算 12 个月 + 2–4 年展望）。**纪律**：列 = 期间、行 = 科目，全模型统一，不允许某段换粒度。**落点**：`retailperiod`/`periodutil` 日历期语义；`actual_cutoff_period`。

**Step 3｜定口径与会计政策。** 开工前固化：经营口径与 IFRS 16 口径并列规则；租赁付款的利息/本金拆分与利息的现金流列报政策（IAS 7 政策选择：经营活动或筹资活动；中国企业会计准则实务列入筹资活动「分配股利、利润或偿付利息支付的现金」——模型做成显式政策开关，见 T9）；有效税率与亏损结转简化规则；变量租金当期费用化、不进租赁负债（既有会计红线）；CAM/服务费的拆分政策。**纪律**：政策是模型的版本化参数，不是某个单元格里的处理。**落点**：`fin_model_definitions.policy`。

**Step 4｜搭假设面板（唯一硬编码区）。** 全部驱动集中一处：销售增长（SSSG）、新店计划、毛利率、人工成本率、变量租金率、营运资本天数（DSO/DIO/DPO）、CAPEX、税率、股利、借款利率。每条假设带：数值、单位、来源（合同事实/系统政策/管理层假设/AI 建议）、责任人、生效期间、版本。**纪律**：计算区出现任何数值字面量都是缺陷（0 和 1 除外）。**落点**：`fpna_assumption_versions` + 假设面板 UI（S3-2）。

**Step 5｜搭收入与毛利预测。** 存量店：SSSG × 基期收入（基期取 run-rate 并标注数据版本）；新店：爬坡曲线（首月达成率 → 成熟月数）；闭店：到期归零。毛利：毛利率假设 × 收入，或按品类结构（F4 落地后可下钻）。**纪律**：收入预测必须能分解回「同店增长 + 新店 + 闭店」三块，给管理层一个能讲清楚的故事。**落点**：`retailkpi` run-rate 推导（与 Retail Scenario 同一套，不新造方法）+ 假设面板。

**Step 6｜搭费用与占用成本。** 人工：成本率法或人头 × 单位成本（F2 人时落地后增强）；租金：**合同驱动**——逐合同读付款计划（先付/后付、固定/指数/变量已结构化），变量租金 = 变量租金率 × 预测收入（当期费用化）；非租赁与其他：比率法或增长率法。**纪律**：租金预测必须与合同台账同源，不允许手工录一份「计划租金」——否则续租事件发生时模型与台账漂移。**落点**：合同 + 付款计划只读接缝；事件驱动重算结果。

**Step 7｜搭营运资本附表。** 天数法：AR = DSO × 收入/期间天数；存货 = DIO × COGS/期间天数；AP = DPO × COGS/期间天数。零售门店 AR 通常近零（现销），AP 与存货是主力；集团口径需含总部往来时单独建行。**纪律**：附表算余额，BS 取余额、CF 取变动额，三地同一来源。**落点**：营运资本附表行（模板内置）+ 天数假设。

**Step 8｜搭长期资产与租赁附表。** PP&E/装修：期初 + CAPEX − 折旧（直线法，年限为政策参数）− 处置。**ROU 与租赁负债：不自算**——直接引用计量引擎的 roll-forward（新增、利息、付款、重估、修改、终止各运动项齐全）。新增店/续租假设产生的「未来新合同」在模型里以计划行表达，并与决策卡/签约前测算的口径一致。**落点**：IFRS 16 服务只读消费；`fpna_plan_lines.capex`。

**Step 9｜搭利润表。** 收入 → COGS → 毛利 → 经营费用 → 占用成本（经营口径）→ EBITDA → 折旧摊销（含 ROU 折旧）→ EBIT → 利息（借款利息 + 租赁负债利息）→ 税前利润 → 所得税 → 净利润。双口径并列见 §4.1。**纪律**：IS 的每个折旧/利息数字必须能追到 Step 8 的附表，不允许在 IS 直接敲数。

**Step 10｜搭资产负债表。** 顺序：先非现金资产（AR/存货/PPE/ROU）与非股权负债（AP/租赁负债/借款），再留存收益滚动（期初 + 净利润 − 股利），**货币资金最后由现金流量表回填**——现金是 CF 的输出，不是 BS 的输入；差额禁止用 plug 科目轧平。**落点**：T1–T3、T10 勾稽。

**Step 11｜搭现金流量表（间接法）。** CFO = 净利润 + 折旧摊销（含 ROU 折旧）− 营运资本变动 ± 非现金调整；CFI = −CAPEX − 处置回流；CFE = 借款净变动 − 租赁本金偿还 − 股利（利息按 Step 3 的政策开关归经营或筹资）。期末现金 = 期初 + 三活动合计，回填 BS。**纪律**：CF 的每一行都能在 IS 或 BS 变动里找到出处（T4–T6、T9）。

**Step 12｜勾稽校验、情景与输出。** 先跑附录 B 全量勾稽，全绿再谈发布；然后复制出 upside/downside 情景（改假设不改结构）；最后输出：三表 + 关键比率 + 敏感性（租金 ±5%、销售 ±5% 对门店贡献与现金的影响）。**纪律**：勾稽不绿的模型不发布（S2-6）；情景是独立版本，不覆盖基线（CONTEXT：Scenario Evaluation 语义）。

## 附录 B：逻辑勾稽公式清单（T1–T16）

> 每条：公式 / 频率 / 容差 / 失败处理。这些是模型的**恒等式**，任何期间、任何情景、任何版本都必须成立；不成立即标红并阻止发布（S2-6），**不允许用轧差项调平**。符号约定：t 为期间下标；Δ 为相对上一期间的变动额。
>
> **防误用提示**：通行的三表方法论（投行模板、建模教程）普遍不含租赁维度——它们的「债务附表」是通用借款逻辑。本产品的租赁勾稽由 T7–T9 承载（roll-forward 唯一来源为计量引擎、本金/利息拆分、利息列报政策开关），照通用教程实现租赁处理是本模块的已知误用路径。

## 附录 C：建模最佳实践（行业标准 → 本系统映射）

> C1–C8 是财务建模行业惯例（FAST/SMART 一类标准的核心）在本系统的落地方式。写进 PRD 的目的：它们是 S2/S3 的设计约束，也是评审时的检查清单。

**C1 输入 / 计算 / 输出三层分离。** 假设只进假设面板，计算只在引擎，输出只读运行结果。Excel 病（公式里埋数字、输出区手改）在系统里由机制杜绝：计算区没有数值字面量（S3-2/§6.3  lint），结果行不可原地编辑（版本冻结）。

**C2 一处定义、处处引用。** 同一驱动（如变量租金率）全模型只存一份；改一处全部生效。系统内即四条版本线（assumption / model_definition / data / exchange_rate）+ `metric_definition_version`，引用永远带版本号。

**C3 行列纪律。** 列 = 期间、行 = 科目；同一行每个期间用同一公式（首期间 lag 缺失等例外在模板里显式声明）；单位统一（存储不分缩放，显示层缩放——S3-7）。公式体内禁止数值字面量——`=收入*1.05` 是禁忌，必须写成 `=收入*(1+假设.收入增长率)` 引用假设行；DSL lint 把「0 和 1 以外的数值字面量」与「预测中途变公式」列为拒绝规则（§6.3），不靠 reviewer 肉眼兜底。

**C4 符号约定唯一。** 本系统约定：**资产、收入、费用均以正数存储，负债与权益以正数存储，方向由行类型与公式决定**；CF 行按流入正/流出正展示由展示层决定。约定写在模板规范里，不允许某行自定义反号（反号是 Excel 模型勾稽失败的第一大原因）。

**C5 规避循环引用。** 利息按**期初余额**计算（S2-8），从机制上消除「利息 → 现金 → 利息」的循环；若未来启用平均余额法，必须显式开关 + 迭代上限（≤100 次）+ 收敛阈值（≤0.01），并在产物上标注。

**C6 校验行是一等公民。** 勾稽校验（附录 B）是报表上的可见行，不是隐藏检查；不平即红、不发布、不调平。**残差显式保留**（与 Contribution Bridge 纪律一致）——一个永远平衡的模型比一个诚实的模型更可疑。

**C7 Actual 冻结。** 历史区只读，来自事实层与计量引擎；重述走 Fact Version 递增，不改旧版。预测区可编，但每个改动落版本。这条纪律让「上个月报给管理层的数为什么和这个月不一样」永远可回答。

**C8 颜色与导出约定（导出 Excel 时随带）。** 蓝字 = 输入/假设，黑字 = 计算，绿字 = 跨表引用；带公式 XLSX 的活公式与口径头沿用 P1 导出模块；工作簿结构（输入页/计算页/输出页分页）由导出模板决定，用户不手排。

**C9 AI 协作纪律。** AI 建议 = 草稿（draft + 依据 + 置信度），人确认才生效；AI 不算金额、不猜折现率、不绕过权限；报表底稿单元格级 provenance + lint fail-closed。**AI 的价值是速度，不是权威**——权威永远来自确定性引擎与人工审批。

**C10 可复演。** 任一数字能以相同数据版本 + 假设版本 + 模型定义版本重新生成（S2-5）；这条是审计与自我纠错的共同前提。
