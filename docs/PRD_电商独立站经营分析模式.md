## 1. Problem Statement（电商财务 BP 视角）

### 1.1 用户画像与规模假设（设计假设，非调研结论）

- 跨境 DTC 品牌，独立站为主：Shopify 三个站点（美国 / 欧洲 / 日本），年 GMV 约 $15M
- 收单：Shopify Payments + PayPal + Stripe；广告：Meta / Google / TikTok，经国内代理投放（**预充值、有返点**）
- 履约：境内采购 + 美东 / 欧洲 3PL 仓发；主体结构：**香港公司收单、境内公司采购**
- 财务团队 2 人（BP + 出纳），没有数据工程师、没有 BI 团队
- 约 2,500 单/日（三站合计），SKU 约 200 个，订单行年增百万行级别

### 1.2 工作流断在哪

1. **周一想看「上周各站净收入 / CM% / MER vs 预算」：数据散在 5 个后台，先花 3 小时导 CSV。**
2. **周中对账**：Shopify payout ↔ 订单应收 ↔ 银行流水三方对不上；PayPal 滚动准备金占用与释放看不清；广告**发票实付 vs 后台账面**的差异没人管。
3. **月底拼管理报表**：渠道 / SKU 毛利靠透视表，口径每次都被 growth 团队挑战（「你这广告费是账面还是实付？」）。
4. **大促（BFCM）前**手搓保本模型，每次重做；**每天** CEO 问「这个 campaign 赚不赚」，给不出又快又可信的答案。

### 1.3 根因

不是没有数据，而是**每个来源各自一套维度、一套币种、一套口径，而且都会事后变**（退款最长 120 天+ 到达、拒付、广告账单调整、代理返点）。缺的不是又一个 BI 图表，是一个「**能对上账、能算清楚、能做模拟**」的财务工作台。判断这个模式成不成立的标准就一条：**能否把 BP「搬数对数 70% / 分析 30%」的时间比例倒过来。**

### 1.4 现状能力复用表

| 能力 | 复用方式 |
|---|---|
| Source Envelope / 受控导入 / 双层幂等 | 直接复用同一字段族与批次纪律（底线 3、4） |
| store-day 事实层的建模范式（Fact Version / Highest Fact Version / Source Conflict / Fact Coverage / Data Classification） | **模式复用，新表族**：站点日事实、campaign 日广告事实、订单行明细 |
| KPI 语义层（`retail-kpi-v1` 形态：严格 null / 零分母、覆盖门槛、币种分区、Metric Surface 启动校验、中文名单一真相源） | **模式复用，平行模块**：电商指标定义（§5 D5） |

## 2. Solution（方案总览）

### 2.1 形态

把既有四环节闭环（发现问题 — 解释原因 — 模拟方案 — 形成行动）从「门店」平移到「站点」，叠加三个电商特有的信任结构：

1. **接入与事实层（E1–E2）**：平台数据（含 CSV 兜底）带着完整来源信封进站点日事实；退款 / 拒付以新 Fact Version 重述期间，不覆盖历史。
2. **算清楚（E3–E4）**：单站利润表（GMV → 净收入 → 落地成本 → 履约 → 支付费 → CM1 → 广告 → CM2 → 经营利润）+ 单位经济（CAC 回本、盈亏平衡 MER / ROAS）+ **收款对账作为信任锚点**：未对平的期间不得进入 Approved 口径。
3. **模拟与行动（E5–E8）**：保本与大促情景（纯函数、全程模拟标识）、差异归因与站点脉搏、预算滚动、Agent 问答与月度经营回顾初稿（Assist Mode，只写草稿层）。

### 2.2 分期

| 批次 | 内容 | 分期 |
|---|---|---|
| E1 数据接入 | Shopify / 广告 / 收单结算 / 3PL / 采购，CSV 模板兜底 | **P0** |
| E2 经营事实层 | 站点日事实 + campaign 日广告 + 订单行明细 | **P0** |
| E3 单站利润表与单位经济 | 科目结构、双广告口径、CM1/CM2、保本 MER/ROAS | **P0** |
| E4 收款对账 | 三方对账、差异归类、准备金、对账签认与口径门禁 | **P0** |
| E5 保本与情景模拟 | 大促预算模拟、定价 / 运费 / 折扣敏感度 | **P0–P1** |
| E6 差异归因与站点脉搏 | Contribution Bridge（量/价/混合/汇率/广告效率）、异常提醒 | P1 |
| E7 预算与滚动预测 | 站点 × 月预算，实际 vs 预算 vs 预测三行 | P1 |
| E8 Agent | 归因问答（带引用）、月度经营回顾初稿、异常triage | P1 |
| E9 库存 × 现金流 + 多主体 | 备货→现金占用、回款滞后、香港/境内内部往来 | P2 |

### 2.3 端到端验收场景（产品级验收，任一不达成则该分期不算完成）

1. **周一 9:00**：打开站点脉搏，三站上周净收入 / CM% / MER vs 预算 + 前 3 差异因子已列出——全程不开 Excel，≤10 分钟。
2. **月结第 2 个工作日**：三平台对账完成、差异清单逐笔归类、对账单签字归档；广告实付 vs 账面差异表（含返点）同步产出。
3. **大促前**：输入预算与预期 CPM / CVR / AOV，10 分钟出保本 MER、预期 CM 与现金缺口提示（备货 + 广告预充 + 回款滞后）。
4. **临时提问**：Agent 回答「德国站 11 月 CM 为什么比 10 月低 3 个点」，带归因链与引用，平台报数与系统算数明确区分，≤30 秒。

## 3. User Stories（用户故事）

> 编号连续，按批次分组。角色除特别注明外均为「电商财务 BP」。

### E1 数据接入

1. 作为电商财务 BP，我希望 Shopify 订单、退款与 payout 数据按批次接入并携带完整 Source Envelope（source_system / import_batch_id / fact_version / as_of_at / data_classification），以便月底不再手工导出和对列，且每个数字有出处。
2. 作为电商财务 BP，我希望 Meta / Google / TikTok 的 campaign 日耗以**账面口径**入库、代理发票以**实付口径**入库，两套并存，以便「广告费是账面还是实付」不再是一句需要解释的话。
3. 作为电商财务 BP，我希望 PayPal / Stripe 结算文件、3PL 账单、采购与头程发票有标准化 CSV 模板（信封字段一个不少），以便没有 API 的来源也有同一条受控入口。
4. 作为电商财务 BP，我希望重复导入（请求级与业务级）不产生第二条记录，以便我可以放心重放窗口期的导入。
5. 作为系统管理员，我希望配置站点、渠道、法人归属与导入批次监控，以便接入面可运维。

### E2 经营事实层

6. 作为电商财务 BP，我希望分析主粒度是**站点 × 日 × 渠道 × SKU** 聚合事实（订单行明细仅作下钻与对账证据），以便任意分析不必从原始订单拉起，也避免百万行订单明细进入分析读路径。
7. 作为电商财务 BP，我希望退款 / 退货 / 拒付在最长 120 天+ 到达时，以**新 Fact Version** 重述对应期间并打修订标记，以便历史不被覆盖、口径变化可解释。
8. 作为电商财务 BP，我希望缺数显示「—」加原因，不许补 0、不许反推（如用工时÷假定客单价倒推订单数），以便覆盖不足时结论显式降级为 Decision Ready = false。
9. 作为电商财务 BP，我希望平台报数（如 Meta ROAS、Shopify total sales 含税含运费）与内部口径冲突时并列降级展示、不得改名贴标签，以便我不会信错数。
10. 作为电商财务 BP，我希望多币种按 Currency Partition 分区展示，折算是带汇率版本的显式第二视图，以便没有一笔金额被静默换算。
11. 作为电商财务 BP，我希望销售税 / VAT 作为代收代缴项目不进收入行、单独挂负债并参与对账，以便税务口径干净。

### E3 单站利润表与单位经济

12. 作为电商财务 BP，我希望每站月度 + 周度利润表：GMV → 净收入 → 落地成本 → 履约 → 支付通道费 → **CM1** → 广告（实付）→ **CM2** → 分摊固定费 → 经营利润，以便 10 分钟回答「这个站赚不赚、差在哪」。
13. 作为电商财务 BP，我希望利润表可按渠道 / campaign / SKU 展开，且子合计由子行推导（下钻与父行不可能不一致），以便口径被挑战时拿得出证据链。
14. 作为电商财务 BP，我希望每行可下钻到订单行 / 账单行 / 发票，以便任何数字 30 秒内追溯到来源。
15. 作为电商财务 BP，我希望盈亏平衡 MER 与盈亏平衡 ROAS 基于显式的固定 / 变动拆分一键计算（CM 率 ≤ 0 时报 `unachievable` 而不是一个巨大的数），以便投放预算讨论有共同底线。
16. 作为电商财务 BP，我希望新客首单 CM、付费新客 CAC 与混合 CAC 并列展示且分子分母标明，以便评估获客是否健康。
17. 作为电商财务 BP，我希望经营口径净收入与会计口径收入并列展示且永不互换（会计口径只读来自总账，本模式永不自算法定收入），以便两套语言各答各的问题。
18. 作为管理层，我希望三站一页的脉搏与 top 差异因子，以便周一会前不用等人拼表。

### E4 收款对账

19. 作为电商财务 BP，我希望 payout 明细 ↔ 订单应收 ↔ 银行到账三方对账，差异逐笔归入具名类别（手续费、汇兑、拒付、在途、调整、准备金），以便月结对账从两周缩到两个工作日。
20. 作为电商财务 BP，我希望 PayPal 滚动准备金的占用与释放被跟踪，以便现金流预测不被冻结资金打脸。
21. 作为电商财务 BP，我希望**未对平的期间不得进入 Approved 口径的正式报表**，差异进 Data Quality Queue，以便正式数字永远可辩护。
22. 作为 Reviewer / Approver，我希望对账结果走 Draft → Prepare → Pending → Approved 签认归档、职责分离留痕，以便审计可追溯。
23. 作为出纳，我希望 payout 到账与银行流水对账视图区分在途与已到账，以及广告预充值 / 代理发票 / 返点到账台账，以便资金侧不靠记忆。
24. 作为 Auditor Readonly，我希望只读导出对账证据链与口径版本，以便审计资料一次备齐。

### E5 保本与情景模拟

25. 作为电商财务 BP，我希望输入广告预算 + 预期 CPM / CPC / CVR / AOV，得到 GMV、CM、保本 MER 的情景对比，以便 BFCM 方案会前出对比表。
26. 作为电商财务 BP，我希望改价 / 改运费 / 改折扣的敏感度模拟，以便定价讨论有数。
27. 作为电商财务 BP，我希望模拟结果全程带 Data Classification 模拟标识、永不混入正式口径（底线 2），以便模拟与事实不可能混淆。

### E6 差异归因与站点脉搏

28. 作为电商财务 BP，我希望月度 P&L 差异按量 / 价 / 混合 / 汇率 / 广告效率做 Contribution Bridge 分解且**顺序固定并回显**，以便差异汇报可复演。
29. 作为电商财务 BP，我希望站点脉搏每日更新净收入 / CM% / MER vs 预算，并对退款率、广告花销突增等给出 Attention Signal（证据不足时显式 Suppressed，不静默过滤），以便异常当天可见。

### E7 预算与滚动预测

30. 作为电商财务 BP，我希望站点 × 月预算与「实际 vs 预算 vs 预测」三行并存、预算版本留痕，以便滚动预测不断链（复用既有 `fpna_plan_versions` 治理，不建第二套版本对象）。
31. 作为 Growth 负责人，我希望对预算与假设**只能提交建议草稿**（财务批准后生效），以便口径之争有流程而不是谁嗓门大。

### E8 Agent

32. 作为电商财务 BP，我希望直接问「德国站 11 月 CM 为什么比 10 月低 3 个点」，得到带归因链与引用的回答，且明确区分平台报数与系统算数，以便 30 秒回答 CEO 提问。
33. 作为电商财务 BP，我希望月结后 Agent 自动生成经营分析初稿（AI 叙述与系统事实分层、全 Certified 单元格底稿），以便月度经营回顾从一天到一小时。
34. 作为电商财务 BP，我希望 Agent 的假设调整建议只落草稿层（`source=ai_suggestion`），approved-only 读取永不回采草稿，以便 AI 可以提议但不可以自我批准。
35. 作为 Growth 负责人，我希望只读查看自己渠道的 CM 与 CAC 回本（数据范围收窄到渠道），以便不必等财务排期。
36. 作为电商财务 BP，我希望权限拒绝保持 `scope_denied` 原因不被软化，以便权限问题不被掩盖（底线 1）。

### E9 库存 × 现金流 + 多主体（P2）

37. 作为电商财务 BP，我希望备货计划 → 采购 / 在途 → 现金占用的视图，叠加回款滞后（payout T+2~T+7、PayPal 准备金、广告预充值），得到经营现金流预测，以便资金计划不再手搓。
38. 作为电商财务 BP，我希望香港收单主体与境内采购主体的内部往来视图（三表模型经电商事实 Port 只读消费，模型不自建第二套收入 / 成本引擎），以便两主体利润与转移安排可见。
39. 作为电商财务 BP，我希望按 cohort 看 12 个月累计 CM1 的 LTV/CAC 与复购，以便获客预算有长期依据。
40. 作为电商财务 BP，我希望礼卡 / 预售等递延收入在总账侧处理、模型侧只读呈现，以便会计判断留在会计系统。

## 4. 口径与命名

### 4.1 新增领域术语（实施启动时并入 CONTEXT.md；在此之前以本表为准）

| 术语（建议英文词条） | 定义 | 备注 |
|---|---|---|
| **Storefront（独立站）** | 电商经营分析的根对象：一个面向一个市场 / 币种独立收单与履约的电商站点（如一个 Shopify 店），带编码、市场、币种、法人归属。是 Store 在电商域的等价物，**不是**同一个概念 | ⚠️ CONTEXT.md 的 Store 词条把 "Site" 列为禁用词；本 PRD 刻意在中文使用「站点」指 Storefront。落地时需修订 Store 词条的 avoid 注记并新增本词条（待决问题 §8.3-①） |
| **Storefront-Day Fact（站点日事实）** | 一个站点一个日期 × 渠道 × SKU 的聚合经营度量：下单金额、折扣、退款、订单数、落地成本、履约、支付通道费 | 经营分析的原子粒度；订单行明细只是证据不是分析粒度 |
| **Campaign-Day Fact（广告日事实）** | 一个 campaign 一个日期的广告度量，**账面口径与实付口径两行并存** | 实付来自代理发票，返点作后续期间成本贷项 |
| **Net Revenue（净收入，经营口径）** | GMV − 退款 − 退货 − 拒付损失（GMV = 下单商品金额 − 折扣，不含税不含运费） | 与会计口径收入并列，永不互换 |
| **Landed Cost（落地成本）** | 采购价 + 头程 + 关税 + 入仓，移动平均 | |
| **Order Contribution（订单贡献，CM1）** | 净收入 − 落地成本 − 履约 − 支付通道费（不含广告） | 单位经济与保本测算的基础 |
| **Contribution After Advertising（广告后贡献，CM2）** | CM1 − 广告费（实付口径） | |
| **Break-even MER（盈亏平衡营销效率比）** | (固定费用 + 目标利润) ÷ CM1 率；CM1 率 ≤ 0 报 `unachievable` | 沿用 Required Incremental Revenue 的「不可达成即报不可达成」纪律 |
| **Break-even ROAS** | 1 ÷ CM1 率 | |
| **Settlement Reconciliation（收款对账）** | payout 明细 × 订单应收 × 银行到账三方独立路径的证据匹配，差异归入具名类别 | 是 GL 对账域的概念（证据匹配），**不是** Tie-Out（模型勾稽），两词不得混用 |
| **Rolling Reserve（滚动准备金）** | 收单机构按比例冻结、延期释放的资金 | 现金流预测的必填项 |
| **Media Rebate（媒体返点）** | 代理按投放量返还的贷项，冲减后续期间实付广告费 | 账面 / 实付差异的组成之一 |

其余全部沿用 CONTEXT.md 既有词汇：Source Envelope、Data Classification、Fact Version / Highest Fact Version、Source Conflict、Fact Coverage、Decision Ready、Currency Partition、Attention Signal / Suppressed Attention、Contribution Bridge、Scenario Assumptions / Scenario Evaluation、Action Proposal、Data Gap、Data Quality Queue、Report Basis（Draft / Pending / Approved）。**新代码禁用 `working` / `official` 作口径名**（既有词表分叉不扩大）。

### 4.2 口径字典（默认口径；每个指标的定义必须挂 Metric Definition Version，报表回显版本号）

| 指标 | 默认口径 |
|---|---|
| GMV | 下单商品金额 − 订单级 / 商品级折扣（不含税、不含运费） |
| 净收入 | GMV − 退款 − 退货 − 拒付损失 |
| 会计收入 | 与总账一致（含退货准备计提），只读来自 GL 导入 |
| 履约成本 | 包材 + 拣配 + 头程 + 尾程 + 退货运费（3PL 账单口径） |
| 支付通道费 | 收单账单实扣（含汇兑费） |
| 广告费·账面 / ·实付 | 平台后台 spend / 代理发票额（返点冲减下期） |
| CM1 / CM2 | 见 §4.1 |
| CAC | 付费新客 CAC 与混合 CAC 并存，分子分母标明 |
| 盈亏平衡 MER / ROAS | 见 §4.1 |
| LTV/CAC | 按 cohort，12 个月累计 CM1 |

### 4.3 既有纪律的沿用（不因新模式打折）

- 五条底线（跨法人隔离、模拟 / 正式区分、来源追溯、重复导入保护、IFRS 16 正式台账零写入）全部原样适用；站点属于法人，行级过滤从第一天就生效。
- 指标在后端计算，前端不得重算评分、排序或任何模型行；指标露出走受校验清单（Metric Surface）。
- 口径冲突只降级不换算；不用 0 填补缺失；样本不足 / 币种混杂显式降级。
- AI 默认 Assist Mode：只识别、建议、起草稿；`scope_denied` 不软化；AI 不计算任何会计金额。

## 5. Implementation Decisions（实现决策）

> 只列决策，不含文件路径。配套模块深化文档展开接缝。

**D1 增量叠加。** 不删除、不重命名、不隐藏任何既有页面 / API / 能力；新页面沿用既有 AppLayout、栅格与交互范式（DESIGN.md §13 止血条款强制生效）。

**D2 事实层。** 新建三类事实对象：站点日事实（站点 × 日 × 渠道 × SKU 聚合）、广告日事实（campaign × 日，双口径）、订单行明细（仅供下钻与对账，列裁剪，不进分析读路径——订单行年增百万行级别，分析只走聚合事实，符合「PostgreSQL 承担控制平面、不堆分析事实进宽表」的既有边界判断）。全部携带完整 Source Envelope。

**D3 重述。** 退款 / 拒付 / 账单调整以新 Fact Version 进入，读取走 Highest Fact Version；被重述期间带修订标记与谱系。绝不原地覆盖。

**D4 幂等。** 业务键（平台订单号、payout ID、发票号）+ 请求级幂等；重放不产生第二条记录。

**D5 语义层。** 平行于既有零售 KPI 语义层建电商指标语义模块，同形约束：严格 null / 零分母、覆盖门槛、来源冲突拒收、币种分区、Metric Surface 启动校验、中文名单一真相源（消费包不得建第二张 labels map）。

**D6 广告双口径。** 账面与实付是两个事实不是同一事实的两个视图；返点作为后续期间的成本贷项；两者差异独立出表，不静默选边。

**D7 单站利润表投影。** 纯函数服务（类比单店利润表投影）：一切输入经注入，子合计由子行推导；经营口径与会计口径并列、basis 标签随行走；会计口径收入只读来自 GL，本模式永不自算法定收入。

**D8 对账引擎与口径门禁。** 纯函数匹配器：payout 行 × 订单应收 × 银行到账 → 具名差异类别；差异进 Data Quality Queue（复用「进队列才有人处理」模式）；**对账完成是对应收入 / 现金数字进入 Approved 口径的前置门**；对账单本身走 Draft → Prepare → Pending → Approved 签认。

**D9 情景与保本。** 纯函数评估器（类比 Scenario Evaluation 语义）：只评估不落正式表，输出永远 Scenario 基调 + Data Classification 标识；保本类指标在 CM1 率 ≤ 0 时报 `unachievable`。

**D10 币种。** Currency Partition 为默认视图；折算是显式第二视图，带汇率版本与类型，无汇率整体降级（沿用既有折算服务的版本纪律）。交易币种 → 记账本位币 → 集团报告币种三层各自可答。

**D11 税务表示。** 销售税 / VAT 不入收入行，独立负债行参与对账；不做税务申报自动化。

**D12 Agent 工具。** 不开第四命名空间：经营读类挂 `retail.` 二级段（如 `retail.site_pulse.read`、`retail.site.scenario.evaluate`），财务读类挂 `fpna.` 二级段（如 `fpna.site_pnl.read`）；最终命名按 Agent_Tool_包装规范的「看数据属于哪个域」判定法过一遍，**不得加剧既有 15 个错位工具债**。读类只读；写类一律只写草稿层。工具数运行时枚举，注册失败 fail-fast。

**D13 页面。** 新路由（站点脉搏、站点 360、单站利润表、对账工作台），容器与状态呈现沿用既有范式（取数钩子、状态分类组件、枚举契约登记）；新枚举登记进前端契约测试。

**D14 三表联动（P2）。** finmodel 新增电商事实 Model Port（只读）；模型不自建第二套收入 / 成本引擎；礼卡等递延收入在 GL 侧处理、模型只读呈现。

**D15 演示数据。** 固定 seed 的电商 Simulated Dataset + Anomaly Manifest（复用零售模拟的既有模式），用于无设计伙伴时复演场景；模拟结论一律 `unvalidated`，永不表述为真实经营结果（红线 11）。

## 6. Testing Decisions（测试决策）

**好测试的定义**：只测外部行为——HTTP JSON 契约与纯函数的输入输出；不测实现细节。替换类改动沿用 GUARD-001：必须证明「B 真的生效」，只证明「A 消失」不算验收。

**测试缝（就高不就低，总数控制在三条主缝 + 两条守卫缝）**：

1. **Handler JSON 契约 golden（最高缝）**：每个新页面的 API 在 handler 边界用 golden 用例锁响应形状与降级语义。先例：现行 handler 层 golden 测试。
2. **纯函数引擎 golden**：单站利润表投影、对账匹配器、保本 / 情景评估器各自以构造输入 + 期望输出逐格锁定；对账匹配器每个具名差异类别至少一个 golden 用例 + 一条先证红再证绿的用例。先例：租赁情景与底稿的 golden 测试。
3. **语义层与前端契约守卫**：Metric Surface 启动校验（清单里的 code 必须存在，否则启动失败）；前端新枚举登记契约测试。先例：KPI 语义层与前端枚举契约测试。
4. **带库集成（守卫缝）**：幂等（重放不产生第二条记录）、重述（新版本不覆盖）、跨法人隔离（站点属法人、行级过滤）必须带真实 PostgreSQL 跑——skip 不构成证据（底线 1 与 4 的证据在这里）。
5. **Agent 注册守卫（守卫缝）**：工具数运行时枚举、尝试注册数 == 成功数、`scope_denied` 等错误码双路径一致；不 grep。

**专项纪律**：差异归因的守恒等式是构造性质不是检查对象（红线 12）——测试锁定中间值序列与顺序敏感性回显，不测「桥加起来等于总差」这种恒真断言；口径字典变更必须产生新 Metric Definition Version，测试钉住「改定义不出新版本即红」。

## 7. Out of Scope（明确不做）

- **平台电商 / marketplace**（Amazon、天猫等）：本模式只覆盖独立站；marketplace 另行立项
- **实时 / 流式**：T+1 足够；不追小时级
- **广告平台 API 自动同步（P0）**：P0 用受控 CSV 批次；API 连接器 P1 再做，且沿用 MCP 的 fail-fast 治理思路
- **ERP / 总账回写**：导出单向；不做凭证写回
- **法定合并与转移定价自动化**：P2 只做内部往来可见性，不做抵销分录
- **税务申报自动化**：税金只做表示与对账
- **LTV 预测模型**：P1 只做 cohort 事实视图，不做预测
- **库存补货优化**：P2 只做现金视角，不做补货算法
- **替代总账 / 法定收入引擎**：会计口径永远只读来自 GL
- **改动既有离线零售、IFRS 16、三表模型的任何口径**：发现既有问题走既有修正流程
