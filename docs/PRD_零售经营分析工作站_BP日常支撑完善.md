## 1. Problem Statement

### 1.1 财务 BP 视角（Review 一）

「单店发现 → 诊断 → 模拟 → 行动草稿」的闭环骨架真实可用，工程质量高于一般 MVP；但今天还支撑不了一个财务 BP 的完整日常工作：

- **没有预算对比。** 经营脉搏只有「当前窗口 vs 上一等长窗口」的环比，没有 Actual vs Budget/Forecast；而预算对比是 FP&A 每日工作量的大头，没有它谈不上经营分析工作站。
- **出不了系统。** 零售三个页面（经营脉搏、门店 360、情景工作台）零导出。关注榜、同群分位表、守恒桥、情景结果都无法生成 Excel/PPT 材料（WBR/MBR）。
- **没有跨店/跨区域视图。** 脉搏页无 region/brand/store 筛选 UI（后端 KPI 端点其实已支持 `group_by=region|brand`，前端没接）；门店 360 严格单店。
- **没有日历期语义。** 只有 7/14/28 天滚动窗口；「上月毛利为什么下滑」「Q3 表现如何」无法直接表达。
- **核心差异化缺位。** 情景只有七个全局百分比杠杆，无闭店动作、无 NPV/回收期、固定租金调整是百分比而非按合同条款。可行性报告中的工作台 E（占用成本与合同情景）与《renewal-termination-decision-card》spec 均未实现。
- **四个确定的交互逻辑 bug 直接伤害「分析结论可信」**（详见 §3 P0）。

### 1.2 AI Engineer 视角（Review 一）

治理边界是模范级（只读 Tool、scope 多层防护、Artifact-only、HITL 全部实锤），但 AI 工程存在确定性缺陷：

- **路由脆弱。** 规划靠关键词匹配 skill registry；「A 门店毛利下滑」这种没有「诊断/分析」字眼的自然提问可能路由不到 retail skill，而数据本身完全够回答。
- **引用保真度缺陷。** 模型没写引用时回退为挂上全部已知来源——引用可以被附加成模型从未做出的声明。
- **无成本护栏。** 整个 core-service 找不到任何 RateLimit；每条消息至少一次 LLM 调用；Web chat 无预算（agent-runner 有，Web chat 没有）。
- **Context 无上限。** 合同全量 dump + 性能 JSON 全量 + 客户端可控且未校验的 History 直接入 prompt → token 溢出风险 + prompt injection 面（注入拿不到权限提升，但能塑造叙述性回答）。
- **交互体验与死代码。** 页内嵌 AI 抽屉无会话持久化（页面一走对话即失）；专门写的深链构造是死代码没人调用；长回答同步阻塞至 4 分钟，SSE 实为 750ms DB 轮询而非 token 流。

### 1.3 数据链路视角（Review 二）

零售侧「文件 → AI 解析 → 入库 → BI 展示」整条链不存在（合同侧这条链完整且质量高）：

- **store-day 事实（新 BI 的数据源）没有任何文件入口。** 财务拿着 POS 导出的 Excel，今天没有任何办法把它弄进经营脉搏/门店 360/情景工作台；唯一非模拟入口是手写 JSON 调 API——那是开发者行为，不是用户行为。BI 页只能看模拟数据，对真实用户确实是鸡肋（与仓库自述「真实 POS/ERP 接入是试点第一阻塞项」一致，但「全量 POS 对接」与「Excel 手动导入」之间还有一整级便宜的台阶没修）。
- **月度导入器是「僵尸」状态。** 后端 CSV/XLSX 受控模板导入完整存在（行级隔离、批次、数据质量留痕，`POST /operating-facts/stores/import` + `import-xlsx`），但没有任何页面调用，web 客户端函数（`operatingFactsApi`）是死代码。
- **预算与 Trial Balance 只有 JSON 或只有 spec。** 预算创建仅 JSON（无文件上传端点）；GL Trial Balance 连路由都没有（只有 ADR-0009 spec）。
- **讽刺的是最难的那半条链已经建完。** 合同侧 ai-intake.v1（文件解析、置信度、原文锚定、草稿审批）是全仓库质量最高的模块之一；受控模板导入器的后端模式也写好了——只是它们一个只服务合同域，一个写旧月度表（新 BI 按硬约束只读 store-day，读不到它），而且后者连前端都没接。

## 2. Solution

按六批推进，每批独立交付、独立验收：

| 批次 | 主题 | 交付物 | 对应 Review 诉求 |
|---|---|---|---|
| P0 | 可信度修复批次 | 4 个确定 bug + 8 个次级交互/口径问题 | Review 一：建议 1 + 交互 bug 清单 |
| P1 | BP 价值三件套 | 平台级导出（带公式 XLSX + 可编辑 PPTX）、跨店/区域视图、日历期语义、事实列表分类过滤 | Review 一：建议 2 + 点名收紧项；用户导出增强要求 |
| P2 | Actual vs Budget | 落地 fpna-version-lifecycle spec + 零售侧 vs 预算对比 | Review 一：建议 3 |
| P3 | AI Agent 加固 | 速率/成本护栏、context 有界、引用保真、意图路由强化；AI 工程收尾（会话持久化、死代码清理、访问审计、置信度来源、流式响应） | Review 一：建议 4 + 点名次级项 |
| P4 | 租赁续租/终止/闭店决策 | 落地 renewal-termination-decision-card spec（工作台 E） | Review 一：建议 5 |
| P5 | 数据入口与导入链路 | store-day 受控模板导入器 + 经营数据导入页、月度导入器僵尸收口、FP&A 导入（预算 Excel + Trial Balance）、解析格式补齐（CSV/docx） | Review 二：全部 4 项 |

所有批次遵守既有五条底线（跨法人隔离、模拟/正式区分、来源追溯、重复导入保护、IFRS 16 正式台账隔离），以及零售经营分析约束（store-day 粒度、`retail-kpi-v1` 语义、不用 0 填缺失、显式降级、经营占用口径 ≠ IFRS 16 口径）。所有经营结论继续保持 `unvalidated` 口径（无真实 POS/ERP 联调、无客户验证）。

**排期说明**：P5-1（store-day 导入器）是 Review 二判定的最高杠杆项——「从内部演示走到试点可用最便宜的一步」，模式已由合同侧验证（受控模板 + 批次 + 数据质量留痕），无新技术风险；建议与 P0/P1 并行排期，不等待 P4。

## 3. User Stories

### P0 — 可信度修复批次

1. 作为财务 BP，我想在全局搜索里搜到门店后直接进入该门店的 360 页看到数据，而不是看到「未选门店」，以便从异常榜单直接下钻。
2. 作为财务 BP，我不想在情景工作台还没评估任何情景时看到「决策就绪」，以便不会被不存在的数据误导。
3. 作为财务 BP，我想让经营脉搏与门店 360 对同一家负贡献门店给出方向一致的环比（从 −100 改善到 −50 必须两边都显示为改善），以便相隔一次点击的两个页面不会互相矛盾。
4. 作为财务 BP，我在脉搏页修改来源系统筛选时，输入不应每敲一键触发全量查询，以便筛选体验与其他页一致（本地 state + Apply）。
5. 作为财务 BP，我想在 /performance 点「让 AI 解释」后，AI 对话页能收到我选中的行动上下文，以便不必重打一遍问题。
6. 作为财务 BP，我想在情景工作台随时切回 baseline 对照「什么都不做」，以便判断方案的真实增量。
7. 作为财务 BP，我想在三页间切换分类/窗口时看到一致的口径（默认窗口、硬编码重置行为、as_of 语义统一），以便对比时不被隐含的口径差误导。
8. 作为财务 BP，我想把情景方案分享给同事时链接能完整复现七个杠杆假设，以便协作讨论可复演。
9. 作为财务 BP，我采纳 AI 提案时验证窗口应与评估时看到的窗口一致，以便验证范围不被塌缩。
10. 作为财务 BP，我想知道混币门店的币种归属不被「最后写入」决定，以便多币种分区不产生错误计数。
11. 作为分析师，我想在覆盖超额（同店同日重复行）时得到报警，以便数据质量问题不被掩盖。
12. 作为维护者，我想让 ai_chat 集成测试注释里的引号与所引 SQL 逐字一致，以便文档引用可信（当前两处 Unicode 弯引号需还原）。

### P1 — BP 价值三件套

13. 作为财务 BP，我想在大多数功能页（经营脉搏、门店 360、情景工作台、performance 等）把数据导出为 CSV 或**带公式的 Excel**（合计行 =SUM、差异列 = 实际−预算、达成率带除零保护），以便拿到 Excel 后继续调整口径、自算数字，而不是拿到死值。
14. 作为财务 BP，我想在导出文件里看到口径头（数据分类、数据集版本、as_of、公式版本、期间），以便对外发送前自证数据口径；导出文件必须带 Working/模拟标识。
15. 作为财务 BP，我想在经营脉搏页按区域/品牌/门店查看汇总、趋势与关注榜，以便跨店比较而不必逐店点入。
16. 作为财务 BP，我想用「上月」「2026-07」「2026-Q3」这样的日历期查看经营数据，而不是只能选 7/14/28 天，以便回答「上月毛利为什么下滑」。
17. 作为财务 BP，我想在日历期与滚动窗口之间自由切换，以便周度晨检与月度复盘用同一套工具、同一套口径。
18. 作为分析师，我想让原始事实列表 API 支持按数据分类（production/simulated）过滤，以便收紧数据访问面、不会误把模拟行当正式行（Review 自评「可接受但值得收紧」；聚合路径保持安全，仅收紧列表读取面）。
19. 作为财务 BP，我想把关注榜、同群表与桥一键生成**可编辑的 PPTX**（原生文本框/表格/图表，不是图片贴图），以便直接在 PowerPoint 里修改后进入汇报流程。

### P2 — Actual vs Budget

20. 作为 FP&A，我想创建 Budget / Forecast / Scenario 版本并保留元数据（创建人、时间、来源、覆盖范围、Official 状态），以便识别计划漂移而不是覆盖原预算。
21. 作为财务 BP，我想把版本差异下钻到合同与期间并确认总额可复核（ties_out），以便理解差异来源。
22. 作为财务 BP，我想让 Actual 只来自已生成计量/关账结果的只读事实层，以便对比永远基于事实。
23. 作为财务 BP，我想在脉搏与门店 360 看到「本月实际 vs 本月预算」的差异与达成率，以便发现计划偏离。
24. 作为分析师，我想在预算覆盖不足、币种混杂或样本不足时看到显式降级，以便不把不完整对比当结论。
25. 作为财务 BP，我想对比 Forecast vs Budget 与 Forecast vs Actual 两种口径，以便分别回答「计划漂移」与「执行偏差」。

### P3 — AI Agent 加固

26. 作为平台管理员，我想对每个用户设置 AI 调用速率与成本上限，以便失控消息不会耗尽预算。
27. 作为财务 BP，我想让长合同/大数据集不撑爆上下文，以便复杂提问稳定返回（context 有界组装）。
28. 作为财务 BP，我想看到 AI 回答里标注「无引用」而不是被挂上与我的问题无关的来源，以便引用可信。
29. 作为财务 BP，我想用「A 门店毛利为什么下滑」这样的自然问法直接触发经营分析，以便不需要背技能关键词。
30. 作为安全工程师，我想让 History 与文件内容不无界进入 prompt，以便缩小注入面。
31. 作为审计，我想让 AI 的引用来源可追溯到具体 Tool 调用与门店范围，以便复演。
32. 作为财务 BP，我想在门店 360 / 情景页打开 AI 对话后，离开页面再回来时上下文仍在（或明确提示一次性会话），以便连续追问不重打。
33. 作为维护者，我想让已写好的深链构造被真实接线调用或删除，以便不留死代码。
34. 作为审计，我想让 AI 读取合同也经过 Tool runtime（带审计与维度收窄），以便所有数据访问与来源可追溯。
35. 作为分析师，我想让置信度反映真实信号（覆盖率、样本量、规则强度），而不是硬编码值，以便判断结论强度。
36. 作为财务 BP，我想在长回答时看到增量输出而不是长时间空白轮询，以便体验可控。

### P4 — 租赁续租/终止/闭店决策

37. 作为财务 BP，我想在同一张卡比较「按现条件续租 / 按新条件续租 / 重新谈判 / 终止/不续租」，以便做门店去留决策，而不是只看房东涨幅。
38. 作为业务负责人，我想看到五年现金曲线、租售比与退出成本，以便判断长期经济性。
39. 作为财务 BP，我想看到折现率来源；缺失时系统拒绝输出 PV/ROU/负债结果而不是猜测，以便假设不被默默制造。
40. 作为 Finance Reviewer，我想保存责任人、业务意见、决定日期与情景快照，以便之后复演当时使用的假设。
41. 作为审计，我想确保决策卡的保存/加载不改变正式合同、付款计划与会计计量结果，以便边界不破。

### P5 — 数据入口与导入链路

42. 作为财务 BP，我想把 POS 导出的 Excel/CSV 上传生成 production 的 store-day 经营事实，以便真实门店数据进入经营脉搏、门店 360 与情景工作台，而不是只能看模拟数据。
43. 作为财务 BP，我想在上传后看到列映射预览与校验报告（行级错误、预计覆盖率），以便确认后才真正入库。
44. 作为财务 BP，我想让导入强制记录来源信封（source_system、import_batch_id、as_of_at），以便每条事实可追溯。
45. 作为财务 BP，我想让同一文件重传不产生重复行（请求级与业务级幂等），以便出错时能安全重试。
46. 作为财务 BP，我想在确认导入后直接跳转到生产数据的经营脉搏，以便立即看到覆盖情况（覆盖率不足时诚实显示 `decision_ready=false`，BI 端零改动）。
47. 作为财务 BP，我想让 AI 建议「POS 表头 → 标准字段」的列映射（Assist Mode、人工确认），以便任意格式的 POS 导出都能快速完成映射；数字解析仍走 Go 确定性校验（LLM 不读数字）。
48. 作为财务 BP，我想在 /performance 直接上传月度经营事实 CSV/XLSX（或看到该功能被明确标记 deprecated），以便不会面对「后端通、前端断」的迷惑状态。
49. 作为 FP&A，我想用 Excel 模板导入预算/计划版本，以便预算数字不需要手写 JSON（与 fpna-version-lifecycle 落地同步）。
50. 作为财务 BP，我想导入 GL Trial Balance，以便「预算 vs 实际」的分析闭环能转起来（按 ADR-0009）。
51. 作为财务 BP，我想让 AI 解析支持 CSV 与 Word 文档（现在只有 PDF+Excel），以便常见业务文件都走同一条解析链。

## 4. Implementation Decisions

按模块给出（接口与接缝细节见 Codebase Design 文档；不在此重复文件路径）。

1. **环比/差异语义单源化。** 所有零售侧环比、差异方向、零分母与负基数处理收敛到 `retailkpi` 语义层既有的差异计算函数，并统一负基数基准约定（分母取绝对值，从 −100 改善到 −50 显示为改善）；门店 360 的桥不再私有实现公式。修 P0-3，防同类问题复发。
2. **期间规范模块（新）。** 统一滚动窗口（7/14/28 天）与日历期（月/季）的解析、默认值与重置语义；服务端三处窗口校验与前端三页默认值全部收敛到一个解析入口；日历期先支持显式 `YYYY-MM` / `YYYY-Qn` 与「上月/本季」映射。修 P0-7，支撑 P1-16/17 与 P2-23。fiscal 日历不在本轮范围。**两个先定后动的行为变更决策（2026-08-16 评审）**：(a) 默认窗口统一为 14 改变经营脉搏现状默认 7，属用户可见变更，需回归既有深链/书签并公告；(b) 既有校验形态不一（脉搏为 7–28 范围校验、门店 360 与情景为 {7,14,28} 集合校验），若收紧为枚举，`window_days=8` 等现存合法 URL 将变 4xx，需保留范围兼容或提供显式迁移策略。
3. **平台导出模块（新）。** 导出行为与口径头只实现一次，**平台级**能力：零售三页先行，其余功能页按同一列/公式描述符接入。输入为各服务的响应类型 + envelope（classification / dataset_version / as_of / formula_version / period），输出 CSV（服务端，口径权威、可审计复演）、**带公式的 XLSX**（前端 ExcelJS，MIT；`{formula, result}` 公式与缓存值同写，缓存值由导出模块从受控响应计算提供——写库库不代算，权威值正好在我们手里）与**可编辑 PPTX**（前端 pptxgenjs，MIT、浏览器端；原生文本框/表格/图表对象）。**XLSX 工作簿用原生 Excel Table**（命名表 + 合计行 `totalsRowFunction: 'sum'` + 筛选按钮 + 冻结表头），**公式用表列结构化引用**（如 `=IF(ISERROR([Actual]-[Budget]),"",[Actual]-[Budget])`），用户增删行后公式与合计自动跟随、可加切片器/筛选——即「BI 友好、可编辑」的工作簿。每个导出 kind 声明自己的列/公式描述符（合计 SUM、列间算术、比率 IF 除零保护），模块统一生成公式并防护公式注入（数据文本中 `= + - @` 开头一律转义）。导出与展示共享同一响应，不重读仓库（对齐既有 projection 纪律）。文件命名与表头带 Working/模拟标识。**（2026-08-16 评审补充）** 列/公式描述符两栈单源：Go（CSV 列序、口径头）与 web（XLSX 公式/Table、PPTX 布局）必须消费同一份描述符数据（JSON 下发或代码生成同步），禁止各写一份漂移；结构化引用除数据单元格 `= + - @` 注入转义外，对 Excel Table 表名/列名另做 sanitize 与转义（表头含 `[ ] # '` 等字符会破坏结构化引用语法）；浏览器端生成设体量预算（行数/内存上限），超限显式提示降级 CSV，不在浏览器内硬撑大工作簿。支撑 P1-13/14/19。
4. **跨店/区域视图。** 经营脉搏服务与页面增加 `group_by=total|region|brand|store`，复用语义层既有聚合与信号规则，区域级样本门槛沿用同群纪律（样本不足显式降级）；多币种分组内分区或降级。后端 KPI 端点已有该能力，属接线而非新建。支撑 P1-15。
5. **预算对比。** 落地既有 fpna-version-lifecycle spec（budget/forecast/scenario 版本、比较下钻、Actual 只读层、ties_out）；零售侧在语义层新增「实际 vs 计划」差异计算，计划事实来自既有 plan 行（store 粒度），月/季配对复用期间模块，覆盖率不足/混币/样本不足显式降级，材料性阈值从既有设置读取。支撑 P2。
6. **AI 意图路由强化。** 既有 skill registry 接口不变（`Select(intent) (Definition, bool)`），匹配策略加深：高频经营词（毛利、下滑、为什么、同群、贡献、闭店…）并入 retail skill 匹配；不引入 LLM function calling 主链路，保持确定性。支撑 P3-29。
7. **引用保真。** 模型未写引用时返回空列表并标注「无引用」，删除全量回退；引用仍须可追溯到具体 Tool 调用与门店范围。支撑 P3-28/31。
8. **AI 护栏（新模块）。** 每用户速率（每分钟消息数）与成本（每日估算上限）护栏 + context 组装预算（有界摘要优先于全量 dump、History 截断）；拒绝语义返回 429 并保留原因。agent-runner 既有预算语义（max-tool-calls / max-model-tokens）对齐复用。支撑 P3-26/27/30。
9. **续租/终止决策卡。** 按既有 renewal-termination-decision-card spec 落地为服务端模块，与计量引擎共用 snapshot/projection 接缝；折现率缺失拒绝输出（既有 HITL 纪律）；结果保存为不可变快照；经营分母取最新 store-day 事实并标注数据版本；保存/加载不触碰正式台账。支撑 P4。
10. **AI 会话持久化与深链收敛。** 零售页内嵌 AI 抽屉的会话上下文跨页面保留，或明确为一次性会话语义并在 UI 提示；既有深链构造被真实接线调用或删除，二选一不留死代码。支撑 P3-32/33。
11. **AI 访问审计收口。** 合同读取从绕过 Tool runtime 的直连改为经 Tool runtime（带审计、维度收窄），与「权限拒绝必须保持原因」纪律一致。支撑 P3-34。
12. **置信度来源化。** 零售 Agent 的置信度从硬编码改为由覆盖率、样本量、规则命中强度推导，输出保持向后兼容。支撑 P3-35。
13. **流式响应。** Web chat 长回答从同步阻塞/DB 轮询改为增量流式输出，或明确超时与进度语义；与 agent-runner 既有预算语义对齐。支撑 P3-36。
14. **事实列表过滤。** 原始 store-day 事实列表 API 增加 `data_classification` 过滤参数；聚合路径保持现状（安全），仅收紧列表读取面。支撑 P1-18。
15. **可编辑 PPTX 导出。** 导出模块的格式枚举扩展 PPTX（前端 pptxgenjs，MIT），生成原生可编辑对象（文本框/表格/图表），口径头与 Working/模拟标识与 CSV/XLSX 一致；用户已确认此需求，不再作为待定后续项。支撑 P1-19。
16. **store-day 受控模板导入器（新端点）。** 仿照既有受控模板导入模式（表头列名映射、行级隔离、批次与数据质量留痕），新增文件导入端点；强制来源信封（source_system、import_batch_id、as_of_at 缺一拒绝），复用既有原子 upsert + Idempotency-Key，500 行/批分块；只产 production 事实。**信封补全与修正政策（2026-08-16 评审）**：Commit 须补全完整 store-day 来源信封——`fact_version` / `dataset_version` 赋值策略显式定义（`retail-kpi-v1`「最高事实版本选择」依赖它），「导错一版、重导一版」的修正语义（新事实版本递增取代 vs 拒绝重叠）实现前定死，不靠 upsert 默认行为隐式决定；**门店身份解析**：POS 文件的门店名称/编码 → 门店主数据 + 法人归属的匹配规则显式化（精确/编码匹配，未匹配门店进校验报告而非静默跳过；跨法人文件拒绝或按行拆分归属，不得混入当前法人）。AI 列映射建议运行在 Assist Mode（只产出映射建议，人工确认后走 Go 确定性解析；数字不进 LLM；建议输入除表头外可附 Go 侧算好的列画像——类型直方图、日期格式识别、脱敏样本——提升映射质量且不违反数字不进 LLM）。支撑 P5-42～47。
17. **经营数据导入页（新页面）。** 上传 → 列映射预览 → 门店匹配结果 → 校验报告（行级错误、预计覆盖率、未匹配门店）→ 确认导入 → 跳转 `/operating-pulse?data_classification=production`；BI 端零改动（覆盖率不足由语义层诚实降级）。支撑 P5-42～47。
18. **月度导入器状态收口。** /performance 补导入 UI（客户端 API 已存在，属接线）或明确标记 deprecated，消除「后端通、前端断」。支撑 P5-48。
19. **FP&A 导入。** 预算版本 Excel 导入（与 P2 的 fpna-version-lifecycle 落地同步交付）与 GL Trial Balance 导入（按 ADR-0009 的 spec 落地）。支撑 P5-49/50。
20. **解析格式补齐（引入 AnyDoc 作为 office 家族解析适配器）。** ai-service 的解析器引入 Firecrawl AnyDoc（Rust、MIT、纯本地、无 ML/无外部服务/无 API Key）：docx/doc、ppt、xls/xlsb、odt、rtf、epub → GFM Markdown，接管「Word 合同」与旧版 .xls 两个当前缺口；CSV 用标准库确定性解析（不依赖 LLM，数字不进模型）；PDF 路径不变（PaddleOCR 优先 + PyMuPDF fallback，扫描件/图片仍走 PaddleOCR）；Word/office 文件无坐标体系，证据定位降级为 quote 锚点（page/coordinates 留空，UI 显示文本引用）；加密文件/超限文件返回明确错误并走人工路径，不静默成功。CLI 文件入口不在本轮（企业用户走 Web）。支撑 P5-51。
21. **数据库迁移双交付纪律。** M6 的 DB 计数适配器、M7 决策卡快照、M8 导入请求与数据质量留痕、P2 版本工作流状态，凡涉及 schema 变更一律同时交付增量迁移（`db/migrations/`）与 `db/init/01_init.sql` 空库版本——既有硬规则，在此显式重申以防新模块遗漏（2026-08-16 评审）。

## 5. Testing Decisions

- **每批产品级验收（2026-08-16 评审补充）**：除下述工程测试外，每批在看板登记时写一条可演示的产品级验收（例：P5 = 一份真实 POS Excel 经导入后在经营脉搏看到 production 数据与诚实覆盖率），避免「独立验收」只有工程口径。
- **好测试的标准**：只测外部行为（接口契约：输入 → 输出 + 错误语义），不测实现细节；每个模块的测试从它的接口 seam 驱动，不跨模块。
- **语义层（环比公式、预算对比、覆盖降级）**：纯函数单元测试。必备用例：负基数方向（−100 → −50 显示改善）、零分母、空值、混币、样本不足降级。先例：retailkpi 现有 testdata 单测。
- **期间规范模块**：月末/季末边界、as_of 交互、默认值一致性、非法输入 4xx。先例：既有服务窗口校验测试。
- **导出模块**：行结构、口径头、CSV 转义、文件名与分类标识；**公式用例**（合计/差异/除零保护、公式字符串含结构化引用且缓存值与受控响应一致的回读断言、`= + - @` 注入转义）；**表对象用例**（命名表存在、totalsRow 合计、筛选按钮、冻结表头）；PPTX 解包断言原生对象存在（非图片）；表名/列名转义（表头含 `[ ] # '` 时结构化引用存活）；handler 集成测试带 `format` 参数；描述符两栈一致性（Go 下发与 web 消费同一 JSON schema，防漂移）；超限降级路径。先例：既有 FP&A 行动导出 CSV 测试。
- **服务与 handler**：`group_by`、日历期、`format`、`data_classification` 参数的回显与错误路径。先例：各 retail handler 测试。
- **AI**：路由命中（自然问法如「毛利下滑」「为什么」）、引用空回退、护栏拒绝语义与预算记录。先例：aiagent / agenttools 零售测试。
- **AI 收尾**：页面往返后会话上下文保留的组件测试（vitest 先例）；死代码移除后无引用；合同读取经 Tool runtime 后审计日志可断言；覆盖率/样本不足时置信度下降；长回答分片输出或超时语义。PPT 生成的文件结构与口径头。
- **导入器（P5）**：幂等重放（同一文件 + Idempotency-Key 只落一批）、行级错误与部分成功、覆盖率报告、envelope 强制（缺字段拒绝）、fact_version / dataset_version 赋值与修正重传语义（新版本取代后查询取最新且旧版可追溯）、门店身份解析（未匹配门店进报告、跨法人拒绝或拆分）、500/批分块、权限（沿用既有 store-day 写入权限）；集成断言只写 store-day 事实、零写 IFRS 16 正式表；AI 列映射只产出建议（不含数值解析），人工确认后才入库。
- **僵尸收口（P5）**：/performance 上传路径可用性，或 deprecated 标注可被验证（页面无死链）。
- **格式补齐（P5）**：AnyDoc 解析用例（docx/ppt/xls 中文文档 → GFM Markdown）、加密文件与超限文件错误路径（明确报错不静默）、CSV 标准库确定性解析；docx 证据定位为 quote 锚点（page/coordinates 为空）。
- **集成**：真实 PostgreSQL 集成测试沿用 `TEST_DATABASE_URL` 模式（未设置时 skip）；P4 决策卡须有「正式台账零写入」e2e 证据（前后计数，先例：MAX-009）。
- **回归**：每批完成跑通 `cd core-service && GOCACHE=$(pwd)/.gocache go test ./... && go vet ./...` 与 `cd ../web && npm run type-check && npm run build && npm test`；IFRS 16 计量参考值不变。
