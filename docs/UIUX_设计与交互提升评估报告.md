## 0. 执行摘要

**一句话总评：这套 UI 的"设计意图"写得比多数企业级产品都好，但意图停在了文档里——真正跑起来的界面，是 903 处内联硬编码样式撑起来的，而不是那套 210 行的设计令牌撑起来的。**

三句话展开：

| 维度 | 判断 |
|------|------|
| **设计体系** | 单色体系的构思（12 级灰阶 + 靠对比/字重/间距/动效建立层级）是有品味的专业选择，令牌文件写得也很完整——但 `tokens.ts` **除 `theme.ts` 外零引用**，Tailwind 完整配置了却全库只有 **2 处 `className=`**，实际渲染由 573 行 `!important` 覆盖 + 903 处内联 hex 决定。体系存在于文档层，不存在于代码层。 |
| **交互实现** | 桌面主路径可用且有质感；但**窄屏彻底不可用**（375px 横向溢出、768px 表格 8 列只剩 3 列且无法滚动）、**头部四个控件键盘不可达**、**正文级灰度对比度不达 WCAG AA**。这三项是可复现的硬缺陷，不是主观审美分歧。 |
| **信息架构** | 16–18 个平级菜单项无分组无角色裁剪；结账中心把一个天然的流程（生成→复核→审批→过账→锁定）拆成 4 个互不相关的 Tab；首页 4 个 14 位裸数字无币种无量级。这是"功能都做了，但没有被组织"的典型状态。 |
| **生成痕迹** | 视觉层干净（0 渐变 / 0 玻璃拟态 / 0 emoji，配色克制到近乎苦行）；但结构层有明显的"完备却无人消费的脚手架"——`animations.ts` 18 个导出有 13 个从未被引用，12 级灰阶有 5 级只出现在自己的定义行。文案层有 4 处说教型副标题在向财务专家解释他们自己的工作。详见 §9。 |

**若只能做三件事**：① 修响应式与表格滚动（当前 1100px 以下审批状态列永久不可达，这是一个功能性阻断，不是体验问题）；② 导航按角色分组 + 状态进 URL（让系统从"能用"变成"顺手"）；③ 建立金额信息设计规范并落到首页 KPI（首页是每天第一眼，现在这一眼给不出任何判断）。

## 1. 当前设计资产盘点（做得好的，不要动）

评审的前提是先认清哪些是资产。以下几项达到或超过同类企业级产品水位，后续重构必须保留：

1. **单色设计语言的构思**。`tokens.ts` 开头那段"在无彩色系统里，层级靠对比 / 字体 / 间距 / 深度 / 动效五种手段建立"是正确且罕见的设计思考。方向不需要改，需要的是落地。
2. **`fmtMoney` 的设计**。强制传入币种、拒绝默认人民币、无法识别的币种代码原样显示——注释里那句"一份用 USD 计量的租约渲染成 ¥10,000.00 不是格式瑕疵，它陈述了一个与账簿不同的金额"是真正的领域理解。全库 107 处在用。
3. **AntD 主题映射的完整度**。`theme.ts` 覆盖 40+ 组件，是正确的"改一次全局生效"路径。
4. **AI Chat 的运行时分层**。`runtime/` 目录把 state / stream / transport / storage / factory 拆开并带测试，是全库工程质量最高的部分。
5. **动效令牌的克制**。时长上限 500ms、无弹跳、位移仅 4–8px——这是对的品味。
6. **`LanguageContext` 里"宁可不提供，也不给半成品语言"的判断**，以及注释中写明恢复条件。这是成熟的产品决策，注释也写清了为什么。

## 2. P0 — 可复现的硬缺陷

以下每一项都在本地实测复现，附度量数据。这些不是设计偏好问题。

### 2.1 窄屏不可用，且表格列永久不可达（最高优先）

**实测（合同台账页）：**

| 视口 | 现象 | 度量 |
|------|------|------|
| 375×812（手机） | 240px 侧边栏不折叠，占 64% 宽度；logo 与标题被完全挤出视口；页面横向溢出 | `scrollWidth 386 > clientWidth 375` |
| 768×1024（平板） | 8 列表格只有 3 列（合同编号 / 币种 / 租赁起始日）可见；**审批状态、范围、资产、操作按钮全部不可达**；空状态插图被裁切一半 | `table.scrollWidth 982 / clientWidth 390` |

**根因（两个叠加）：**
- `web/app/contracts/page.tsx:508` 外层 `Card` 设 `overflow: "hidden"`；
- `Table` 未设 `scroll={{ x: ... }}`，其自身 `overflow-x` 计算值为 `visible`。

两者相乘的结果是：**溢出的列既不显示也不能滚动，用户没有任何办法看到审批状态**。这不是"手机上不好看"，是笔记本外接副屏、分屏办公、iPad 现场看合同这些真实场景下的功能阻断。

全库 `@media` 查询数量为 **0**，响应式完全依赖 AntD `Col` 的 `xs/sm/lg`（70 处），而布局骨架（Sider 宽度、Content padding、Header 内容）全是固定像素。

**建议：**
- `AppLayout` 增加断点响应：`< 1024px` 自动 `collapsed`，`< 768px` 改为 `Drawer` 抽屉式导航 + Header 汉堡按钮；Content padding 由 `32px 48px` 降为 `16px`。
- 所有数据表统一设 `scroll={{ x: "max-content" }}`，并移除包裹 Card 的 `overflow: hidden`（或改为 `overflow: auto`）。
- `< 768px` 时表格切换为卡片列表视图（合同编号 + 名称 + 状态 + 金额四要素），而不是让用户横向拖八列。

**验收标准：** 375 / 768 / 1280 / 1920 四档下，`document.documentElement.scrollWidth === clientWidth`，且合同台账所有列可通过滚动到达。

### 2.2 页面内容被入场动画"扣住"

**实测：** 每个页面的内容都包在 `motion.div initial={{ opacity: 0 }}` 中。Framer Motion 依赖 `requestAnimationFrame`，而浏览器在 `document.visibilityState === "hidden"` 时不派发 rAF。实测登录页在此状态下，内容容器 `opacity` 冻结在 **0.018** 并持续不变——页面 DOM 完整，但视觉上是空白。

**⚠️ v1.2 升级：Recharts 图表受同一根因影响，且后果严重得多。**

给首页喂入真实感数据后实测，两张图表**完全空白**——但坐标轴、网格、图例全部正常渲染：

| 元素 | DOM 状态 | 后果 |
|---|---|---|
| 折线（`.recharts-line-curve`） | 路径 `d` 几何**完全正确**，但 `stroke-dasharray: "0px 718.7px"` | 整条线落在虚线的"空隙"里，100% 不可见 |
| 饼图扇区（`.recharts-sector`） | `d=""` 空路径 | 完全不渲染 |

Recharts 用 `stroke-dasharray` 从 `0 L` 动画到 `L 0` 来"画"线，用路径插值来展开扇区。rAF 不跑 → 冻结在第 0 帧。**因果已验证**：仅把 `stroke-dasharray` 置为 `none`，两条线立即以正确几何显现，数据一直都在。

这比页面淡入严重得多——淡入至少留下 0.018 的残影，图表则是**带着完整坐标轴的空框**，用户读到的是"没有数据"，而不是"还在加载"。

**这很可能就是《产品发展与 UIUX 优化建议书 v1.5》执行摘要里那条「仪表盘趋势图永久空白」的真实成因**——此前被归因为数据缺口，实际是动画冻结。若属实，该项的修复成本远低于原估。

**影响面：**
- **无障碍（确定影响）**：全库 `prefers-reduced-motion` 处理数量为 **0**。前庭功能障碍用户无法关闭入场动效，不符合 WCAG 2.3.3 (AAA) 与 2.2.2 的精神。
- **自动化捕获（确定影响）**：打印 / PDF 导出 / 视觉回归测试 / 截图型售前材料都会拿到**空白图表**。对一个要出审计底稿和披露附注的系统，"报表打印出来图是空的"是会真实发生的。
- **后台标签页预渲染**：切回前台后动画会恢复，交互用户实际不受影响——此项风险有限，不必夸大。

**建议：**
- **所有 Recharts 组件设 `isAnimationActive={false}`**（`LineChart` / `PieChart` / `BarChart` 的 `Line` `Pie` `Bar` `Area` 均需单独设置）。数据图表的入场动画本就没有信息价值，对财务图表尤其如此——用户要的是数字，不是数字长出来的过程。
- 在 `layout.tsx` 外层包 `<MotionConfig reducedMotion="user">`，一行解决 Framer Motion 的减少动效响应。
- `globals.css` 增加：
  ```css
  @media (prefers-reduced-motion: reduce) {
    *, *::before, *::after {
      animation-duration: 0.01ms !important;
      animation-iteration-count: 1 !important;
      transition-duration: 0.01ms !important;
    }
    html { scroll-behavior: auto; }
  }
  ```
- 页面级入场动画改为"内容默认可见 + 动效叠加"（`initial={false}` 或用 CSS `animation` 而非 `opacity: 0` 起始态），确保任何情况下内容不会因动画未执行而不可见。

### 2.3 灰度对比度不达 WCAG AA

**计算值（白底 #FFFFFF）：**

| 色值 | 对比度 | AA 正文（4.5:1） | 使用次数 | 实际用在哪 |
|------|--------|------------------|----------|-----------|
| `#8C8C8C` | **3.36:1** | ❌ 不通过 | 65 处 | 页面副标题、表格元信息、图表轴标签、占位符 |
| `#BFBFBF` | **1.84:1** | ❌ 严重不通过 | 21 处 | KPI 副标题、"Working"版本标记、登录页提示、通知时间、表格操作图标默认色 |

`#BFBFBF` 在 1.84:1 下已经接近"看不见"。而它承载的信息不是装饰性的——**"Working / Official"版本标记用的就是这个色**，这恰恰是本系统审计控制叙事里最关键的一个状态区分。

**建议：** 建立三级文本色阶并写死为唯一来源：正文 `#262626`（15.3:1）、次要 `#595959`（7.0:1）、弱化 `#737373`（4.6:1，刚过 AA）。`#8C8C8C` 与 `#BFBFBF` 降级为**仅用于非文本元素**（分隔线、禁用态图标、图表网格线）。任何承载语义的文字不得使用。

### 2.4 头部四个控件键盘不可达

**实测：** `.ant-layout-header` 内可聚焦元素共 **4 个**——2 个面包屑链接 + 搜索输入框 + 输入框清除按钮。

**不可达的控件**（均为 `<div onClick={...}>`，无 `tabIndex`、无 `role`、无 `aria-label`）：
- 侧边栏折叠开关 `AppLayout.tsx:293`
- 通知铃 `NotificationBell.tsx:150`
- 语言切换 `AppLayout.tsx:344`
- 用户菜单 / 登出 `AppLayout.tsx:374`

通知下拉里的每一条提醒项同样是 `<div onClick>`（`NotificationBell.tsx:105`）——**键盘用户无法打开任何一条到期提醒**。

全库应用自身编写的 `aria-*` / `role` 属性共 **2 处**（页面上检测到的 66 处全部来自 AntD 组件自带）。

**建议：** 上述交互元素一律改为 `<button type="button">`（配合 `Button type="text"` 保持视觉不变），补 `aria-label` 与 `aria-expanded`。这是低成本、高确定性的修复。

### 2.5 后端英文原始错误直出中文界面

**实测截图可见**：合同台账页顶部弹出 toast — **"invalid token"**，一个全中文界面里出现的英文技术错误串。

根因是全库统一模式 `message.error(error.message || t("xxx.load_failed", language))`：只要后端返回了任何 `message` 字段，就直接显示后端原文，本地化文案永远走不到。

**建议：** 在 `lib/api.ts` 层建立错误码 → 本地化文案的映射，`apiRequest` 抛出结构化错误（`{ code, message, detail }`），UI 层只消费 `code`。同时为 401 建立统一处理（提示"登录已过期"并跳登录页），而不是把 `invalid token` 甩给用户。

### 2.6 状态 Tag 配色失效（已复核确认，P0 首位）

> v1.0 初稿此项标注为"待复核"。用户反馈证实："有些浅色底浅色字，有些深色底深色字。" 已隔离渲染实测，确认并定位根因，详细修复方案见 **§8**。

**根因是两层叠加：**

**第一层 — AntD 调色板算法在无彩色种子色上失效。** `generate()` 的浅色变体依赖种子色的饱和度，`theme.ts` 传入的是饱和度为 0 的灰阶：

| theme 种子色 | `generate()[0]` → Tag 背景 | `generate()[6]` → Tag 文字 | 原生渲染 |
|---|---|---|---|
| `colorSuccess` = `#000000` | **#404040** | **#000000** | 深底深字 **2.03:1** |
| `colorError` = `#000000` | **#404040** | **#000000** | 深底深字 **2.03:1** |
| `colorWarning` = `#262626` | **#666666** | **#000000** | 深底深字 **3.66:1** |
| `colorInfo` = `#595959` | **#999999** | **#333333** | 4.44:1（勉强） |

预期中的"浅色淡底"根本没被生成出来——最浅的一档就是 #404040。

**第二层 — `globals.css` 的白字补丁打歪了。** 那句 `color: #fff !important` 把上面四个全刷成白字：success / warning / error 因此被"救活"（10.37 / 5.74 / 10.37:1），但 `processing` 本来就是浅灰底，白字上去变成 **2.85:1**。

**这就是两个方向的来源：** 深底深字是原生状态，浅底浅字是补丁的副作用。

**实测全量结果（隔离页面渲染 + 计算对比度）：**

| Tag | 底 | 字 | 对比度 | AA |
|---|---|---|---|---|
| `processing`（13 处，最常用） | #999999 | #ffffff | **2.85** | ❌ |
| `gold` | #fffbe6 | #d48806 | **2.76** | ❌ |
| `orange` | #fff7e6 | #d46b08 | **3.34** | ❌ |
| `green` | #f6ffed | #389e0d | **3.37** | ❌ |
| `success` / `error` | #404040 | #ffffff | 10.37 | ✓ |
| `warning` | #666666 | #ffffff | 5.74 | ✓ |
| `default` / `blue` / `purple` / `red` | — | — | 5.07–21 | ✓ |

**⚠️ 重要的修复顺序约束：单独删掉 `globals.css` 那句 `!important` 会让情况变糟**——success / error 会从 10.37:1 掉回 2.03:1（深底深字）。两个补丁必须同时落地，见 §8。

**次生问题（比对比度更影响观感）：** 同一个状态列里混着三种视觉物种——4 个实心深灰块（success/warning/error/processing）+ 6 个淡彩色块（preset 系）+ 1 个浅灰块（default）。密集表格中扫下来是一堵灰墙，颜色不再编码任何含义。

### 2.7 i18n 键名被直接打给用户（全库 20 处，含发给 AI 的上下文）

**实测（首页喂入真实感数据后）：** 页面底部「未来关键日期」区块直接渲染出以下字符串——

```
dashboard.upcoming_critical_dates  4
  续租通知截止日
  2026-08-09 · dashboard.reminder_days        [renewal_notice] [dashboard.overdue_days]
```

**根因：** `i18n.ts:6676` 的 `t()` 在缺键时**直接返回键名**：

```ts
const entry = dict[key];
if (!entry) {
  return key;      // ← 键名原样上屏
}
```

**全库差集实测：20 个被调用的键在 6,688 行字典里不存在**（脚本见 §7.1 ①），分布在 4 个页面：

| 分组 | 数量 | 键 |
|---|---|---|
| 首页 | 6 | `dashboard.upcoming_critical_dates` `dashboard.reminder_days` `dashboard.overdue_days` `dashboard.within_days` `dashboard.remaining_days` `dashboard.no_upcoming_dates` |
| **报表页 → AI Chat 交接** | **11** | `reports.ai_chat_mode` `..._working` `..._official` `..._view` `..._granularity` `..._period` `..._interest` `..._depreciation` `..._closing_liability` `..._closing_rou` `..._report_title` |
| 其他 | 3 | `reports.amortization_group` `ai.draft_select_at_least_one` `settings.journal_policy_saved` |

**其中 `reports.ai_chat_*` 那 11 个比显示错误更严重——它们不是显示给人看的，是拼进发给 AI 的上下文串的。** `reports/page.tsx:738–751`：

```js
parts.push(`${t("reports.ai_chat_mode", language)}: ${...}`);
parts.push(`${t("reports.ai_chat_closing_liability", language)}: ${fmtMoney(...)}`);
const summary = parts.join('; ');
let url = `/ai-chat?...&summary=${encodeURIComponent(summary)}`;
```

所以点「让 AI 解释这张报表」，模型实际收到的是：

```
reports.ai_chat_mode: reports.ai_chat_working; reports.ai_chat_view: summary;
reports.ai_chat_closing_liability: ¥1,284,567.00; ...
```

模型大概率还能猜对（键名语义透明），但**提示词质量被削弱，且这段字符串会原样出现在聊天记录里**——这是产品最核心的差异化功能，演示时会直接暴露。

同一首页区块还把 `date_type` 的原始枚举值 `renewal_notice` 当标签显示，未做映射。

**为什么之前没被发现：** 这些区块都只在有对应数据时才渲染（关键日期需未来 90 天内有记录，AI 交接需先查出报表）。空环境与当前 demo 种子数据完全看不到——**恰好在有真实数据的客户环境暴露**。这与 §2.6、§2.8 同属"只在有数据时暴露"的一类，共同指向 §7.0 缺少固定回归数据集这个根本原因。

**建议（三层）：**
1. 补齐这 20 个键（含 zh-HK / en），并为 `date_type` 建立枚举 → 文案映射。
2. **改掉 `t()` 的缺键回退策略**：开发环境 `console.error` 并渲染醒目占位（如 `⟦missing:dashboard.overdue_days⟧`），生产环境回退到 `zh-CN` 或空字符串——**绝不能把点分键名当作文案上屏**，更不能拼进发给模型的提示词。
3. **加 CI 门禁**：§7.1 ① 的差集脚本，非空即失败。这是一个"静默失败伪装成正常输出"的典型案例，靠人工评审发现不了，必须由构建期校验兜住。

### 2.8 多币种下首页图表与 KPI 全部算错（P0，数字错误）

**症状：** 「租赁负债趋势」折线呈锯齿状，每月在 0 与峰值之间来回震荡，某个月份之后突然变回平滑的单调递减曲线。租赁负债期末余额在数学上不可能这样。

**后端没有错，前端的假设错了。**

`services/reporting/amortization_projection.go:196`：

```go
separateCurrencies := request.View != ViewContract && len(currencySet) > 1
```

组合中只要存在第二种币种，`summary` 视图就**按币种拆行**（`GroupKey` = `summary|CNY` / `summary|USD`），即**每个 `period_key` 返回 N 行，N = 币种数**。这是刻意且正确的设计——它拒绝把 USD 加进 CNY，与 `fmtMoney` 的口径一致。

而 `web/app/page.tsx:190–221` 假设"每期一行"，于是同一份数据被四种方式误用：

| 位置 | 代码 | 后果 |
|---|---|---|
| `:194` 趋势图 | `rows.map()` 逐行成点 | 每期 N 个点；`XAxis dataKey="period"` 是分类轴，重复的 period 成为相邻独立刻度槽 → **锯齿** |
| `:204` 总租赁负债 / 使用权资产 | `pastRows[pastRows.length - 1]` 取**末行** | 只反映**一个**币种的余额 → **系统性低估** |
| `:205` 本月租赁费用 | `rows.find()` 取**首个**匹配行 | 同样只有一个币种；且 `find` 取首、上面取尾，**两张卡可能基于不同币种** |
| `:208` 未来 12 个月现金流出 | `.reduce()` 累加全部行 | **跨币种裸加，不折算** |

**即同一行四张 KPI 卡使用了三种互不相同、且都不正确的聚合口径**，同时都不显示币种（§3.3）。这是首页最显眼位置上的**错误数字**，不是观感问题，故列入 P0。

**诊断佐证：** 曲线由锯齿转平滑的那个月份，正是第二币种下最后一份合同到期、不再产生 bucket 的月份。谷底为 0 通常是因为该币种组由短期/低价值豁免合同构成——豁免合同费用化，无负债、无 ROU。

**修复：**

```js
const currencies = new Set(rows.map(r => r.currency).filter(Boolean));

if (currencies.size <= 1) {
  // 单币种：按 period_key 合并（幂等），KPI 取合计，并显示币种符号
} else {
  // 多币种：图表按币种分系列（每币种一条线或分面），
  // KPI 分币种小计或提供币种切换器 —— 不做合并
}
```

**⚠️ 关键约束：在汇率表落地前不要合并成一个数。** 后端确有 `applyProjectionExchangeRate`，但其 `exchange_rate` 是调用方手工传入的平乘——《产品发展与 UIUX 优化建议书 v1.5》§2.2 已判定"外币记账是断链的：无汇率表、无期末重估、无折算损益"。**用手填汇率在首页合成一个总额，比现在的锯齿更危险**：锯齿一眼看得出不对，一个基于假汇率的合计数看起来完全正常，却会被当作真实敞口向上汇报。

**连带检查结果：缺陷仅存在于首页，另外两个调用点没问题。**

- `/cashflow-forecast:137` 与 `/reports:269` 都只做 `setData(res.data)` 后**以表格渲染**，且表格带「币种」列（`reports/page.tsx:118,566`）。每期多行在表格里是**正确且诚实**的呈现——用户看得到币种列。
- `/reports` 还允许用户显式传 `report_currency` + `exchange_rate`，即折算是**用户主动选择**的，不是系统偷偷做的。这是对的设计。

**修复成本比预想低得多——正确的实现已经存在于本代码库，首页没有复用它。**

`reports/page.tsx:340` 的 `amortSummary` 已经解决了同一个问题：

```js
// latest period per group_key for closing balances
amortData.forEach((row) => {
  const key = row.group_key || "__default__";
  const existing = groupMap.get(key);
  if (!existing || row.period_key > existing.period_key) groupMap.set(key, row);
});
const latestRows = Array.from(groupMap.values());
...
currency: currencies.size === 1 ? Array.from(currencies)[0] : null,
```

它做对了两件首页做错的事：

| | `/reports` `amortSummary` | 首页 `page.tsx` |
|---|---|---|
| 期末余额取数 | **按 `group_key` 分组后各取最新期再合计** → 不漏币种 | 全局取末行 → **只剩一个币种** |
| 币种标注 | 混合时 `currency: null`，宁可不命名 | 不显示币种，也不区分 | 

其源码注释写明了理由：*"合计会把不同币种计量的行加在一起。只有当它们全部一致时，摘要才能命名一个币种；否则宁可不命名，也不去断言这些数字并不共享的币种。"* 这与 `format.ts` 里 `fmtMoney` 的判断同源。

**因此本项的最小修复 = 把 `amortSummary` 抽成共享 hook（如 `useAmortizationSummary`），首页改为复用**，并把趋势图改为按 `group_key` 分系列。工作量从"中"降为"小"。

**⚠️ 但不要止步于此。** `amortSummary` 仍然是把各币种的期末余额**数值相加**，只是诚实地不给它安一个币种标签。对表格页的摘要行这可以接受；对首页那个 26px 的头条数字则不够——一个无币种的十亿级数字仍会被当作真实敞口向上汇报。首页应当在汇率表落地前**按币种拆分展示**（或提供币种切换器），落地后再合并并标注折算基准与汇率日期（见 §5.3 多币种聚合规则）。

## 3. P1 — 结构性问题（信息架构与工作流）

### 3.1 导航 IA：16–18 个平级项，无分组、无角色裁剪

**实测：** 1280×720 视口下，侧边栏最后 3 项（Agent 运营 / 设置 / 管理后台）需要滚动才能看到。菜单项全部平级，无任何分组。

**三个具体问题：**

1. **无分组** — 首页、我的待办、合同台账、AI Chat、报表查询、经营驾驶舱、组合分析、签约前决策、条款比价、敏感性分析、多准则对比、现金流预测、结账中心、ROI 测算、审计日志、Agent 运营、设置、管理后台，一条直线排下来，用户无法形成心智模型。

3. **图标重复** — 三对菜单项共用同一图标：`BarChartOutlined`（报表查询 / Agent 运营）、`SafetyOutlined`（多准则对比 / 管理后台）、`LineChartOutlined`（敏感性分析 / 现金流预测）。图标失去区分功能，纯装饰。

**建议 — 四组式导航：**

| 分组 | 菜单项 | 可见角色 |
|------|--------|---------|
| **日常作业** | 我的待办、合同台账、AI Chat | 全部 |

| **会计与合规** | 结账中心、报表查询、多准则对比、审计日志 | 会计 / 审批人 / 审计 |
| **系统** | 设置、Agent 运营、管理后台 | 管理员 / 审计 |

首页从菜单中移除，改由左上角 logo 承担（Logo 点击回首页是通用约定，现在 logo 不可点）。分组后单个角色实际看到 6–9 项，全部在首屏内。同时为每个菜单项配唯一图标。

### 3.2 结账中心是 Tab 堆叠，不是流程

**现状：** `monthly-closing/page.tsx`（1,413 行）用 4 个平级 Tab 组织：`generate`（生成分录）/ `entries`（分录列表）/ `batches`（批次）/ `lock`（期间锁定）。

**问题：** 月结在业务上是一个严格有序的状态机——**选期间 → 检查就绪度 → 生成分录 → 复核 → 审批 → 过账 → ERP 回写 → 锁定期间**。把它拆成 4 个互不相关的 Tab，等于要求用户自带流程知识。新会计第一次用，不知道该先点哪个 Tab；老会计每月重复，也要靠记忆在 Tab 间跳。

而这套系统的差异化恰恰是控制框架（三级审批 + SoD + 期间锁 + Working/Official 双模式）。**控制框架的价值必须在界面上"看得见"才卖得动**——现在它散落在 4 个 Tab 里，演示时讲不成一条线。

更可惜的是，`/todo` 页已经拿到了 `CloseReadiness`（含 `status`、`blocking_count`、`findings[]` 带 `remediation`）和 `CloseException` 数据——**流程编排需要的数据全都有了，只是没有被编排**。

**建议 — 改为"结账驾驶舱"单页：**

```
┌─────────────────────────────────────────────────────────┐
│  2026-07 结账          ● 进行中    负责人：张会计         │
│  ①就绪检查 ─── ②生成 ─── ③复核 ─── ④审批 ─── ⑤过账 ─── ⑥锁定│
│    ✓ 通过      ✓ 128笔   ⚠ 3项待处理   ○        ○      ○  │
├─────────────────────────────────────────────────────────┤
│  ⚠ 阻断本期结账的 3 项（点击直达处理页）                   │
│    · CT-2024-0311 缺折现率        → 去补录                │
│    · CT-2024-0417 事件未生成分录  → 去重算                │
│    · 批次 B-07-02 未回写凭证号    → 去回写                │
├─────────────────────────────────────────────────────────┤
│  [ 下一步：提交 125 笔分录复核 ]      ← 唯一主 CTA         │
└─────────────────────────────────────────────────────────┘
```

要点：① 顶部步骤条即当期状态，一眼知道卡在哪；② 阻断项清单直接消费已有的 `findings[].remediation`，每条带跳转；③ **任何时刻只有一个主 CTA**，就是"下一步"；④ 现有 4 个 Tab 降级为详情抽屉（需要时展开分录明细、批次列表），不再是导航主干。

同一模式可复用到合同审批流。

### 3.3 首页 KPI：无币种、无量级、假精度、未标 Working

四个问题叠在同一个组件上（`DashboardCards.tsx:78`）：

```tsx
{value.toLocaleString("zh-CN", { minimumFractionDigits: 2, maximumFractionDigits: 2 })}
```

1. **没用 `fmtMoney`** — 全库 107 处都在用的、专门为"金额必须带币种"设计的函数，最显眼的四个数字反而绕过了它，直接裸 `toLocaleString`。
2. **无币种符号** — 用户看到 `1,284,567,890.00`，不知道是人民币还是港币。
3. **多币种静默相加** — 数据来自 `reportApi.amortization` 汇总，跨币种合同的负债被直接加总，界面上没有任何提示。这与 `fmtMoney` 注释里那句"它陈述了一个与账簿不同的金额"是同一类错误，只是发生在聚合层。

5. **未标 Working** — `page.tsx:182` 硬编码 `mode: "working"`。而 `/reports` 页把 Working / Official 做成醒目的 Radio 切换 + 警示语（"工作版数据，未定版"）。**最常被看的那块屏幕，反而不说自己在展示未定版数字。**

### 3.4 界面状态不进 URL

**实测：** 全库写查询参数的调用（`router.replace` 带 query）数量为 **0**。`useSearchParams` 仅 2 处（`reports`、`ai-chat`），且都是单向读取，从不回写。

**后果：**
- 刷新页面 → 筛选、Tab、会计期间、分页全部重置
- 无法分享链接 → "把那个 2026-07 的负债滚动报表发我看看"做不到，只能截图
- 浏览器后退键无法撤销 Tab 切换
- 无任何用户偏好持久化（每页条数、默认法人主体、默认期间、列配置）

对一个财务/审计工具，"发个链接过来"是每天发生的高频动作。这一项的性价比很高——技术上就是一个 `useUrlState` hook，一次实现，所有列表页与 Tab 页复用。

**建议：** 建立 `useUrlState(key, defaultValue)` hook，把筛选条件、Tab key、期间、分页统一同步到 querystring（`router.replace`，不产生历史记录污染）；用户偏好（每页条数、默认主体）存 localStorage。

### 3.5 合同台账：缺金额、缺风险标记、关键列会消失

**现状 8 列**：合同编号 / 合同名称 / 币种 / 租赁起始日 / 租期结束日 / 审批状态 / 范围 / 资产。

三个问题：

1. **没有一个金额列**。财务用户扫台账时想知道的是"哪几份合同负债最大""这个月要付多少"，现在全是文本属性，必须逐份点进详情。建议增列：租赁负债余额、ROU 余额、月租金（含右对齐 + 等宽数字 + 可排序）。

2. **`discount_rate_missing` 已取到却没渲染**。`page.tsx:51` 的 `Contract` 接口里有这个字段，数据也拿回来了，但表格里没有任何呈现。而这是一个会阻断计量的硬性风险位——应该做成行首的醒目标记，并支持"仅看有问题的"快筛。

3. **`合同名称`（唯一的人类可读标识）在窄屏会消失**。它是唯一设了 `ellipsis: true` 且不设 `width` 的列，其他 7 列都是固定像素——空间不足时，弹性列被压到 0 宽度。实测 768px 下该列在表头已完全不可见。建议给它 `minWidth`，并把它与合同编号合并为一个"主标识"单元格（编号小字 + 名称主字），这也是数据表的通行做法。

**筛选能力同样偏薄**：仅搜索 + 审批状态 + 排序方向。缺法人主体、门店、资产类型、租赁范围、到期区间（"6 个月内到期"是最高频的一个筛选）、以及保存筛选为"我的视图"。

### 3.7 全局搜索是个摆设，⌘K 名不副实

**现状（`GlobalSearch.tsx`）：**
- `contractApi.list(token)` **一次性拉取全量合同到前端**，用 `String.includes` 做本地过滤。几百份合同尚可，几千份就是明显卡顿 + 大流量。
- 只搜合同。搜不到报表、页面、门店、出租方、待办、设置项。
- `⌘K` 只是把焦点移到输入框，**不是命令面板**。用户按了 ⌘K 期待的是"输入即可跳任何地方 / 执行任何动作"。
- 无最近访问、无键盘上下选择、无分组结果、无搜索历史。

**建议：** 升级为真正的命令面板（Modal 形态，⌘K 唤起）：
- 搜索走服务端（`/api/v1/search?q=`，跨合同/门店/出租方/报表/分录）
- 结果分组：合同 / 页面 / 动作 / 最近访问
- 支持动作项："新建合同""跳到 2026-07 结账""导出披露附注"
- 完整键盘导航（↑↓ 选择、Enter 打开、Esc 关闭、Tab 切分组）
- 空查询时显示最近访问的 5 条 + 4 个高频动作

---

### 3.8 通知铃只暴露了六分之一的待办

**现状：** `NotificationBell` 只拉 `listUpcomingCriticalDates`（关键日期）。

而 `/todo` 页的 `WorkQueue` 结构里已经有 **6 类**：待复核合同、待审批合同、待处理事件、待审批分录、待过账分录、到期关键日期。铃铛只显示了第 6 类。

其余缺失：无已读/未读状态（每次打开都是全部）、无"查看全部"入口跳 `/todo`、无按类型分组、无操作（只能跳转，不能就地审批）。

**建议：** 铃铛改为消费 `workQueueApi.get`（数据已在），按类型分组显示，角标为总待办数；底部固定「查看全部待办 →」跳 `/todo`；加已读状态（本地即可）。这一项几乎零后端成本。

### 3.9 首页整体信息设计：回答错了问题

> §3.3 讲的是 KPI 卡的金额格式，本节讲整屏的信息设计。基于喂入真实感数据后的完整渲染判断。

**一句话：首页现在回答的是「系统里有什么」，它应该回答「我今天要干什么」。**

视觉手艺本身没有问题——字距、间距、留白干净，配色克制。问题是整屏 1400px 几乎不产出任何可据以行动的信息：

| 区块 | 占用 | 问题 |
|---|---|---|
| 4 张 KPI 卡 | ~120px | 等宽等重等字号，**没有头条**；无环比、无预算基准、无变化率。`1,151,929,734.00` 单独摆着无法判断好坏 |
| 「合同 128 份 · 已批 4 · 待批 2 · 草稿 1」 | 一行 12px 灰字 | **孤儿元素**，不属于上下任何容器；且与右侧饼图重复表达同一件事 |
| 租赁负债趋势折线 | ~380px | 两条几乎重合的单调递减直线。摊销曲线画成折线图信息量趋近于零，看完得不出任何决定 |
| 合同状态分布饼图 | ~380px | 与上面那行小字冗余 |
| 最近合同 | ~380px | **只显示合同编号**，无门店名、无金额、无到期日；且"最近创建"不是财务关心的排序 |
| 快捷操作 | ~380px | 3 项中 2 项与页头按钮重复、1 项与导航重复（详见 §9.1）；卡片被拉伸到与左侧 6 行列表等高，右下大片空白 |

布局节奏是 AntD 默认的 `4 卡 → 8:4 → 8:4 → 通栏`，所有卡片同圆角、同边框、同 hover——只有网格，没有层次。

**讽刺之处：** 回答"我今天要干什么"所需的数据**已经全部存在**——`/todo` 页的 `workQueue` 有 6 类队列（待复核合同 / 待审批合同 / 待处理事件 / 待审批分录 / 待过账分录 / 到期关键日期）+ `CloseReadiness` 的阻断项与 `remediation`。首页一个都没用，反而去拉了**全量合同表**（`contract.go:445` 显示分页是 opt-in，不传 `page_size` 返回全表）只为算四个计数和显示六行。

**建议 — 首页与待办页合并，重排为三层：**

```
今日待办                             2026-07 · Working 口径 · 数据截至 08-11 09:15

┌─ 需要你处理 ──────────────────────────────────────┐
│  7 项待审批分录 · 3 份合同待复核 · 2 个阻断项          │  ← 唯一的主要内容区
│  [ 去处理 → ]                                      │
└───────────────────────────────────────────────────┘

租赁负债  ¥12.85 亿  ▼ 1.8% 环比        本月费用  ¥2,519 万  ▲ 预算 +3.2%
                                        ← 两个带基准的数字，不是四个裸数

未来 90 天关键日期 (4)                  ← 保留，这是当前唯一即时有用的模块
```

具体处置：

- **删除**趋势折线（挪至报表页，那里才是看曲线的地方）、状态饼图、快捷操作卡、那行孤儿统计文字
- **改造**「最近合同」→「需要关注的合同」（缺折现率、临期未续、重估未生成分录），每行带门店名 + 金额 + 状态
- **KPI 从 4 个减到 2 个**，但每个都带基准（环比 / 预算），并按 §5.3 量级化
- **头部副标题**改为口径与新鲜度声明（见 §9.2）
- 数据源从"拉全量合同表"改为消费 `workQueueApi.get` + `getReadiness`

减少的模块不是损失——现在这 1140px 的三行卡片，实际信息量少于合并后的一个待办区块。

**不要加"早上好，{用户名}"式的问候语。** 本报告初稿的示意图里用了它，这与 §9.3 自己立的判据矛盾——问候既不回答"我该做什么"，也不回答"我看的是什么数"，属于同一类填充物。用户名应当出现在它有功能的地方（审批人、操作留痕、数据切片归属），而不是当寒暄。标题位直接写"今日待办"即可。

## 4. P2 — 设计体系的一致性问题

### 4.1 四套并存的样式来源

| 来源 | 规模 | 实际采用 |
|------|------|---------|
| `design-system/tokens.ts` | 210 行，完整令牌 | **除 `theme.ts` 外零引用** |
| `tailwind.config.js` | 完整配置（12 级灰阶、字号、间距、阴影、动效） | 全库 `className=` 仅 **2 处** |
| `globals.css` | 573 行 AntD `!important` 覆盖 | 实际生效 |
| 内联 `style={{}}` | **903 处**，硬编码 hex | 实际生效 |

也就是说：**写得最认真的两层完全没被使用，实际渲染由最难维护的两层决定。** 改一个灰度，要在 903 处内联样式里 grep 替换。

**建议（单一来源收口，分三步，可增量执行）：**
1. `tokens.ts` 成为唯一真源，`tailwind.config.js` 与 `globals.css` 的 CSS 变量都从它生成（或至少建立构建期一致性校验）。
2. 抽出 15–20 个通用组件消化掉大部分内联样式：`PageHeader`、`KPICard`、`SectionCard`、`DataTable`、`StatusTag`、`MoneyCell`、`EmptyStateWithAction`、`FilterBar`、`StepFlow`。仅 `PageHeader` 一项就能消除 20+ 个页面里重复的那段 `display:flex; justifyContent:space-between; marginBottom:32` 结构。
3. 加一条 lint 规则：禁止在 `.tsx` 里出现字面量 hex 颜色。

**这一项不必一次做完**，但应该在下一个新页面开始前定好，否则内联样式还会继续增长。

### 4.2 令牌漂移：边框有两个"默认色"

| 来源 | 值 |
|------|-----|
| `tokens.ts` `border.default` | `#E5E5E5` |
| `globals.css` `--border-default` | `var(--mono-90)` = `#D9D9D9` |
| 内联样式 | `#E5E5E5`（42 处） |

结果：走 `.ant-card` CSS 的卡片边框是 `#D9D9D9`，内联写的分隔线是 `#E5E5E5`，同一屏上并排出现两种"一样但不一样"的灰。而 `#E5E5E5` 甚至不在那套 12 级灰阶里（灰阶里是 `#D9D9D9` 和 `#F0F0F0`）——它是凭空多出来的第 13 级。

### 4.3 "无彩色系统"的宣言与实际不符

`tokens.ts` 宣称 `success: #000000` / `error: #000000` / `warning: #333333`。实际代码里：

- `#CF1322`（红）× 17、`#1677FF`（蓝）× 6、`#D46B08`、`#389E0D`、`#FFF7E6`、`#FFF1F0`、`#F6FFED` 等
- AntD 预设色 Tag 46 次，含 `blue` 5 / `orange` 4 / `green` 3 / `red` 1 / `gold` 1 / `purple`

**这不一定是错的——纯单色系统在财务软件里确实吃力**（红字、警示、通过/驳回，天然需要色彩编码）。问题是**没有做决定**：文档说无彩色，代码在偷偷用彩色，两边都不成体系。

**建议：** 承认并规范为"单色为主 + 语义色克制点缀"：定义 4 个语义色各一组（默认 / 浅背景 / 文字），全部满足 AA 对比度，写进 `tokens.ts`，删掉所有裸 hex。同时确保**颜色永不作为唯一编码**——每个语义 Tag 必须同时带图标或文字（当前 `Tag color="error"` 只靠颜色区分，色觉障碍用户读不出）。

### 4.4 所有卡片都有 hover 抬升

`globals.css:117` 的 `.ant-card:hover { border-color: strong; box-shadow: hover }` 全局生效。结果是纯展示用的 KPI 卡、图表卡、筛选栏卡在鼠标经过时都会"亮一下"，暗示可点击——但它们不可点。

**建议：** hover 效果改为显式类 `.card-interactive`，只给真正可点的卡片（快捷操作、最近合同行）加。

### 4.5 i18n 半成品与硬编码中文并存

- `lib/i18n.ts` **6,688 行**，覆盖 zh-CN / zh-HK / en 三语；`SUPPORTED_LANGUAGES` 只留 `["zh-CN"]`，切换器隐藏。（此决策本身合理，注释也写清了恢复条件。）
- 但**同时**，`AppLayout.tsx` 里 7 个菜单标签直接硬编码中文：经营驾驶舱、组合分析、签约前决策、条款比价、敏感性分析、多准则对比、ROI 测算；面包屑映射同样硬编码。
- 合同台账的「范围」「资产」两个列标题、`LEASE_SCOPE_LABELS`、`ASSET_TYPE_LABELS`、`STATUS/TYPE OPTIONS`（结账中心）也是硬编码。

即维护着一个三语字典的同时，又在新代码里绕过它。**目标客户若含港资/外资连锁**（zh-HK 语言包的存在暗示了这一点），这笔债迟早要还，而且会随页面增加而变贵。

**建议：** 加一条 lint 规则禁止 `.tsx` 中出现裸中文字符串（`test/` 除外），逼所有新文案走 `t()`。存量按页面分批回填。

### 4.6 命名与标识不一致

- 侧栏写「首页」，页面 H1 写「仪表板」——同一个页面两个名字。
- **产品 logo 是一个机器人图标**（`RobotOutlined`，同时用在 Header、登录页、以及 AI Chat 菜单项）。一个 IFRS 16 租赁核算与决策平台，用聊天机器人图标做品牌标识，会让第一眼印象偏向"AI 玩具"而非"审计级财务系统"。建议设计一个专属字标（哪怕只是一个几何标记），把机器人图标留给 AI Chat 功能本身。
- Header 的 logo 区域不可点击（无法回首页）。

### 4.7 控制台警告（技术债，会在升级时集中爆发）

实测控制台：
- `Warning: [antd: Card] bodyStyle is deprecated. Please use styles.body instead.` — 全库大量使用
- `Warning: [antd: Spin] tip only work in nest or fullscreen pattern.` — `ProtectedRoute`、首页

这些在 AntD 6 会成为破坏性变更。建议现在批量替换，成本极低。

### 4.8 关于改名：建议改定位语，不改产品名

> 起因：产品方提出"我们更像一个给 FP&A、FBP、财务、运营团队的经营分析平台"，考虑改名。本节只从"界面上显示什么名字、第一屏怎么叙事"的角度给结论，商业命名决策仍属 §6.5 范畴。

**当前对外名称**：`i18n.ts:173` `app.title` = 「租赁管理系统」/ `Lease Management`；`layout.tsx:9` `metadata.title` 同名。

#### 先确认一个前提变了

《产品发展与 UIUX 优化建议书 v1.5》§6.5 设过一条措辞红线：

> "在预算/实际对比、预测、决策支持层落地之前，对外不要自称『FP&A 系统』——demo 拿不出 budget vs actual 会透支信任。"

**这条红线的前提条件现在已基本满足。** 核查结果：

| v1.5 时点未落地 | 当前状态 |
|---|---|
| 预算/实际对比 | ✅ `handlers/budget.go`（543 行）+ `BudgetVariancePanel.tsx`（492 行），含 budget / forecast / scenario 三种版本类型 |
| 差异归因 | ✅ 六类驱动因子（新签 / 到期 / 续租终止 / 租金变更 / 指数调整 / 折现率） |
| 决策支持层 | ✅ `/pre-deal` 签约前决策（五年损益曲线、EBITDA 桥、退出成本）、`/deal-compare` 条款比价、`/performance` 经营驾驶舱 |

也就是说，"拿不出 budget vs actual"这个顾虑不再成立，**产品方的直觉在事实层面站得住**。

#### 但仍建议不改产品名，理由三条

**① §6.5 已就"不改名"做过决策，且理由未变。** 2026-05 刚从 `ifrs16-management-system` 改为 `lease-management-system`，波及容器名、数据库名、MinIO bucket、JWT secret、前端 branding。三个月内二次改名的迁移成本大于收益。

**② "经营分析平台"会加重 §6.5 诊断的那个病，而不是治它。** §6.5 判定「租赁管理系统」的问题是**承租方向歧义**（易被读成房东/融资租赁工具），处方是"补方向词 + 改第一屏叙事"。而"经营分析平台"比"租赁管理系统"更加方向中性——它丢掉了「租赁」这个唯一承载 IFRS 16 / Lease Administration 品类信号的词，搜索与品类心智一起丢。

**③ 命名会把定价权指向免费层。** §6.6 定了商业模式：**免费给出去的是"算的答案"，收费的是"可信的过程"**（台账、控制、留痕、披露）。"经营分析平台"正好命名在免费那一侧。而这个产品目前最强、最难被复制的资产恰恰是控制框架（三级审批 + SoD + 期间锁 + Working/Official + 披露包）——把名字从它身上挪开，等于放弃最硬的差异化叙事。

#### 建议动作：升级定位语，不动产品名

v1.5 当时的稳妥说法是「租赁合同管理与 IFRS 16 计量平台，**正在向**租赁 FP&A 延伸」。既然决策层已落地，这句可以去掉"正在"，升级为：

```
租赁管理平台
管好企业租来的门店、仓库、厂房与设备
—— 合同台账 · IFRS 16 合规 · 租赁经营决策
```

三段式对应三类买家（运营/地产 · 财务核算 · FP&A / FBP），**顺序不能反**：先说方向（"租来的"，消除房东工具误解）、再说合规（护城河）、最后说决策（增量）。英文仍按 §6.5 用品类词 `Lease Administration & Accounting Platform`。

界面上的落点很小，共四处：`i18n.ts` 的 `app.title`（保持）+ 新增一个 `app.tagline`、`layout.tsx` 的 `metadata.title/description`、登录页标题下方、README 首屏。**不涉及任何基础设施改名。**

**一个反向提醒：** 如果确实想让名字覆盖 FP&A/FBP，更稳的路径不是改主名，而是**按 §3.1 的角色化导航让不同角色看到不同的第一屏**——BP 登录看到的是经营驾驶舱和比价工具，会计登录看到的是待办和结账。同一个产品对不同角色呈现不同重心，比换一个试图同时讨好四类人的名字有效得多；四类人都想覆盖的名字，通常四类人都不认领。

## 5. 三个重点设计方案

### 5.1 方案 A：导航信息架构重构

见 §3.1 的四组式方案。补充两点：

- **分组标题不占太多空间**：用 11px 大写字母灰色标题，组间距 12px。折叠态下分组降级为分隔线。
- **配合命令面板**：分组导航解决"我知道要去哪"，命令面板（§3.7）解决"我知道要做什么"。两者互补，缺一个另一个的价值都打折。

### 5.2 方案 B：结账驾驶舱

见 §3.2 的线框。三条设计原则：

1. **流程即界面**：状态机的每个状态在界面上都有唯一对应的视觉位置。用户不需要知道"该点哪个 Tab"，只需要看"步骤条卡在第几步"。
2. **阻断项优先于一切**：如果有阻断项，页面主体就是阻断项清单，其他内容全部折叠。数据已在（`CloseReadiness.findings[].remediation`）。
3. **单一主 CTA**：任何时刻页面上只有一个黑色实心按钮，就是当前步骤的下一步动作。其他动作全部降级为次要按钮或抽屉内操作。

### 5.3 方案 C：金额信息设计规范

一个财务系统最该有规范的地方，现在恰恰没有。建议写入 `docs/` 并落成 `<MoneyCell>` / `<MoneyKPI>` 组件：

| 场景 | 格式 | 示例 |
|------|------|------|
| **KPI 大数字** | 量级化，3 位有效数字，hover 显示完整值 | `¥12.85 亿` |
| **表格金额单元格** | 完整值，右对齐，等宽数字（`font-variant-numeric: tabular-nums`），千分位，2 位小数 | `¥ 1,284,567.00` |
| **图表轴标签** | `Intl.NumberFormat` compact（当前 `DashboardCharts.tsx` 已正确使用） | `12.9亿` |
| **变化率** | 带符号 + 箭头 + 语义色 + 图标（不单靠颜色） | `▲ +2.3%` |
| **负数** | 括号（会计惯例）而非负号 | `(1,284.00)` |
| **零值 / 空值** | 空值用 `—`，零值用 `0.00`，**二者必须可区分** | — |
| **多币种聚合** | 必须显式标注折算基准与汇率日期，或拆分展示 | `含 USD 2 笔 · 按 6.8 折算` |
| **未定版数据** | 所有 Working 模式数字带统一角标 | `[工作版]` |

## 9. AI 生成痕迹清理

> 本章回答一个专门的问题：这套界面里有没有"AI 味"？

**先说结论：视觉层几乎是干净的，痕迹全在结构层和文案层。**

排查了典型的生成式视觉俗套，结果如下——**0 处**紫蓝渐变、**0 处** backdrop-blur / 玻璃拟态、**0 处** emoji 当图标、**0 处**无意义 hero 区。全库仅 3 处 `gradient`，全是功能性的（骨架屏 shimmer ×2、登录页 1px 点阵背景）。配色克制到近乎苦行，这恰恰是生成式默认不会产出的东西——**这部分是真设计，应予保留。**

问题在另外两个地方。

### 9.1 症状一：完备但无人消费的脚手架

同一个模式重复了四遍——生成一套看起来专业完整的体系，但它的完整性是为了"看起来完整"，不是被需求推出来的：

| 资产 | 规模 | 实际消费 |
|---|---|---|
| `design-system/tokens.ts` | 210 行 | **0 个外部消费者**（仅 `theme.ts`） |
| `design-system/animations.ts` | 18 个导出 | **13 个从未被引用** |
| `tailwind.config.js` | 完整配置 | 全库 `className=` **2 处** |
| 12 级灰阶 | 14 个色值 | **5 级在全库只出现 1 次——就是它们自己的定义行** |

**灰阶那条最能说明问题。** `#0A0A0A` / `#141414` / `#434343` / `#737373` / `#A6A6A6` 五个色值，全库检索各命中 1 次，位置都是 `globals.css` 里 `--mono-N:` 的定义行本身。从未被任何一处消费。所谓"12 级灰阶"实际是 9 级。

更麻烦的是**注释断言了代码不遵守的规则**：

```
10: "#141414",  // Primary buttons, active states   ← 主按钮实际用 #000000
 5: "#0A0A0A",  // Deep surface (modal overlay)     ← overlay 实际是 rgba(0,0,0,0.4)
```

注释描述的是一个想象中的系统。真人写设计令牌通常是"不够用了才加一级"，一次给满 12 级并给每级配一句用途说明，是生成物的特征。

另外全库 **530 处 `─────` 装饰性分隔注释**（集中在 `animations.ts` 12 / `i18n.ts` 10 / `ai-chat` 10 / `monthly-closing` 9），也是很强的生成签名。此项无害，不必专门清理，但在收敛设计体系时可以顺手减少。

#### 为什么这是生成痕迹

两个修辞结构是签名级的：**「不是 X，而是 Y」的对偶句**、**「A → B → C → D」的箭头链工作流概括**。生成模型被训练成要论证要升华，让它"写个页面副标题"，默认产出一句立论——因为立论在散文里读起来才像洞察。但界面文案不是散文。

#### 为什么这比视觉俗套更值得修

**一是权威倒置。** 这几个页面的用户是财务 BP、FP&A 负责人、Controller，从业十几二十年。系统告诉他"你要回答的问题不是记账，而是经营影响"——他当然知道，他就是因为知道才点进来的。这句话暗示了对方可能不知道自己的工作是什么。对一个要卖给专业买家的产品，这是负资产。

**二是它会腐烂。** 立论只在第一次有意思。第 50 次打开这个页面，它就是一句永远不变、占着首屏最好位置的噪音。

#### 那个位置应该放什么

有个巧合：说教文案占的这块地，恰好是 §7 检查清单里点名缺失的东西该放的位置——**数据口径与新鲜度**。对财务工具而言，标题下面那行字最该回答的是"我现在看的是什么口径的、什么时候的数"：

```
经营驾驶舱
2026-07 · Working 口径 · 数据截至 08-10 18:00 · 12 家门店未对账

签约前决策
未保存方案 3 个 · 上次测算 08-09

仪表板
Working 口径 · 数据截至 08-11 09:15
```

`performance` 现在那句的后半段已经是对的方向，只是被前半段的说教盖住了。

#### 折现率提示：真正的问题不是文案

「入表金额取决于它」之所以存在，是因为**这个字段根本没有默认值**，每次测算都要手填。换句文案解决不了这个。应该做的是给它一个来源明确的默认值：

```
折现率 *
[ 4.85% ]  集团 IBR · 5 年期 · 2026-07 版    [覆盖]
```

有了默认值和来源标注，提示文字自然不需要了。这与《产品发展与 UIUX 优化建议书 v1.5》§2.5 提出的折现率治理（合同利率优先、去掉静默兜底、IBR 分层利率表）是同一件事在前端的落点。

### 9.3 一条可执行的文案判据

建议写入团队的文案规范，作为 code review 的检查项：

> **界面文案只允许回答两个问题：「我该做什么」和「我看的是什么数」。**
> **不允许回答「你为什么该在乎」。**

推论三条：

1. **字段提示（`extra` / `help` / placeholder）只写口径、单位、取值来源、以及填与不填的后果。** 不写这个字段有多重要——用户既然看到了这个字段，重要性已经由它的存在证明了。
2. **页面副标题只写状态**：期间、口径（Working / Official）、数据时点、待处理计数。不写页面的存在理由。
3. **禁用两个句式**：「不是 X，而是 Y」的对偶立论；「A → B → C → D」的工作流概括。二者都是把 PRD 语言泄漏到界面上的标志。

配套加一条 lint 或 review checklist：新增的 `Text type="secondary"` 页面副标题，必须包含至少一个动态值（计数、期间、时间戳）——纯静态的一句话副标题基本都是立论。

### 9.4 与其他章节的关系

本章的两个症状和 §4.1「四套并存的样式来源」是同一个成因的不同切面：**表现层是被一次性生成的，业务层是被一点点做出来的。**

一个佐证是注释质量的分布梯度——越靠近财务领域，代码越像人写的；越靠近设计体系，越像生成的：

- `format.ts` 的 `fmtMoney`：「一份用 USD 计量的租约渲染成 ¥10,000.00 不是格式瑕疵，它陈述了一个与账簿不同的金额」
- `LanguageContext.tsx`：「提供一个渲染半翻译界面的语言，比不提供更损信誉」
- `monthly-closing/page.tsx` 的 `ENTRY_TYPE_OPTIONS`：「其他值会筛出一个看起来像数据的空页面」

这三处都是真正懂业务的人在做判断，是本项目最有价值的部分。而 `tokens.ts` 开头那篇"在无彩色系统里，层级通过五种手段建立"的小论文，正确、漂亮，且和下面 903 处内联硬编码没有任何关系。

**所以准确的说法不是"这个项目有 AI slop"，而是：业务层是资产，表现层是待兑现的意图。**
