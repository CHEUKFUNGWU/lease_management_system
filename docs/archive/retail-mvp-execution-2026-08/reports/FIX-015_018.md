## 2. FIX-015 空态输入框位置

评审原话两条：「输入框太低了」→ 改完后「上移得太夸张了吧」。

**两个成因**：一是输入框贴视口底边没有留白，二是空态下 `.home-chat-body`
的 `flex: 1` 把整列吃满，输入框被顶到快捷提问下方约 800px 处。

**最终形态**：列高 `calc(100dvh - 124px)` → `148px`（窄屏 108 → 132），
输入框底部与视口保留 24px；列保持满高、输入框守住底部，只让空态的快捷提问
在剩余空间垂直居中。

**中间走过的弯路要记一笔**：先试过空态整列 `height: auto`，实测矫枉过正——
输入框浮到视口三分之一处，下方空出更大一片。**不要再往这个方向改回去。**

FIX-007 原验收口径「composer bottom 落在视口边缘」随本票修订为「clears the
viewport edge」，注释已写明原因。

`chatLayout.test.ts` 的结构断言原先匹配 `className="home-chat-body"` 字面量，
body 的 className 变成条件表达式后改为匹配类名本身，结构契约不变。

**顺带修的一处隐患**：`.home-chat-body.is-empty` 若写在基础规则之前，
`ruleBody()` 的正则会先命中它，导致「body 必须 `overflow-y: auto`」的契约
假性失败。CSS 规则顺序会影响该文件里所有对同一选择器的断言，新增修饰规则
一律放在基础规则之后。

## 8. 待办与已确认方向

### 8.1 桑基图（利润表流向）——方向已确认，未开工

评审参考 Intel 利润表桑基图，要求最终能精细到品类。**分期已确认**：

| 期 | 营收侧 | 费用侧 | 能回答 | 阻塞点 |
|---|---|---|---|---|
| 一期 | 不分品类 | 按 labor / rent / non_lease / other 分流 | 钱花在哪、门店贡献怎么来 | 只差后端投影接口 |
| 二期 | **按大类分流** | 保持店级合计 | 男装还是女装卖得多、鞋还是包毛利高 | 新事实表 + 大类映射 |
| 三期 | 按大类 | 显式分摊规则 | 哪个品类真正赚钱 | 见下方警告 |

**一期今天就能做**。`retail_store_day_facts` 表里 `revenue`、`gross_profit`、
`labor_cost`、`fixed_rent`、`variable_rent`、`non_lease_cost`、
`other_controllable_cost` **全部是 `DECIMAL(18,2)` 金额**，只是 API 对外
投影成了 `labor_cost_rate` 这类比率。不需要新采集数据，也不存在前端用比率
乘回金额导致轧不平的问题。recharts 3.8 自带 `Sankey`，无新依赖。

建议契约：

```
GET /api/v1/retail/stores/{id}/pl-flow
{ nodes: [{ key, label }],
  links: [{ from, to, value }],
  currency, basis, residual, status, formula_version }
```

**二期是数据模型问题不是图表问题**。`retail_store_day_facts` 的唯一键是
`(store_id, business_date, version, source_system)`，**整表没有任何品类或
SKU 列**。需要新增 `store × date × category` 事实表加一整条导入链路；给现表
加维度会破坏唯一键并打乱所有现有 KPI 口径，不可取。前置依赖是**目标客户的
POS 能否按品类出数**。

大类映射（客户在设置页维护「我的大类」并匹配源系统品类码）应复用现表已有的
`mapping_status IN ('mapped', 'unmapped', 'ambiguous')` 三态语义，不要另发明
一套。**未匹配的销售额必须在桑基图上显示成独立的一条流**——桑基图上左右不平
读者一眼就能看出来，可信度当场归零。

**三期的警告**：营销、活动、人工全是店级记录，没有品类归属。要算「男装利润」
就必须分摊，而按销售额 / 按陈列面积 / 按导购工时三种算法会得出三个完全不同的
答案。分摊是判断，与产品自己写在页面上的「仅供 Working 经营分析，**不作解释性
判断**」直接冲突。真要做，分摊规则必须可配置、图上标注、且能切回不分摊视图。
