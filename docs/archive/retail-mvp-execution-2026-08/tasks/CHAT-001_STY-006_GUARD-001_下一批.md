## 4. CHAT-001 首页简报污染 AI Chat 会话列表（P1）

`web/app/home/briefGate.ts` 的 `runHomeBrief` 调 `aiChatApi.chat` 时**不带 `session_id`**，后端每次新建会话。文件里那个 `cached` 只在同一个 SPA 会话内去重 —— 刷新、开新标签、重新登录都会重新计数。

结果：用户的 AI Chat 侧栏里堆满了同一句「请读取当前经营脉搏并生成…」，把真实对话淹没了。

### 4.1 ⚠️ 这里有一条不能踩的线

**不要简单地「不落库」。** Agent 运行必须可审计（`agent_run_audit_*` 是转型五条底线之一）。正确形态是：

> **保留运行与 trace，但不把它作为用户可见的会话推进侧栏。**

两个可选实现，**选一个并说明理由**：

- **A** 后端给会话加「系统发起」标识，会话列表默认过滤；trace 与审计链路不变。
- **B** 每个用户复用一个固定的「每日简报」会话，简报追加为消息而不是新建会话。

A 更干净，B 改动更小但会让那个会话越滚越长。

### 4.2 验收

```
core-service: go test ./internal/handlers/... ./internal/repository/...
web: npm test -- briefGate
```
断言：连续触发三次首页简报后，用户可见会话数不增加；`agent_run` / 审计记录数**照常增加三条**（这条必须验，否则就是把可追溯性删掉了）。

## 5. STATE-002 判定顺序收口（P1，很小）

`classifyDataState` 当前顺序：

```
scope_denied → actionFor → isRequestFailure → 404/422 empty → failed
```

`actionFor` 排在 `isRequestFailure` **前面**。今天两个调用方都自己校验了 status/code，所以行为正确；但这个接缝**允许**未来的调用方写个无条件的 `actionFor`，把网络失败和 500 呈现成「你去做点什么就好了」的空态 —— 正是 STATE-001 这一整批要消灭的形状。

**要求**：把 `isRequestFailure` 提到 `actionFor` 之前（或只把「后端说没有」的错误喂给 `actionFor`）。两个现有调用方只在 404/422 上动作，不受影响。

**验收**：矩阵测试新增一条 —— 传一个**无条件返回动作**的 `actionFor` + 一个网络失败，结果必须是 `failed`。
