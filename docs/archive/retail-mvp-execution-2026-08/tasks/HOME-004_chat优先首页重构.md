## 0. 为什么返工

HOME-001~003 交付后，用户实际使用的评价是「一点规矩和排版都没有，像块草稿画布」。**这个批评成立，根因在 Planner 一侧**：

之前的指令只规定了行为、角色、状态与组件复用，验收清一色是机械可验的（DOM 断言、类名存在、计数）。指令还明确免除了实施者判断观感——因为他看不到界面。**结果是功能全对、测试全绿、版面没有任何人负责。**

本票因此**逐块规定构图**，并且验收方式改变（见 §6）。

## 1. 目标版式

用户确认的方向（方案 A，三栏）：

```
┌────────┬─────────────────────────────────┬──────────────┐
│ 导航    │ ◈ 今日经营简报（紧凑一条，可展开）    │ 待确认建议    │
│        ├─────────────────────────────────┤ 需要你处理    │
│ 经营分析 │                                 │ 总租赁负债    │
```

**主次翻转**：简报从主体降为顶部一条紧凑上下文带；chat 会话成为中间栏主体；输入框常驻底部。

**首页不放会话列表**（方案 A）。想切历史会话去 `/ai-chat`，该页保持不变。

## 2. 中间栏：简报带

### 2.1 默认收起，一行讲完

收起态一行内给出：数据分类 · 覆盖率 · decision-ready · 关注项数量 · 展开入口。复用 `<DataTrustBar>` 的收起形态，**不要另写一套**。

展开态再给全量口径（dataset / source / as_of / formula / 事实版本区间）。

### 2.2 ⚠️ 不要再把 `answer` 原文倒出来

当前 `BriefView.tsx:110` 是：

```tsx
<Typography.Paragraph className="home-brief-answer">{result?.answer}</Typography.Paragraph>
```

而 `answer` 里含后端 `aiagent/retail_operations.go:661` 用 `fmt.Sprintf` 拼出的机器文本：

```
数据上下文：simulated · dataset=retail-sim-v1-2853d9537f358baf · source=retail_simulator
· as_of=2026-06-05 · window=7天 · formula=retail-kpi-v1 · evidence=complete · confidence=0.90。
经营脉搏：… revenue=current=1801064.11, comparison=1794566.35, change=0.36 (percent); …
```

**这段在 `/ai-chat` 里是合理的**（对话需要可追溯的机器上下文），**但作为首页主内容就是调试输出**，而且它重复了正上方 DataTrustBar 已经排好的同一批字段。

首页简报带**改为消费 `result` 的结构化字段**：

| 内容 | 呈现 |
|---|---|
| 覆盖率 / 分类 / decision-ready / 版本 | `<DataTrustBar>` |
| revenue / gross_margin_rate / store_contribution 等摘要数字 | **KPI 卡**，复用 `/operating-pulse` 已有的卡片语言 |
| 关注门店 | 结构化卡片（见 §2.3） |
| 机器上下文原文 | 收进 `<ThinkingTrace>` 折叠区 |

**不改后端**：`answer` 字符串保持原样（`/ai-chat` 还在用），只是首页不再直接渲染它。

### 2.3 关注门店卡片要有结构

当前是三行裸文本、严重度只有一个小圆点。改为每张卡片有明确的三个位置：

- **门店标识**：`#序号` + 门店编码 + 门店名
- **信号**：指标名与变化量（数值用 `tabular-nums`）
- **严重度**：`<SeverityDot>` + 文字标签（DESIGN.md 原则 3：颜色不是唯一信号）
- 引用角标 `[n]` 保留

## 3. 中间栏：chat 会话

1. 简报带下方是**真实的消息流**，不是一个孤立输入框；
2. **复用 `/ai-chat` 已有的消息渲染**（`MessageContent` / `TypewriterMessage` 一带），包含 ToolChip、引用、置信度、思考轨迹。**不要在首页复制一套**；
3. 输入框常驻中间栏底部；
4. 首次进入且无对话时，消息流区域给**可点击的建议提问**（复用 `/ai-chat` 的快捷提问），不是一片空白。

## 4. 版面规矩（本票的重点，逐条可检查）

| # | 规则 | 具体值 |
|---|---|---|
| L1 | 正文行长 | `max-width: 68ch`，不得让正文铺满整栏 |
| L2 | 纵向节奏 | 间距只用 4px 基数（DESIGN.md §5.1）；**同层级的块之间间距必须一致** |
| L3 | 层级 | 简报带标题 / 卡片标题 / 正文 / 元数据 四级分明，用尺寸与字距拉开，**字重仍只有 400/500/600** |
| L4 | 置信度徽标 | 不独占整行，与工具 chip 同排 |
| L5 | 信任条 | 分组呈现，不是一串用空格连起来的纯文本 |
| L6 | 数值 | 一律 `tabular-nums`；金额走统一 formatter |
| L7 | 右栏空态 | 「待确认建议」为空时不占大片高度，收缩为一行 |
| L8 | 三栏比例 | 中间栏在 1440 下不小于 640px；1280 下右栏不被挤压到不可用 |

**不得新增内联样式、`!important`、`fontWeight > 600`、硬编码中文**——`enforce-design` 会拦。

## 5. 保持不变

1. **角色感知**：`editor` / `reviewer` / `approver` 仍渲染 `WorkQueueFocus`，不是简报也不是 chat；
2. **右栏内容一项不少**：待确认建议、需要你处理六项、总租赁负债、本月租赁费用、月结就绪度；
3. **`/ai-chat` 独立页不动**，路由与入口保留；
4. 三态（无数据 / 非 decision-ready / `scope_denied`）保持，`scope_denied` 不得软化；
5. 提议仍沉淀到右栏 `<ApprovalCard>`，确认前零写入；
6. `< 768` 仍退化为单栏 + 待办 Drawer。

## 6. ⚠️ 验收方式变了

命令级验收照旧（type-check / build / test / `enforce-design` / 角色矩阵 / 三态），但**它们不再是通过条件的全部**。

**本票必须先经用户视觉确认，才能合并。**

因此交付时请提供：

1. **结构变更清单**（沿用上一批格式：组件落位、新增/删除的 CSS 类与 token、断点行为、每种角色的分支）；
2. **§4 版面规矩逐条自查表**：每条写明落在哪个类/哪个值上（例：L1 → `.home-chat-body { max-width: 68ch }`）；
3. 明确写出**你无法确认的部分**（观感、疏密、对齐）——那些由用户看。

Reviewer 会据此推导视觉影响并整理成检查表交用户；**用户点头前不合并**。

**特别提醒**：本票是为了解决「像草稿画布」，**不要只做主次翻转而不动版面**——§4 那八条是这张票存在的理由。
