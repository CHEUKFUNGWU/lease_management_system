## 1. 用户、唯一任务与边界

目标用户是完成集团晨检后，需要调查单家门店的零售经营负责人。页面唯一任务是：在同一数据口径下判断“异常发生在哪些指标、相对同群处于什么位置、哪些可计算因素与变化同时发生、证据是否足够”，为后续情景分析做准备。

### 用户能看到什么

- 新增 `/store-360`：门店身份、数据可信条、current/comparison KPI、门店与同群趋势、同群分位、三组变化桥和可展开证据；
- 从 `/operating-pulse` 的 attention 行进入门店 360，并可按原筛选返回经营脉搏；
- 页面始终标明 Working、production/simulated、dataset、来源、coverage、公式/诊断版本、币种和 fact version；
- “变化贡献/观察信号”明确不是因果结论或根因。

### 用户能完成什么经营任务

- 选择一间授权门店和 7/14/28 天窗口，比较本期与前一等长期间；
- 判断该店销售、毛利、客流、转化、客单、人工、占用成本和门店贡献的变化；
- 与同品牌+同区域+同币种门店的中位数和分位区间比较；
- 查看销售、毛利、门店贡献的确定性变化桥，知道哪些算术因素与变化同向，但不把相关或分解写成根因；
- 展开 coverage、缺失字段、来源、数据集、事实版本和公式证据，决定是否足以进入 MAX-007 情景分析。

### 明确不做

- 不做 AI 解释、自动根因、外部天气/商圈/竞品归因；
- 不做预测、促销/排班/租金情景、行动草稿或审批；
- 不写任何经营事实、合同、事件、IFRS 16、月结、Official 或审计增强；
- 不删除或替换 MAX-005 的同页单店脉搏；门店 360 是新增的更深入口。

## 4. 最小后端 API

新增只读、受 `reports:read`、JWT、TenantMiddleware 和现有 region/brand/store data scope 保护的 API。不得新增 migration。

### 4.1 授权门店选项

```text
GET /api/v1/retail/store-options
  ?data_classification=production|simulated
  &dataset_version=...        # simulated 必填；production 禁止
```

稳定信封至少包含：

- `basis=Working`、classification、dataset version；
- 当前授权且 active、与 classification/dataset 匹配的 `store_id/code/name/brand/region`；
- 按 `store_code, store_id` 稳定排序；
- 空列表返回 200，不返回其他法人或越权 region/brand/store；
- 只读 store population，不要求事实存在，不返回金额。

若可安全复用 `RetailKPIRepository` 的 population 查询，应复用；禁止另写一套遗漏 scope 的 SQL。

### 4.2 门店诊断

```text
GET /api/v1/retail/stores/:store_id/diagnostics
  ?data_classification=production|simulated
  &dataset_version=...
  &as_of=YYYY-MM-DD
  &window_days=7|14|28
  &source_system=...           # 可选
```

版本：`retail-store-diagnostics-v1`。稳定响应至少包含：

1. `basis=Working`、diagnostics/formula/pulse version、classification、dataset、generated_at；
2. store code/name/brand/region；current 与 comparison 等长、不重叠日期；
3. target current/comparison coverage、decision_ready、currency/currency_status；
4. 与 MAX-003 同定义的 KPI summary，不复制或改写公式；
5. target daily trend，以及固定同群每日中位数和当日有效 peer count；target gap 仅使 target 值为 null，peer 仍独立计算，任何缺失不补 0；
6. peer benchmark；
7. 三组 deterministic bridge；
8. observations 和 evidence/provenance；
9. source systems、dataset versions、fact version min/max、highest_as_of、data quality issues 和现有 KPI drilldown URL。

### 4.3 单次读取约束

- Service 只对 current+comparison 合并范围调用一次 `RetailKPIRepository.QueryFacts`，一次读取全部授权 population/facts；禁止对每家 peer 或每日循环查库；
- 在内存中验证目标门店属于 `ExpectedStores`；不存在或越权统一返回 404，不泄露是否属于其他法人；
- 必须复用 `retailkpi.AggregateFacts` 及其 KPI/null/coverage 语义；如需共享 MAX-004 的 summary/trend helper，只做无行为变化的纯函数提取，并回归 MAX-004/MAX-005；
- 不在 Handler 或前端重算 KPI、peer 或 bridge。

## 5. 同群定义与统计合同

MVP peer 固定为：目标门店之外、同 `brand + region + currency`、当前请求范围内授权、current period `decision_ready=true` 的门店。

- 不跨法人、授权范围、brand、region、currency、classification 或 dataset；
- 目标店必须排除；
- `minimum_peer_count=3`。不足时 `status=insufficient_peers`，benchmark 值为 null 并说明原因；禁止静默扩到全集团；
- 使用 current window 聚合 KPI；每项返回 target、peer_count、median、p25、p75、percentile、target_minus_median、unit、status/reason；
- percentile/quantile 算法必须在代码和报告固定并测试；相同输入排序确定；
- 不把 percentile 自动翻译成“好/坏”。成本率较高、收入较高只描述相对位置；
- peer 日趋势使用同一固定 peer 集合；每天仅用当天非 gap、该 KPI complete 的 peers 计算中位数，并返回有效样本数。

固定 benchmark KPI：

```text
revenue, gross_profit, gross_margin_rate, footfall,
conversion_rate, average_transaction_value,
labor_cost_rate, occupancy_cash_cost_rate,
store_contribution, store_contribution_margin, sales_per_sqm
```

## 6. 三组确定性变化桥

所有 bridge 都是算术分解，不是因果模型。每组返回 `status`、method/version、current、comparison、total_change、items、rounding_residual、reason；items 按固定业务顺序返回，前端不得重排或重算。

### 6.1 销售额变化桥 `revenue_shapley_v1`

恒等关系：

```text
revenue = footfall × conversion_rate(decimal) × average_transaction_value
```

- 对 footfall、conversion、ATV 的全部 3! 替换顺序求平均边际贡献（Shapley），消除顺序偏差；
- 三项贡献 + rounding residual 必须等于 current revenue - comparison revenue（容差 0.01）；
- 任一所需值 unavailable/partial 或零分母导致恒等式不可验证时，整组 unavailable，并返回明确 reason；不得用 0 代替。

### 6.2 毛利额变化桥 `gross_profit_shapley_v1`

恒等关系：

```text
gross_profit = revenue × gross_margin_rate(decimal)
```

- 对 revenue 与 gross margin 的 2! 顺序求平均贡献；
- 两项 + residual 等于 gross profit change（容差 0.01）；
- 缺失/零分母语义同上。

### 6.3 门店贡献变化桥 `store_contribution_additive_v1`

恒等关系：

```text
store_contribution = gross_profit
                   - labor_cost
                   - occupancy_cash_cost
                   - other_controllable_cost
```

- 固定返回毛利、人工成本、经营占用现金成本、其他可控成本四项；成本 contribution 的符号必须反映对门店贡献的影响；
- 四项 + residual 等于 contribution change（容差 0.01）；
- occupancy 仅用 fixed rent + variable rent + non-lease cost，不得引入 IFRS 16 折旧/利息/ROU/负债。

## 7. Observations 与证据链

- observations 只从 API 已计算的 current/comparison/peer/bridge 生成模板化事实陈述，不使用 LLM；
- 固定排序：数据不足警示优先，其后按绝对变化贡献/与 peer median 差异降序，再按 code；
- 示例：“销售额较对比期下降 8.2%；算术分解中客流变化贡献 -¥X。该结果仅是观察信号，不作解释性判断。”；
- 每条包含 code、label、statement、metric/bridge reference、status、evidence IDs；
- evidence 至少含 current/comparison 日期、observed/expected store-days、所需字段、公式版本、source_systems、dataset、fact versions、highest_as_of、data quality/mapping issue、KPI drilldown URL；
- decision_ready=false 时页面顶部和相关 bridge/peer 都必须降级，不得生成肯定性文案。

## 9. 错误与空状态
