# 票一：MONEY-004 —— 把披露报表包也迁到精确金额

## 1.1 为什么这张是 P1

上一批把 `ifrs16` + `monthend` 迁到了 `money.Amount`，但**精确性止于该边界**：`reporting` 通过 `.Float64()` 把值转回浮点，所以**披露报表包的数字仍然是 float64 派生的**。

披露报表是**审计师直接看的东西**。「审计链已迁移」目前只覆盖计量与分录，不覆盖披露——这张票补上这一段。

## 1.2 范围

| 文件 | float64 |
|---|---|
| `services/reporting/disclosure_projection.go` | 55 |
| `services/reporting/projection.go` | 26 |
| `services/reporting/amortization_projection.go` | 20 |
| **合计** | **117** |

另有 `projection.go:398` 的 `roundProjection(float64) float64` —— 按 ADR §Decision 4，中间不舍入，只在边界舍入一次，该函数应随迁移消除或改为边界量化。

**其余包一律不动**（fpna / retailkpi / cashflow / dealcompare / predeal / renewaldecision 等），由 `enforce-money` 守卫防止恶化。

## 1.3 必须实现

1. 上述三个文件的金额字段改用 `money.Amount`；
2. **消除 `.Float64()` 往返**：从 `ifrs16` 取值后不再转回浮点再算，全程保持精确；
3. `roundProjection` 按 ADR 处理；
4. **披露口径的四舍五入必须与计量一致**（`money.Round(currency)`），不得另起一套。

## 1.4 验收（注意 D3 —— 上一批的教训）

| # | 检查 | 期望 |
|---|---|---|
| D1 | 三个文件的 float64 金额字段 | 0（非金额如比例、期数保留） |
| D2 | `.Float64()` 在 reporting 中的残留 | 仅剩必要的对外边界，逐处说明理由 |
| D3 | **披露报表 JSON 与迁移前语义等价** | **量化到币种精度后零差异**。⚠️ **不要求逐字节一致** —— 浮点噪音消除本来就会改变字节，上一批已因此更正过标准（见 Review §6）。请贴「量化后差异数 = 0」与「原始字节差异条数及其形态样本」两组数据 |
| D4 | 148 条回归断言（容差 0） | 全部通过 |
| D5 | 其余包 float64 计数 | 与迁移前一致（贴逐包对照） |
| D6 | 全量 `go test -count=2` + vet + 真实 PostgreSQL | 通过 |
| D7 | `enforce-money` 守卫 | 无新增违规 |

# 票二：FIX-001 —— 两个 AI 可解释性缺口

## 2.1 背景

上一批 AI-001 建了 `<ToolChip>` 与 `<ConfidenceBadge>`，但后端有两处缺口使它们无法完整工作。

## 2.2 必须实现

### A. Tool 调用耗时

`<ToolChip>` 已预留耗时展示（缺失时不渲染、不编造，做法正确），但 `AgentToolCall` **没有耗时字段**——审计记录里有时长，Tool 调用协议里没有。

补上耗时字段并在 Run 响应中透出，让 `<ToolChip>` 能显示。

**沿用既有语义**：耗时缺失时保持缺失，不要用 0 填充（AGENTS.md「不用 0 填补缺失」）。

### B. 会话历史丢失置信度

`ai-chat` 消息的 `confidence` 目前**只存在于内存**，未持久化到会话历史（`repository/ai_chat_runtime.go` 中 0 处引用）。刷新页面或重新加载会话后，`<ConfidenceBadge>` 就没数据了。

持久化 `confidence` 与其降级原因，使重载会话后仍可显示。

## 2.3 明确不做

1. 不改 `<ToolChip>` / `<ConfidenceBadge>` 组件本身（它们已就绪）；
2. 不改 Agent 的置信度计算逻辑；
3. 不扩大到其他 Run 事件字段。

## 2.4 验收

| # | 检查 | 期望 |
|---|---|---|
| F1 | Tool 耗时贯通 | 后端产出 → Run 响应 → 前端可读，端到端测试 |
| F2 | 耗时缺失时 | 仍然缺失，**不是 0** |
| F3 | confidence 持久化 | 重载会话后仍可读到，含降级原因 |
| F4 | 既有会话（无该字段） | 正常加载，不报错 |
| F5 | 全量 Go + Web 验证 | 通过 |

# 票三：I18N-002 —— 清理死 i18n key

## 3.1 ⚠️ 这张票有一个会静默炸的坑，先读完再动手

朴素 grep 得到「1717 个 key 中 334 个无引用」。**这个数字不可信。**

代码里存在**动态构造的 key**，例如：

```tsx
// contracts/page.tsx:524
options={Object.entries(LEASE_SCOPE_KEYS).map(([value, key]) => ({ label: t(key, language) }))}
// store-360/logic.ts:68
const label = key ? t(key, language) : status;
```

这类 key 从常量表取值，**grep 找不到它们的字面量**，会被误判为死 key。

而 `t()` 对未知 key **返回空字符串，不报错**——删错一个 key，生产环境就是一块空白文案，没有任何错误提示。

## 3.2 必须实现（顺序是硬的）

**第一步：先让失败变响亮，再删任何东西。**

1. 让 `t()` 在开发/测试环境下遇到未知 key 时**明确失败**（抛错或测试断言），生产环境保持现有降级行为不变；
2. 补一个测试，遍历所有**常量表**（`LEASE_SCOPE_KEYS`、`ASSET_TYPE_KEYS` 及同类）里的 key，断言它们都存在于字典中。

**第二步：在保护网下清理。**

3. 重新统计死 key —— 必须把常量表引用计入，不能只数字面量；
4. 删除确认无引用的 key（三种语言一并删）；
5. 全量测试与构建通过，且**新增的未知 key 检测不报错**。

## 3.3 明确不做

1. 不改任何在用文案的内容；
2. 不改 `SUPPORTED_LANGUAGES`；
3. **拿不准的 key 就留着** —— 少删几个无害，删错一个是生产空白文案。

## 3.4 验收

| # | 检查 | 期望 |
|---|---|---|
| K1 | 未知 key 在测试环境会失败 | 故意 `t("no.such.key")` → **测试失败**。贴输出 |
| K2 | 常量表 key 全部存在 | 测试断言通过 |
| K3 | 删除数量与依据 | 报告列出删除数量、如何确认无引用（含常量表处理方式） |
| K4 | 三语一并删除 | 无残留半边 key |
| K5 | 全套 web 验证 + `enforce-design` | 通过 |

**K1 必须先于删除完成。** 报告里请体现这个顺序。
