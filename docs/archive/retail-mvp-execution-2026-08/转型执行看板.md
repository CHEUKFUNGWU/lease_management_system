> 现行入口：`docs/AI_文档索引与现行决策.md`

> Planner / Reviewer：Codex 主任务  
> Executor：Max  
> 工作方式：一次只派发一个可独立验收的任务；Max 提交代码、测试和交付报告后，由 Reviewer 独立检查并决定通过、返工或进入下一票。

## 状态定义

- `READY`：指令和验收标准已冻结，可执行；
- `IN_PROGRESS`：Max 正在执行；
- `IN_REVIEW`：Max 已交付，等待 Reviewer 检查；
- `CHANGES_REQUESTED`：未满足验收标准，必须按评审意见返工；
- `ACCEPTED`：证据充分且验收通过；
- `BLOCKED`：存在无法由 Executor 自行解决的外部阻塞。

## 执行规则

1. Max 不自行扩大任务范围，也不顺手重构无关模块。
2. Max 不修改用户已有的未跟踪文件，除当前任务明确列出的文件。
3. 所有数据库变更必须同时提供增量迁移和 `db/init/01_init.sql` 空库初始化版本。
4. 所有写入必须保持多租户范围、权限、基础幂等、来源追溯和版本控制；审计在 MVP 只保留最小操作留痕。
5. 模拟数据或模拟事实必须在数据库、API、导出和 UI 中保持明确标识，不能进入 Official 过账链路。
6. Max 不提交、不推送；Reviewer 验收后再决定版本控制动作。
7. 每票必须生成 `docs/execution/reports/<TASK-ID>.md`，记录交付物、测试命令、结果、风险和未完成项。
8. 每张任务票必须写明“用户能看到什么”和“用户能完成什么经营任务”；缺少这两项不得进入 `READY`。
9. 资源分配按 70% 用户可见功能、20% 数据与测试、10% 安全审计执行。纯治理任务除非阻断数据正确性或租户隔离，不得进入当前关键路径。
10. 不得降低五条底线：跨法人隔离、模拟/正式数据区分、来源追溯、重复导入保护、IFRS 16 正式台账隔离。
11. 产品转型采用增量叠加：不得删除、重命名、隐藏、替换或破坏任何既有功能、页面、导航入口、API、合同管理、IFRS 16、月结、报表或既有 Agent 能力。
12. 未在任务票明确授权时不得修改既有 UI。专项 UI 票可以新增经营分析页面、重排导航顺序和提高入口优先级，但必须沿用整体 AppLayout、视觉体系、栅格排版和交互范式；全部原页面、路由和功能继续可访问，并提供兼容回归证据。
