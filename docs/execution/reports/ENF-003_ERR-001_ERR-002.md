## A. ENF-003 — 守卫判定改计数法

**放宽/收紧说明（§5 常设要求）**：判定从「有/无」改为「多少」——`count(newLine) > count(oldLine)` 即违规。内联样式按**静态属性个数**比（逐对计数，动态值豁免），不是 `style={{` 出现次数。这是**收紧**：往存量违规行加码不再放行；触碰存量行而不加码（N3）仍放行，不误报。

### scope_denied 端到端（R4）

**NULL/越权判断依据**：仓储 `resolveRetailStoreDayFactStore` 用调用方 EntityFilter 查门店，无行即返回**类型化 `scope_denied`**。依据：(1) AGENTS.md 明令 `scope_denied` 不得被软化为「无数据」——原自由文本「not found in tenant scope」正是软化表述，且掩盖权限问题；(2) Agent seam 既有先例 `retailErrorCode` 把 store 不可见一律映射 `ErrorScopeDenied`，HTTP 写路径与之一致；(3) store_id 是 UUID，不存在可枚举的枚举面。读路径（诊断/情景 404）保持 `not_found` 不动——读路径无法在不做存在性二次查询的前提下区分「门店不存在」与「在其他法人」，这是 §8 所述既有降级，**本票不扩大修复，仅记录**。

- **附带发现（未动，仅记录）**：
  1. 读路径（诊断/情景）对越权门店仍回 `not_found` 404——无法在不做存在性二次查询（会泄漏跨法人存在性）的前提下区分，保持现状（§8 允许记录）；
  2. `retail_scenarios.go` 的 `DataUnavailableError` 从未被构造，`reason` 分支实际不可达（已顺带修掉 nil 解引用，见 B 节）；
  3. 转换后 422 默认分支会出现「`system_failure` code + 422 状态」的组合（如模拟数据生成的非幂等失败）——code 与状态码是两个维度，状态码语义按票面不动，后续若收敛状态码语义应单独开票；
  4. `c.Error` 挂载的服务端日志在 Gin 默认 handler 下会进响应体日志，生产中间件若配置了 Recovery/Logger 需确认不把 error 链回写客户端（现状无此配置，记录）。
