## 0. 理解确认

- **为什么不能简单地「法人为空就拒绝」**：管理员是合法跨法人角色，`users.legal_entity_id` 为空是管理员的正规形态（seed 中 admin 角色持 `*:*` 权限 → `scope.Global`）。无差别拒绝会锁死管理员。
- **「非 Global 且无法人」为什么是配置错误而非合法状态**：CONTEXT.md 的 Legal Entity Access 定义——非管理员可访问的最大范围由分配给该用户的法人决定。无法人即无可访问范围，却因 38 处 `($N='' OR …)` 谓词短路获得**全部法人**的读权限，与领域语义矛盾，只可能是建用户时漏填。
- **本票为什么不改那 38 处查询**：`cmd/api/main.go:164-171` 是唯一收口点，所有认证路由都经过这条中间件链。在此加一道判定比改 38 处查询更彻底（不可能漏挂）、改动更小、更易验证；改查询是后续「LegalEntityID 值类型」任务的根治手段（把漏过滤变成编译错误）。

## 2. 关键决策

- **守卫是新写的还是改造 RequireTenant()**：**改造既有 `RequireTenant()` 并复用其名字**。理由：diff 最小；ticket §4.1 明确允许复用；grep 证据直接呈现「死代码被启用」而非新增一个函数后再删旧函数。旧语义（任何空法人即 403）本身会锁死管理员，属于必须纠正的语义错误。
- **中间件顺序确认结果**：`access_scope` 在守卫执行时可取到。链序为 `JWTAuth → LoadUserPermissions → DataScopeMiddleware → TenantMiddleware → RequireTenant`；`DataScopeMiddleware` 用 JWT 声明中的 `legal_entity_id` + 权限 + data_scopes 构建 `access.Scope` 并 `c.Set("access_scope", …)`，在 `RequireTenant` 之前执行。守卫读到缺失 scope 时同样 403（失败关闭）。链级测试（`buildTenantGuardRouter`）用真实五段链复现了该顺序。
- **「是否管理员」的判定复用了哪段既有逻辑**：复用 `requestedRoles(req)` 产出的去重角色列表，配合新增的 `hasRole(roles, "admin")`（放在 `isAssignableRole` 旁）。判定依据与守卫一致：admin 角色在 seed 中持有 `('*','*')` 权限 → `scope.Global`，所以「roles 含 admin ⇔ Global」。没有新造角色字符串比较逻辑。
- **无「更新用户」接口**：`cmd/api/main.go` 中 `/admin/users` 仅有 GET（列表）与 POST（创建），仓库无 `UpdateUser` handler，ticket §4.2 第三句不适用。
