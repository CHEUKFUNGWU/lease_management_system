## 1. 背景与已核实事实

### 1.1 现状

| 层 | 事实 |
|---|---|
| 数据库 | `DECIMAL(18,2)` **76 列**、`DECIMAL(18,4)` **5 列**、`DECIMAL(18,8)` **1 列** —— **存储是精确的** |
| Go | 金额一律 `float64`，**全仓 0 个 decimal 库** |
| 逐步舍入 | `round2` **重复定义 10 处、调用 137 次** |
| 逐期递推 | `services/ifrs16/calculation.go:222` `liability = entry.ClosingLiability` —— 摊销表逐期携带余额，36+ 期 |
| 回归比对 | `testdata/ifrs16_regression_cases.json` 顶层 **`"tolerance": 1`**，全局唯一值，148 条断言全部适用 |

问题集中在一个边界：**存储精确，一读进 Go 就掉进二进制浮点，算完再写回去。**

### 1.2 业界共识（外部检索，2026-08-14）

- **金额路径上不应出现 float64**；主流是**整数最小单位**（`int64` 存分）或 **decimal 类型**，数据库用 `NUMERIC`/`DECIMAL`；
- **「每步四舍五入到分」不但救不了浮点，还会引入双重舍入偏差**——正确做法相反：中间步骤保留更高精度，**只在最终边界舍入一次**；
- **对账应当精确相等；「需要容差带」本身就是表示法错了的信号**；
- 舍入模式必须显式选定（IEEE-754 有五种），会计场景通常要 half-up 或银行家舍入，且**正负数行为可能不同**——退款、红冲、贷项直接受影响；
- 币种小数位不同（JPY 0 位、USD 2 位、KWD 3 位），**不要硬编码「分」**。

### 1.3 ⚠️ 一个必须先讲清的区分（否则本批会得出错误结论）

**当前的 `tolerance: 1` 不是 float64 造成的。**

在 ¥3,255,676 量级上做约 40 次浮点运算，误差量级约为 `1e-9`；而容差是 `1`，**大了约九个数量级**。也就是说容差存在是**另一个原因**（最可能是 Golden 标准答案由人工/Excel 计算并取整，容差是留给参考值的，不是留给代码的）。

**因此：**

- ❌ **不要在报告里写「迁移到 decimal 后可以把容差降到 0」**——这不成立，也不是本批的成功标准；
- ✅ 正确表述是：**这是两个独立问题**——(a) 表示法（本批处理）、(b) Golden 参考值精度（本批只需查清成因并写进 ADR，不修）。

这一条会作为验收项检查。**把两件事混为一谈，本票退回。**

# 票一：ADR-0020 —— 金额表示法决策

## 2.1 交付物

`docs/adr/0020-money-representation.md`，沿用既有 ADR 格式（Context / Decision / Consequences 或该目录现行结构）。

## 2.2 ADR 必须回答的问题

| # | 问题 | 说明 |
|---|---|---|
| Q1 | **选哪种表示法** | 整数最小单位 vs decimal 类型。**必须结合我们的实际约束论证**，不能照抄通用建议 |
| Q2 | **选哪个库**（若选 decimal） | 给出评估维度与结论 |
| Q3 | **舍入模式** | 显式指定（half-up / 银行家舍入），并说明**负数行为**（红冲、贷项） |
| Q4 | **在哪里舍入** | 「只在边界舍入一次」的边界具体是哪些（写入数据库？生成分录？API 响应？） |
| Q5 | **中间精度** | 保留多少位（guard digits） |
| Q6 | **多币种小数位** | 如何处理 JPY(0) / USD(2) / KWD(3)，我们当前实际用到哪些币种 |
| Q7 | **JSON 线上格式** | 见 §2.4，这是最容易炸的地方 |
| Q8 | **`tolerance: 1` 的真实成因** | 查清并记录（**不修**）。若确为 Golden 参考值所致，写明后续如何收敛 |
| Q9 | **迁移范围与顺序** | 哪条链先迁、其余何时迁、期间如何共存 |
| Q10 | **不迁移的部分如何防止恶化** | 见 MONEY-001 的守卫 |

## 2.3 Q1 的关键约束（不要照搬通用建议）

通用建议偏向**整数最小单位**，但我们有三个约束需要纳入论证：

1. **数据库已经是 `DECIMAL`**——decimal 类型与之 1:1 映射，**无需 schema 变更**；改整数分则需要重新定义每列语义；
2. **存在 `DECIMAL(18,4)` 与 `(18,8)` 列**（汇率、指数类），**次于「分」的精度是真实需求**，整数分表示不了；
3. **多币种**，小数位不同，「分」不是一个统一概念。

**这三条不是让你必须选 decimal**，而是**必须在 ADR 里正面回应**。若结论仍是整数最小单位，要说明上述三点怎么解决。

## 2.4 Q7：JSON 兼容性是最容易炸的地方

前端金额字段目前**全部是 TS `number`**（如 `current: number | null`），formatter 签名也是 `value: number | null | undefined`。

**多数 decimal 库默认序列化为 JSON 字符串**（`"123.45"`）。若直接切换，**前端会静默坏掉**——类型对不上、`toLocaleString` 行为异常。

ADR 必须明确：**线上格式保持 JSON number**，并说明如何实现（自定义 `MarshalJSON`、或库提供的无引号选项）。

**若 ADR 结论是改成字符串**，必须同时说明前端改造范围与迁移方式——但**本批不做前端改造**，那样的话 MONEY-002 的范围要相应调整并回来找 Planner 确认。

## 2.5 验收

| # | 检查 | 期望 |
|---|---|---|
| E1 | Q1–Q10 全部有明确结论 | 不接受「视情况而定」 |
| E2 | Q1 正面回应了 §2.3 三条约束 | ✅ |
| E3 | Q8 区分了表示法问题与参考值问题 | **未混为一谈** |
| E4 | 影响面量化 | 51 个 float64 金额字段、137 处 `round2` 的分布与迁移批次划分 |
| E5 | ADR 编号与格式 | `0020`，与既有 ADR 一致 |

**ADR 提交后停下来等 Reviewer 确认，不要直接开始 MONEY-001。**

# 票二：MONEY-001 —— 金额接缝

> **前置：ADR-0020 已被 Reviewer 确认。**

## 3.1 必须实现

按 ADR 结论建立 `core-service/internal/money`（或 ADR 指定位置）：

1. **金额类型**，封装 ADR 选定的底层表示；
2. **舍入策略**：模式显式、正负行为明确、**舍入点集中在一处**，不散落成第二个 `round2`；
3. **币种小数位感知**（ADR Q6 的结论）；
4. **数据库互操作**：`sql.Scanner` / `driver.Valuer`，与 `DECIMAL(18,2)` / `(18,4)` / `(18,8)` 往返**无精度损失**；
5. **JSON**：按 ADR Q7 结论实现，默认必须与现有线上格式一致；
6. **分摊**：若 ADR 涉及拆分/分摊（税、费用分配），提供**最大余数法**保证各部分之和精确等于总额。

## 3.2 守卫：防止未迁移部分继续恶化

加一条 CI 可执行检查：**新增的金额字段不得是 `float64`**。

判定沿用 `enforce-design` 已验证有效的**计数法 + 行级新增**思路（见 `web/scripts/enforce-design.mjs`），但作用于 Go 侧。字段名匹配可用 `Amount|Balance|Liability|Revenue|Rent|Cost|Interest|Depreciation|Payment|Price|Fee` 一类词表——**词表要写在一处并可扩展**。

## 3.3 明确不做

1. **不迁移任何既有字段**（那是 MONEY-002）；
2. 不改数据库 schema；
3. 不动前端；
4. 不动 `round2` 的既有 137 处调用。

## 3.4 验收

| # | 检查 | 期望 |
|---|---|---|
| M1 | 往返精度 | `DECIMAL(18,2)`/(18,4)/(18,8) 写入→读出**逐位相等**，真实 PostgreSQL 测试 |
| M2 | 舍入模式 | 正数与**负数**各有断言，覆盖 .5 边界 |
| M3 | JSON 格式 | 序列化结果与迁移前**逐字节一致**（贴对照） |
| M4 | 分摊守恒 | 各部分之和 == 总额，含无法整除的情形 |
| M5 | 守卫生效 | 新增一个 `float64` 金额字段 → **失败**；改成金额类型 → 通过。**贴两次输出** |
| M6 | 守卫不误报 | 当前 main 上跑 → 通过 |
| M7 | 全量 Go + vet | 通过 |

# 票三：MONEY-002 —— 迁移审计链

> **前置：MONEY-001 已完成。**

## 4.1 范围严格限定：只迁一条纵向

**不要迁移全部 51 个字段。** 本票只迁**审计面最关键、且存在逐期递推**的一条链：

| 包 | 现状 |
|---|---|
| `services/ifrs16` | float64 出现 **123 次** |
| `services/monthend` | float64 出现 **13 次** |
| `repository` 中这两条链用到的金额字段 | 从 116 次中挑出相关部分 |

选它的理由：**IFRS 16 计量 + 月结分录是产品对外的审计背书链路**，也是唯一逐期携带余额、误差会滚雪球的地方。

其余包（FP&A、零售 KPI、报表等）**本票不动**，由 MONEY-001 的守卫防止恶化，后续分批迁移。

## 4.2 必须实现

1. 上述范围内的金额字段改用金额类型；
2. **消除该范围内的逐步舍入**——按 ADR Q4/Q5 结论，中间保留高精度，只在边界舍入一次；
3. 该范围内的 `round2` 调用清零（其余包保留）；
4. **摊销表逐期递推路径**（`calculation.go:222` 一带）必须有测试证明多期累计无漂移。

## 4.3 关于回归容差：本票不要动它

见 §1.3。`tolerance: 1` 与本次迁移无关。

- **不要把容差改成 0**，也不要声称迁移让容差可以降低；
- **可以做**：新增一组**精确相等**的断言，覆盖迁移范围内的确定性中间量（如逐期负债余额的守恒关系：期初 − 付款 + 利息 = 期末），与既有容差断言**并存**；
- 既有 148 条断言**必须继续全部通过**——这是"迁移没改变业务结果"的证据。

## 4.4 明确不做

1. 其余包的金额字段；
2. 数据库 schema；
3. 前端；
4. 回归容差值；
5. 不删 `round2` 的定义（其余包还在用）。
