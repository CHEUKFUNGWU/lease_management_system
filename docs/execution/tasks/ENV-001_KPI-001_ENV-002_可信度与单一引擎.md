# 票一：ENV-001 —— Source Envelope 模块

## 1.1 问题

`CONTEXT.md` 定义了 **Source Envelope**，但**没有任何模块拥有它**。provenance 目前在 **14 处**手工 rollup，形状五花八门，前端渲染三套。

两个已确认的后果：

1. **`coverage_rate` 在 `retailkpi` 里是 `null`，在 `retailpulse:395` 被强制成 `0`** —— 缺失信号本身被零填充，直接违反 AGENTS.md「不用 0 填补缺失」；
2. 两个页面把 `formula_version` **硬编码成字面量**，v2 一旦发布，界面会在 v2 的数字上显示 "v1"。

## 1.2 必须实现

一个模块产出信封，**所有零售读取原样返回它**，不再各自拼装。信封至少包含（对齐 CONTEXT.md）：

- Data Classification（`production` / `simulated` / 跨越时 `mixed`）
- source systems、dataset version、Fact Version 区间、as-of
- **Fact Coverage**（observed / expected store-days + rate，**rate 缺失时为 `null`，禁止 0**）
- Decision Ready 及其原因
- formula / pulse / semantic 版本（**从服务读取，不得硬编码**）

## 1.3 明确不做

1. 不改任何 KPI 计算（那是 KPI-001）；
2. 不改前端（那是 ENV-002）；
3. 不改 schema。

## 1.4 验收

|---|---|---|
| P1 | `coverage_rate` 无零填充 | `grep` 全仓无「coverage 为 null 时置 0」的写法；单测覆盖 null 路径 |
| P2 | 手工 rollup 收口 | 14 处降到 1 处产出 + N 处消费；报告列出前后对照 |
| P3 | 版本号来源 | `grep -rn '"v1"' web/app` 中不再有 formula/pulse 版本字面量 |
| P4 | 各读取端信封形状一致 | 同一结构体，测试断言 pulse / store360 / scenario / kpis / facts / agent 六处形状相同 |

# 票二：KPI-001 —— 让 `retail-kpi-v1` 成为唯一 KPI 引擎

## 2.1 问题：两个引擎，同名指标，不同答案

| 指标 | `retailkpi`（store-day） | `operating/fourwall`（月度） |
|---|---|---|
| 租售比 | (固定 + 变量) / 营收 | **固定 / 营收 —— 变量被丢掉** |
| 销售 / ㎡ | 营收 / 日均面积 | 营收 / 单月一行 |
| 贡献率 | 零分母 → `null` | **`value / max(revenue, 1)`** |
| Peer Cohort | brand+region+currency，最少 **3** 家 | region+brand，最少 **1** 家 |

**两处是明确的数据正确性缺陷**：

1. **`operating/fourwall.go:79/91/92` 的 `max(f.Revenue, 1)` 给零营收门店凭空造了一个分母**，算出看似正常的比率——这正是零售线建来杜绝的「不用 0 填补缺失」；
2. **Fact Coverage 谓词有 9 处副本，其中 `retailstore360/store360.go:242/252` 用 `!=`**，而 `retailpulse:606` 与 `retailkpi:179` 用 `ExpectedStoreDays > 0 && Observed < Expected`。超额覆盖（observed > expected）在门店 360 会触发降级、别处不会，**Peer Benchmark 被整片抹掉**。

而 CONTEXT.md 明确定义：Peer Cohort「样本低于最小值或跨币种时不产出基准，而不是产出一个弱基准」。`/performance` 目前用 1 家同群就发布一个自信的分位数。

## 2.2 必须实现

1. 把**周期变化率、Peer Cohort 资格、分位数**收进 `retail-kpi-v1` 接口；
2. 消除 `max(revenue, 1)` 这类捏造分母，零分母一律 `null`；
3. Fact Coverage 谓词 9 处副本收敛到 1 处（以 `ExpectedStoreDays > 0 && Observed < Expected` 为准）；
4. **`/performance` 改指向统一引擎**。

## 2.3 增量叠加底线：`/performance` 必须继续可用

这是本批**唯一触及转型前存量界面**的改动。它是**换实现，不是删功能**：

- 路由保留，页面继续可访问；
- 需要提供**兼容性回归证据**：改动前后同一输入的输出对照，差异逐条解释（**预期会有差异**——旧引擎算错了，但每条差异都要说清楚是哪个缺陷导致的）。

## 2.4 明确不做

1. 不删 `operating/fourwall.go`（可以让它转调统一引擎，但不删文件、不删路由）；
2. 不改月度 `store_operating_facts` 表结构；
3. 不动前端页面布局。

## 2.5 验收

| # | 检查 | 期望 |
|---|---|---|
| K1 | `grep -rn 'max(f.Revenue, 1)' core-service/` | **0** |
| K2 | 零营收门店的贡献率 | 返回 `null`，不是捏造值；单测钉住 |
| K3 | Coverage 谓词 | 收敛到 1 处，`store360` 的 `!=` 已消除；测试覆盖 observed > expected |
| K4 | Peer Cohort 最小样本 | 统一为 3，跨币种不产出；`/performance` 路径同样适用 |
| K5 | **`/performance` 兼容性证据** | 改动前后同一输入输出对照，每条差异有归因说明 |
| K6 | 全量 Go + vet + 真实库 `-count=2` | 通过，零残留 |
