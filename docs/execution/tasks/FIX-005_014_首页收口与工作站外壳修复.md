## 3. B 组：卡片之间没有间隙（FIX-009，**全站审计**）

用户实机反馈「卡片和卡片之间能不能保留一点间隙」，并要求**排查整个工作站是否存在同样问题**。

### 3.1 根因（已实测确认）

`RightColumn.tsx:101` 用 `<Spin spinning={loading}>` 包住了四个并列区块（工作队列卡、KPI 卡组、结账就绪度卡、未来关键日期卡）。AntD 的 `Spin` 会插入 `.ant-spin-nested-loading > .ant-spin-container` 两层 div，而**全仓库没有任何一条针对 `.ant-spin-container` 的样式**——父级 `.home-right-stack { gap: 24px }` 因此只作用于它的 3 个直接子节点，Spin 里面的四块完全没有间距。

Reviewer 实测（300px 右栏，逐块 `getBoundingClientRect()`）：

| 相邻区块 | 间距 |
|---|---|
| 工作队列卡 → KPI 卡组 | **0px** |
| KPI 卡组 → 结账就绪度卡 | **0px** |
| 结账就绪度卡 → 未来关键日期卡 | **0px** |
| （对照）队列卡内部的行与行 | 8px |

### 3.2 同款缺陷第二处（已确认）

`home/WorkQueueFocus.tsx:56` 完全同构：父级 `.home-work-focus { gap: 16px }`，`<Spin spinning={loading}>` 包住三个区块 → 同样全部贴合。**这是 editor / reviewer / approver 三个角色的首页**，用户看到的是 admin 视角，这一处还没人报，但一定坏着。

### 3.3 全站审计范围（必须逐个核对并在报告里列表回答）

`<Spin spinning=...>` 的其余调用点，逐个确认「是否包住了多个依赖父级 gap 的兄弟节点」：

- `settings/page.tsx:497`、`:560`、`:705`
- `contracts/[id]/page.tsx:388`
- `todo/page.tsx:379`
- `cashflow-forecast/page.tsx:450`
- `monthly-closing/page.tsx:1028`、`:1080`

报告里给一张表：文件:行号 / 包住几个兄弟 / 父级是否用 gap / 是否受影响。**只包一个卡片的直接标注「不受影响」即可，不用改。**

### 3.4 顺带：卡片语言不统一

同一列里有两套卡片：AntD 卡是 `#FFFFFF` + `1px var(--border-default)` 实边框；手写的 `.home-readiness-card` 是 `#F7F7F7` + 无边框 + `box-shadow: 0 0 0 1px rgba(0,0,0,0.04)`（4% 灰发丝线）。在 `--bg-page: #FFFFFF` 的白底上，后者几乎看不出边界——这也是「感觉糊成一片」的一半原因。

**要求**：手写卡片统一到 AntD 卡的表达（同一 `--bg-surface` 与 `--border-default` 实边框、同一圆角），或反过来统一到发丝线，**全站只留一套**。选哪套写明理由。

**验收**：
```
web: npm test -- RightColumn WorkQueueFocus
web: node web/scripts/enforce-design.mjs
```
断言：`.home-right-stack` 与 `.home-work-focus` 作用域下的 `.ant-spin-container` 存在纵向 gap 规则；报告里贴出修复后四组相邻区块的实测间距（应为父级 gap 值，不是 0）。

## 4. B 组：全局搜索控件（FIX-010）

用户原话「搜索框那里是什么回事，丑」。Reviewer 在真实 `AppLayout` 里实测出两个确定缺陷：

1. **胶囊底色没生效**。`.global-search-trigger` 声明了 `background: var(--bg-inset)`（无 `!important`），但在真实 header 里 `getComputedStyle(btn).backgroundColor` === **`rgba(0, 0, 0, 0)`** —— AntD 运行时注入的 `.ant-btn` 系列样式在同等 specificity 下后插入，赢了级联。结果搜索控件退化成一段裸文字。（把 `GlobalSearch` 单独挂在裸页面上测时背景是好的 —— 所以**必须在 `AppLayout` 里验，不要单测组件**。）
2. **`⌘K` 角标被撑成一条竖线**。按钮高 34px，但内部子元素继承了 header 的行高：`.ant-btn-icon` 实测高 **60px**、`kbd` 实测高 **64px**、宽仅 24px —— 一个 24×64 的带边框细高盒子，就是用户截图里 `搜索 ⌘K` 右边那条「竖线」。

**要求**：两条都修。底色要在 `AppLayout` 真实环境里生效（提升 specificity 或走 AntD token 配置，**不要再加 `!important`**——那正是 UIUX 方案阶段一要拆的东西，加一条就多一条债）；`kbd` 与 icon 高度收回按钮内（`line-height: 1` + 显式高度）。

**验收**：在 `AppLayout` 内渲染的测试中断言 `.global-search-trigger` 的背景 token 生效、`kbd` 高度 ≤ 20px。报告贴出修复前后 `getComputedStyle` 的 `backgroundColor` 与 `kbd` 的 `getBoundingClientRect().height`。

## 9. DIAG-001 报表类页面「请求未成功」（**先复现，再谈修**）

用户报告以下页面出现「请求未成功」：经营驾驶舱 / 组合分析 / 现金流预测 / ROI 测算 / 敏感性分析 / 报表查询 / 结账中心 / 多准则对比。

Reviewer 已排除的：

- **不是镜像问题**。web 的 `NEXT_PUBLIC_*` 是写死的构建常量（`/api`、`/api/ai`），客户端同源、由 Next rewrites 转发到 `core-service:8080`，宿主端口变化影响不到它。
- **不是数据库问题**。`lease_contracts=2`、`retail_store_day_facts=10860`、`users=2`，`core-service` 日志只有 `Connected to PostgreSQL` + 启动行，无错误。
- **不是鉴权问题**。401 会走 `api.session_expired`（「登录已过期」），不是这条文案。

**已定位的共同点**：上述页面**全部**走 `reportApi.*` 这一条缝（`cashflow-forecast/page.tsx:124,148`、`portfolio/page.tsx:128,141` 等）。而「请求未成功」是 `apiErrorMessage` 的兜底文案，对应 `conflict / data_unavailable / invalid_arguments / business_failure / review_required / capability_denied / timeout`，或**任何没带 code 且状态码不属于 401/403/404/5xx 的响应**（`lib/api.ts:35-79`）。

**要求**（按顺序）：

1. **复现并取证**：登录后逐个打开这 8 个页面，记录每个失败请求的 `URL / HTTP status / 响应体 code 与 detail`。报告里给一张表，**不接受「已复现」这类结论式描述**。
2. **分类**：区分「后端真的报错」与「数据为空但被当成错误」。仓库里已有先例——FIX-002~004 那批就是把「空」从「错」里摘出来做成空态。
3. **修**：
   - 若是空数据 → 改成空态呈现（复用 FIX-003 的空态组件），不弹错误。
   - 若是真错误 → 修后端，并让前端消息**指名道姓**：哪个能力、什么原因、下一步做什么。当前 `api.request_failed` 的注释自己都承认它含糊（「Reached by any status that is not 401/403/404/5xx」）。
4. **顺带收紧**：`apiErrorMessage` 的兜底分支带上失败能力名与 trace id，便于以后一眼定位。

**⚠️ 拦坑**：不要为了让页面「不报错」而 catch 掉异常显示空白 —— 那是把可信度问题藏起来，直接退回。

**验收**：
```

core-service: go test ./...
```
外加 §9.1 的复现表格与修复后的同表对照。
