## 1. 背景

本系统的第一条不可突破底线是**跨法人隔离**：法人 A 的账号不得读写法人 B 的数据。

当前这条底线由「38 处查询各自自觉写对」来保证，且存在一条可达的绕过路径：

| 环节 | 位置 | 事实 |
|---|---|---|
| 1 | `db/init/01_init.sql` | `users.legal_entity_id UUID`，**可为空** |
| 2 | `core-service/internal/handlers/auth.go:108` | `AdminCreateUserRequest.LegalEntityID *string`，**无 `binding:"required"`** |
| 3 | `core-service/internal/handlers/auth.go` `buildTokens` | `if user.LegalEntityID != nil { … }` —— NULL 时变量保持 `""`，空串写进 JWT |
| 4 | `core-service/internal/middleware/tenant.go:13–30` | `TenantMiddleware` 把缺失值规范化为 `""` 后放行 |
| 5 | 各 handler | 例：`handlers/fpna_governance.go` 有 26 处 `GetTenantID` 调用，**0 处空值检查** |
| 6 | 仓储层 | **38 处** `($N='' OR legal_entity_id::text=$N)` —— 空串时谓词恒真，**返回所有法人的数据** |
| 7 | `core-service/internal/middleware/tenant.go:45` | `RequireTenant()` 已存在，但**全仓 0 个调用点**（死代码） |

**可复现的失败场景**：管理员建一个不带 `legal_entity_id` 的普通用户 → 该用户 JWT 的法人声明为 `""` → 调用 `GET /api/v1/performance/decision-memos` → 谓词短路为真 → 返回**全部法人**的决策备忘录。计划版本、映射、数据质量记录、报表工件、Agent 信号是同一形状。

**严重度说明（请如实理解，不要在报告里夸大）**：这是**潜在且触手可及**，不是「正在泄漏」。现有种子用户都带法人 ID，管理员本就应为空。但一次不带该字段的建用户调用就会静默产生一个跨法人读取者，且没有守卫、没有测试、没有编译期保护。

## 2. 为什么不是直接改那 38 条查询

**因为有一个单一收口点。** `core-service/cmd/api/main.go:167–170`：

```go
api.Use(middleware.JWTAuth(cfg.JWTSecret))
api.Use(middleware.LoadUserPermissions(roleRepo))
api.Use(middleware.DataScopeMiddleware())
api.Use(middleware.TenantMiddleware())
```

**所有**需要认证的路由都经过这条链。在这里加一道判定，比修改 38 处查询更彻底、更小、更容易验证，且不可能被漏掉某一处。

改造那 38 处查询是后续任务（引入不能持有空串的值类型），**本票不做**。

---

## 3. 关键设计约束（写错这里会锁死管理员）

**不能简单地「空法人就拒绝」。** 管理员是合法的跨法人角色，其法人字段本来就是空的。

正确判定是：**法人为空 且 不是 Global** → 拒绝。

`Global` 的来源是既有的 `access.Scope`，在 `core-service/internal/middleware/rbac.go:85` 由 `*:*` 权限决定：

```go
scope := access.Scope{
    Global:        HasPermission(permissionStrings, "*", "*"),
    LegalEntityID: legalEntityIDStr,
    …
}
```

仓库里已有一处完全相同形状的判定可以参照 —— `middleware/rbac.go` 的 `RequireLegalEntityWideScope()`：

```go
if !ok || (!scope.Global && (scope.LegalEntityID == "" || …)) {
    c.JSON(http.StatusForbidden, gin.H{"error": "…"})
    c.Abort()
    return
}
```

**领域依据**（`CONTEXT.md` → Legal Entity Access）：非管理员可访问的最大范围由分配给该用户的法人决定。因此「非 Global 且无法人」在领域上就是配置错误，不存在合法用例，拒绝是正确行为。

## 4. 必须实现

### 4.1 收口守卫（核心）

在 `core-service/internal/middleware/tenant.go` 中提供一个守卫（可以新写，也可以把死代码 `RequireTenant()` 改成正确语义并复用其名字，二选一，在报告里说明选了哪个）：

- 从 `middleware.GetAccessScope(c)` 取 `access.Scope`；
- 若取不到 scope，或 `!scope.Global && strings.TrimSpace(scope.LegalEntityID) == ""` → 返回 **HTTP 403** 并 `c.Abort()`；
- 其余情况放行。

挂载到 `core-service/cmd/api/main.go` 的 `api` 组中间件链**末尾**（即现有 `middleware.TenantMiddleware()` 之后）。

**必须自行确认中间件顺序**：守卫依赖 `access_scope`，该值由 `DataScopeMiddleware()` 写入。请确认在守卫执行时 `GetAccessScope` 能取到值；若顺序有问题，调整顺序而不是绕过守卫。**在报告里写明你确认的顺序。**

### 4.2 输入侧收紧

`core-service/internal/handlers/auth.go:108` `AdminCreateUserRequest`：

- 创建**非管理员**用户时，`legal_entity_id` 必须提供且为合法 UUID；缺失时返回 **HTTP 400**，错误信息说明该字段必填；
- 创建管理员（跨法人）用户时，允许为空；
- 若存在同形状的「更新用户」接口，同样处理。

判定「是不是管理员」请复用该文件已有的角色判定逻辑（`requestedRoles` / `isAssignableRole` 附近），不要新造一套角色字符串比较。

### 4.3 回归测试（必须新增，否则本票不予验收）

在 `core-service/internal/middleware/` 与 `core-service/internal/handlers/` 下补测试，至少覆盖：

| # | 场景 | 期望 |
|---|---|---|
| T1 | 非 Global 用户 + 法人为空，请求任一受保护路由 | **403**，且未进入 handler |
| T2 | Global（管理员）用户 + 法人为空 | **放行**，行为与改动前一致 |
| T3 | 普通用户 + 法人非空 | **放行**，行为与改动前一致 |
| T4 | 法人为空白字符串（`" "`） | 与 T1 同样 **403**（证明做了 trim） |
| T5 | 建用户：非管理员角色 + 缺 `legal_entity_id` | **400** |
| T6 | 建用户：非管理员角色 + 非法 UUID | **400** |
| T7 | 建用户：管理员角色 + 缺 `legal_entity_id` | **成功创建** |

T1 请至少选 **3 条不同域**的路由各测一次（建议：一条 FP&A、一条零售、一条合同），证明守卫是全局生效而不是单路由补丁。
