## 1. 背景：阶段一是唯一没做的阶段，而它本该最先做

十个批次做完之后，按 UIUX 方案自己的验收标准实测：

| 项 | 目标 | 现状 | |
|---|---|---|---|
| `!important` | ≤ 20 | **140** | ❌ |
| `1px solid` | 0 | **25** | ❌ |
| 全仓内联样式 | —（评审基线 906） | **795** | 十批只降 111 |

六项过四项，**没过的两项恰好是这个阶段的全部意义**。`!important` 从 2026-08-13 评审至今一个没少。

方案 §6 写着「阶段一是其余三个阶段的硬前置，否则新组件会继续被 `!important` 覆盖」。我们把阶段二三四做了、阶段一没做，顺序正好反过来。**这条债已经兑现过一次**：FIX-010 修全局搜索框时，`.global-search-trigger` 的胶囊底色在真实 `AppLayout` 里失效，正是 AntD 运行时样式在同等特异性下后插入、压过了我们的规则。

**止血不用做**：`enforce-design.mjs` 已按「新增行」拦截 `!important` / 静态内联样式 / 字重 / 硬编码中文。本批全部是**存量**。

## 2. STY-007 AntD 覆盖改走 token（**P0，本批主体**）

### 2.1 现状分布（实测）

140 处 `!important` 里：

```
ant-*      114 处   ← 本票范围
ai-*        21 处   ← STY-008
session-*    3 处   ← STY-008
store-*      2 处   ← STY-008
```

**八成是在跟 AntD 打架。** 方案 §5 定的方向是「用 token 驯服 AntD，不换框架」——`web/app/design-system/theme.ts` 已经有完整的 `components` token 段（Modal / Button / Card / Table / Tag…），FIX-019 就是在那儿改一个 token 解决了全站 17 个 Modal 的标题栏。

### 2.2 要求

**逐个组件族迁移，一族一个 commit。** 每族的流程固定：

1. 找出该族在 `globals.css` 里的 `!important` 规则。
2. 判断它想覆盖的是哪个 AntD token（`titleFontSize`、`headerBg`、`borderRadiusLG`、`colorBorderSecondary`…）。
3. 把值搬进 `theme.ts` 的对应 `components` 段，删掉 CSS 规则。
4. **token 表达不了的**才保留 CSS，并且**去掉 `!important`、改用提高特异性**（例如 `.app-header .ant-btn`）。保留一条就在规则上方写明为什么 token 做不到。

建议顺序（按处数从多到少，先啃大的）：Table → Button → Card → Modal → Menu → Tag → 其余。

### 2.3 ⚠️ 拦坑（这条最重要）

**不要把多个类并进一条共享规则时改动取值。** FIX-034 就是这么翻车的：我把 `store360-peer-table`（8px）、`scenario-loading-block`（160px）、`scenario-block-gap-sm`（12px）并进了 16px / 220px / 8px 的共享规则，三处值被同化，STY-006 才查出来。

**并规则可以，改值不行。** 值不同就分开写。

其余：

- **AntD 的运行时样式是后插入的**，同特异性下它赢。所以验证必须在**真实 `AppLayout` 里**跑，把组件单独挂在裸页面上测会得到错误的绿灯（FIX-010 的教训）。
- 不得引入新的 `!important` 来「先让它生效」——那是在用债还债。

### 2.4 验收

```
web: npm test
web: node scripts/enforce-design.mjs
web: npm run build
```

外加：

1. **计数**：报告给出每族迁移前后的 `!important` 计数，总数必须从 140 显著下降（本票目标 ≤ 40）。
2. **实测**：每族至少一条 `getComputedStyle` 的改动前后对照，且**在 `AppLayout` 内渲染**（GUARD-001 的规则）。
3. **反向验证**：任选一族，把 token 改回错误值，测试必须红。

## 3. STY-008 剩余 `!important` 与 `1px solid`（P1）

- `ai-*` 21 处、`session-*` 3 处、`store-*` 2 处：这些是**我们自己的类**，`!important` 通常意味着「当时不知道被谁覆盖了」。逐条查清覆盖来源，用特异性或调整规则顺序解决。
- `1px solid` 25 处 → 走 `--border-default` / `--border-subtle` token（DESIGN.md 的 shadow-as-border 原则）。

**验收**：`!important` ≤ 20（方案目标）、`1px solid` = 0，报告贴计数与两条实测对照。

## 5. STATE-003 `StateBlock`：把阶段二真正收口（P1）

### 5.1 阶段二只做了一半

方案阶段二的验收写着「**空/载/错三态全站同一组件**」。现状：

- 判定层 ✅：`lib/dataState.ts`（STATE-001）已经统一了「这是空、是待操作、还是失败」
- 呈现层 ❌：**`StateBlock` 组件根本不存在**。实测全仓 `<Empty>` **40 处 / 17 个文件**，`<Alert type="error">` 8 处，各写各的

**判定统一了，呈现没统一。** 文档把阶段二记成待办也不准确——DataTrustBar 那半已经接了 10 个页面。

### 5.2 要求

1. 建 `<StateBlock />`，入参直接吃 `DataState` 的 `kind`（`empty` / `actionable` / `failed` / `scope_denied` / `ready`），四态各有固定呈现：
   - `empty`：安静一行 + 为什么空（参照 FIX-033 之后右栏空态的密度）
   - `actionable`：说明 + **下一步动作按钮**（STATE-001 已有三个落点可参照）
   - `failed`：错误 + 原因 + 重试
   - `scope_denied`：权限拒绝，**不得软化**（AGENTS.md 红线）
2. **本票只迁零售三页 + 首页右栏 + 合同详情**，其余 12 个文件另开票。
3. `scope_denied` 的呈现必须与 `failed` 可区分。

### 5.3 验收

```
web: npm test -- StateBlock state
```
断言四态各自渲染；已迁页面不再直接使用 `<Empty>` / `<Alert type="error">`；`scope_denied` 文案保留原因。
