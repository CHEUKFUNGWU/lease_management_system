## 0. 你接手的是什么

一份《UI/UX与产品能力全面改善建议书》提出了 31 页的大改。我按代码逐条核实过，**建议书的缺口分析有一半已被代码推翻**：品类量/结构/价三效应拆解、库存 DOI 与周转、竞对对标、促销投后增量毛利归因、公式 DSL 引擎（含循环引用检测），这些都已经在跑。所以本批次**不是**照建议书施工，是照复核后的 Spec 施工。

真正要处理的是三件事，严重性递减：

1. **界面在说假话。** `/performance` 有一列叫「同群平均坪效达成率」，渲染的是设备综合效率 `oee_pct`。同一张表把工厂代码的空值兜底显示成「核心商圈」。这违反本仓最硬的一条纪律：缺失显示「—」，不用别的数字冒充。
2. **做出来的能力没露出。** 人效指标 `sales_per_labor_hour` 在 `retail-kpi-v1` 里定义好了、事实层有 `labor_hours` 列、计算代码在跑，只是 `retailstore360` 的两个字符串切片没把它列进去，前端拿不到。
3. **五项真缺口。** 促销投前保本、新店业务可行性、利润差异归因、滚动预测滚入、公式可视化编辑器。

**坑 7：RH7 别为滚动路径新开一条 run 写入口。** `fin_model_runs` 只有一条写入口（`finmodel/persist`），架构测试是 `finmodel/writeguard_test.go`。你新开一条它会红，那不是测试过时。

**坑 8：RH4 的 import guard 要遍历全部子包。** 照 `finmodel/importguard_test.go` 的写法。只查根包会漏掉子包里的 `ifrs16` import，那份测试当初就差点栽在这儿。

**坑 10：你没有视觉能力。** 报告里不要写「看起来怎样」「界面更清晰了」，那只能靠猜。写**能从代码直接读出的结构事实**：哪个组件渲染在哪、新增删除了哪些 CSS 类与 token、每种角色走哪条分支、新增了哪些文案 key。视觉影响由我推导后交用户确认。

> **注意（这条我第一版写错了，已更正）**：不要用「输出不含『坪效』『商圈』『同群』字样」做断言。空态文案本身就要提到「坪效」和「同群对标」才能把话说清楚，禁词式断言会和文案打架，而且它验的是措辞不是行为。按下面四条写：

- 断言渲染结果包含 `perf.peer.unavailable_title` 的文案；
- 断言 `resolveBasis("oee_pct", "equipment", "retail_store")` 返回 `usable: false`，且 `resolveBasis("sales_per_sqm", "retail_store", "retail_store")` 返回 `usable: true`（两个方向都要，否则一个恒返回 false 的实现也能过）。

### R0-3　三个页面的定位说明

**背景**：`/performance` 与 `/operating-pulse` 回答同一个问题、走不同后端、数值可能对不上。`/roi` 是内部系统投入产出测算工具，不是经营分析，且已不在导航里。使用者现在没有任何线索知道这些。

perf.scope_note
  这一页看的是月度口径的经营驾驶舱：四墙 EBITDA 排行、行动项跟进、月度事实
  导入。日度和周度的经营波动看「经营脉搏」。两页的数取自不同的后端，同一
  指标可能有差异，做汇报时以其中一页为准，别混着引用。

pulse.scope_note
  这一页看的是日度和周度的经营波动，带覆盖率与 Decision Ready 判定。月度口径

  同一指标可能有差异。

roi.scope_note
  这一页算的是引入本系统能省多少人工，用于内部立项，不是门店经营分析。找门店
