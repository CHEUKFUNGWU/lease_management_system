# AR5c 开工前置 — ACORE-2 #7 审计断言的位置位移确认

## 1. 断言原文与当前层

`internal/agentcore/hooks/mutation_test.go:183-190`（TestMutationAfterHooks 第一段）：

```go
auditErr := errors.New("audit down")
recorder := agenttools.AuditRecorderFunc(func(...) error { return auditErr })

// AuditRecorder: its failure must surface through the chain.
if _, err := afterChain(Deps{Audit: recorder}, "")(context.Background(), ac); !errors.Is(err, auditErr) {
    t.Fatalf("audit failure must propagate, got %v", err)
}
if _, err := afterChain(Deps{Audit: recorder}, "AuditRecorder")(context.Background(), ac); err != nil {
    t.Fatalf("removing AuditRecorder must drop the failure, got %v", err)
}
```

**当前层：工具调用返回值层。** `afterChain(...)` 就是 AfterToolCall 链本身；
auditErr 从链函数的 error 返回值同步冒泡。同一函数里第二段断言移除中间件后
error 消失——两条合起来构成「失败可见 + 移除即消失」的完整因果。

## 2. 方案 (b) 下移到哪一层、为什么必须移

移到 **run 收尾层**：审计失败不再从链返回值冒泡（picoclaw 的 `callAfterTool`
对 hook error 只 `continue` 跳过该 hook——error 通道在挂点上不存在传播语义，
这是结构事实，不是选择）；改为 wrapper 记录失败标记，回合收尾处 run 以
`fmt.Errorf(..., ": %w", auditErr)` 形式失败。

为什么必须移：原生挂点的 error 通道只表达「跳过该 hook」，任何试图在链级
重现 errors.Is 冒泡的实现都等于改上游分发器（方案 (c)，已被否）。

## 3. 「移除即红」因果是否成立

**成立。** 移位后的等价断言（run 收尾层）：

- 红（先证）：新内核原生行为（吞 error）下 run 正常完成 →
  `errors.Is(runErr, auditErr)` 断言红；
- 绿：(b) 实现后 run 失败且 errors.Is 因果保留 → 绿；
- **变异敏感**：删掉 AuditRecorder 中间件 → 标记从不被置位 → run 成功 →
  同一条断言再次变红。「红在哪一层」= run 收尾层（不再是工具调用返回值层）。

**结论：因果不断裂，可以继续。** 附带义务：实施时该测试必须以三段式
（原生红 → 实现绿 → 删中间件再红）留痕，并在测试注释里写明位置位移理由。
