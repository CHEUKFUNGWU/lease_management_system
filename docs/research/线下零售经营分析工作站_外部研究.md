# 线下零售经营分析工作站：外部一手资料研究

> 研究日期 / 资料访问日期：2026-08-11  
> 研究问题：现有 IFRS 16 租赁管理产品能否合理扩展为“线下零售经营分析工作站”；应覆盖哪些数据域与 KPI；租赁数据如何与门店、商品、库存、客流和排班结合；AI Agent 的权限和治理边界是什么；哪些能力应自建、哪些应集成。  
> 证据口径：优先采用标准组织、监管机构、官方产品/API 文档及公开监管申报资料。本文不使用咨询报告或媒体文章来支撑核心判断。
> 2026-08-12 范围修订：产品只服务本集团作为承租方的零售经营、占用成本、合同约束与 IFRS 16，不进入地产开发、招商、选址、物业资产经营或房东管理。本文引用物业经营者公开指标仅用于证明“销售、面积与占用成本”的联结方式存在，不代表产品范围。

## 一、结论摘要

### 1. 产品方向具备可行性，但应定义为“经营决策层”，不是替换 POS、ERP、WMS 或 WFM

微软的官方零售数据模型将零售数据碎片化、检索耗时、口径不一致和治理不足列为主要问题，并将统一数据模型定位为治理、报表、BI 和高级分析的基础；其零售产品场景同时覆盖 POS、供应链、忠诚度、商品、库存、需求预测、门店洞察和一线员工，而不仅是合同或财务核算。[S1][S2] 这说明“跨系统经营分析 + 行动闭环”本身是已被主流企业软件厂商确认的产品类别。

对本项目的含义是：可从“以 IFRS 16 计量为中心”转为“以门店经营单元为中心”，保留租赁子账、合同事件和审计链作为难以复制的纵深能力。产品不应重新制造交易系统，而应连接既有 POS/电商、商品、库存、劳动力、客流和财务系统，在其上建立统一指标、诊断、情景模拟、决策卡和受控执行。

### 2. 最有差异化的切入点是“单店经济模型”，租赁能力应从中心变成优势数据域

IFRS 16 的官方目标是确认使用权资产和租赁负债，以呈现租赁交易和未来现金流；这是一套财务报告口径，不等于门店日常经营成本口径。[S11] IFRS Foundation 的项目总结进一步说明：与未来销售或使用挂钩的可变付款通常不进入租赁资产和负债计量，而与通胀指数挂钩的付款进入计量；经营分析却仍需观察当期实际 turnover rent，这正是会计与经营口径必须并存的原因。[S23] 另一方面，公开监管申报中，零售物业经营者会把 occupancy cost ratio 定义为“年化占用成本 / 过去十二个月租户销售额”，并同时跟踪每平方英尺销售额，表明“销售、面积和占用成本”的联结是实际经营决策中的常见组合，而非纯会计问题。[S12]

因此，产品应同时保留两套不可混淆的视图：

- **会计视图**：使用权资产、租赁负债、折旧、利息、重估、关账与披露；
- **经营视图**：固定租金、抽成租金、CAM/物业费、税费、租赁现金承诺、面积、门店销售、毛利、人工和店级贡献。

两者共享合同、门店、期间和事件，但必须有独立的指标定义与版本。把 IFRS 16 折旧/利息直接当作门店 occupancy cash cost，会造成决策口径错误。

### 3. 典型数据域和 KPI 已有足够的一手资料支撑，关键难点在语义统一与数据质量

Shopify 官方分析字段给出了净销售、客单价、毛利、毛利率、库存可售天数、售罄率等可执行定义；Oracle Retail Insights 覆盖门店客流、转化率、GMROI、周转、可售周数等零售指标；Square API 暴露订单明细、库存变动、人员、工资、排班、工时和地点。[S4][S6][S7][S8][S9] 这些资料共同支持以下最小分析域：门店/组织、商品、交易、库存、客流、客户、人员排班、租赁占用成本、财务与计划。

难点不是“有没有指标”，而是同一名称在来源系统中的定义、时区、税费、退货、跨渠道归属、可比店规则和数据延迟不一致。产品必须建设版本化语义层、来源血缘、数据质量状态和可重算快照，而不能让 Agent 临时写 SQL 解释指标。

### 4. AI Agent 可行，但默认应为“可引用的分析员 + 可审批的工作流助手”

微软的企业 Agent 设计指导明确建议：使用用户级身份读取用户本来有权访问的数据；系统身份只用于边界清晰的服务操作；不可逆操作须审批；所有工具调用、拒绝和升级都应可审计。[S15] 其零售 Copilot 文档也明确提示 AI 生成的门店报告摘要可能不正确。[S14] NIST AI RMF 要求在全生命周期持续 Govern、Map、Measure、Manage，并包含上线后监控、申诉/覆盖、停用、事件响应和变更管理。[S18]

所以首阶段 Agent 应聚焦：检索、解释、异常归因、情景模拟、行动建议、任务草稿、续租/闭店决策材料草稿；不应自动改价、发采购单、发布排班、终止租约、过账或对外发送承诺。后续即使开放写操作，也必须在用户身份、最小权限、预览差异、审批、幂等、预算、可撤销和审计日志的约束下逐项开通。

### 5. 推荐 Build-vs-integrate：自建“语义、决策、治理”，集成“事实来源、执行系统、基础模型”

官方 API 已证明 POS/订单、商品、库存、地点、人员和排班数据可以通过 API、批量导出和 Webhook 接入。[S8][S9][S10] Shopify 还明确提示 Webhook 不保证绝对送达，应用必须运行对账任务；这意味着连接器不能只做事件流，还需“历史回灌 + 增量事件 + 周期对账”。[S10]

建议自建：零售经营语义层、租赁与门店桥接、店级损益/单店经济、指标版本、证据链、诊断与情景引擎、决策工作流、Agent 工具权限与评测。建议集成：POS/OMS、电商、ERP、WMS、CRM/忠诚度、排班考勤、客流设备、天气/商圈数据和基础大模型。除非客户明确要求，不应自建 POS、WMS、完整 WFM、人脸识别或通用数据湖平台。

## 二、外部证据支持的零售分析数据域

下表是建议的产品规范。标记为“外部证据”的字段来自官方资料；“产品推断”是结合这些资料形成的设计建议，并非某一家厂商的标准模型。

| 数据域 | 最小实体 / 事实 | 主要来源 | 可支持的决策 | 证据性质 |
|---|---|---|---|---|
| 组织与门店 | 法人、品牌、区域、门店、仓库、营业日历、地址、面积、营业状态 | 微软零售数据模型允许按需选用和扩展实体；Shopify Location 把零售店、仓库、快闪店等建模为库存与履约地点。[S1][S3] | 门店分层、区域对标、可比店口径、单位面积效率 | 外部证据 + 产品推断 |
| 商品与商品策略 | 商品、SKU/变体、品类、品牌、供应商、价格、折扣、税、陈列/组合 | Square Catalog API 覆盖商品、变体、选项、品类、折扣、税和价格规则。[S9] | 品类贡献、价格带、促销复盘、组合与关联销售 | 外部证据 |
| 交易与销售 | 订单、行项目、数量、原价、折扣、退货、支付、渠道、门店、员工 | Square Orders API 可查询线上和 POS 的历史销售、退货和行项目；Shopify 有按商品、SKU、地点和员工的 POS 销售报表。[S5][S9] | 销售增长、客单、件单、退货、折扣和员工辅助销售 | 外部证据 |
| 库存与供应链 | 日末库存、可售量、收货、调拨、销售、退货、报损、盘点、在途 | Square Inventory API 把销售、退货、收货、报损和盘点作为库存变更；Oracle 维持每日、商品、库存地点层级的库存位置。[S9][S7] | 缺货、积压、调拨、补货、清货、现金占用 | 外部证据 |
| 客流与空间 | 进店人数、时段、门店/区域、匿名停留或动线聚合、面积 | Oracle Retail Insights 使用客流和转化率；微软公开足迹检测参考架构说明可用边缘推理分析门店访客流量。[S7][S13] | 转化率、排班匹配、面积与陈列效率 | 外部证据；隐私边界见第四节 |
| 人员与排班 | 员工、岗位、工资率、计划班次、实际工时、休息、地点 | Square Team/Labor API 覆盖员工、岗位、工资、排班、工时卡、休息和地点。[S8] | 人工成本、销售/工时、排班偏差、峰谷匹配 | 外部证据 |
| 客户与忠诚度 | 匿名顾客/会员、首购/复购、订单历史、偏好、营销同意 | 微软零售场景明确包含 POS、供应链和忠诚度；Shopify 分析定义新客和回头客。[S2][S4] | 拉新、复购、会员贡献、客群差异 | 外部证据；需严格个人信息治理 |
| 租赁与占用成本 | 合同、门店、面积、固定/变量租金、CAM/物业费、税费、押金、关键日期、选择权、现金承诺、ROU/负债 | IFRS 16 支持会计资产负债和租赁现金流；公开申报支持占用成本/销售额和销售/面积的经营联结。[S11][S12] | 续租、谈判、搬迁、闭店、扩店、保本销售 | 外部证据 + 产品推断 |
| 财务与计划 | COGS、门店费用、预算、预测、目标、实际、期间和版本 | Shopify 的毛利指标依赖 COGS；微软将统一零售数据用于 BI、预测和库存优化。[S1][S4] | 店级贡献、预算偏差、滚动预测、资源配置 | 外部证据 + 产品推断 |
| 事件与行动 | 缺货、异常、门店任务、续租、促销、调拨、审批、结果反馈 | Microsoft Store Operations 把门店数据、洞察、任务和运营流程结合；Agent 设计要求行动、审批和审计。[S2][S15] | 从洞察到负责人、截止日、审批和复盘 | 外部证据 + 产品推断 |

### 建议采用的主数据和事件语言

GS1 EPCIS 用“what、when、where、why、how”描述商品与资产的状态、位置、移动和业务语境，并以 GTIN、GLN 等标识支撑跨企业互操作。[S3] 对本产品最有价值的不是完整实现 EPCIS，而是采用其思路：

- 商品、地点、组织和业务事件使用稳定外部键，并保留 source system + source ID；
- 每一条库存、交易、租赁和行动事实都包含有效时间、记录时间、地点和业务原因；
- 原始事件不可变，纠错通过新事件或版本完成；
- 不把来源系统名称直接当成业务语义，统一映射到版本化的 canonical model。

## 三、推荐 KPI 树与口径纪律

### 3.1 第一层：经营结果

| KPI | 建议定义 | 官方依据 / 注意事项 |
|---|---|---|
| 净销售额 | `gross sales - discounts - sales reversals` | Shopify 官方字段定义。[S4] 税、运费是否包含必须另设指标，避免把 total sales 与 net sales 混用。 |
| 毛利额 | `net sales - COGS` | Shopify 官方定义。[S4] 缺失商品成本时必须标为不完整，不得用售价倒推。 |
| 毛利率 | `gross profit / net sales` | Shopify 官方定义。[S4] 分母为零或负时应单独处理。 |
| 订单数 / 交易数 | 符合状态规则的销售交易数 | 退货会形成订单记录；必须明确是否排除全退订单。[S4] |
| 客单价 AOV | `(gross sales - discounts) / orders` | Shopify 官方定义。[S4] 产品应另提供净销售/净交易的管理口径，并标注差异。 |
| 件单量 UPT | 净销售件数 / 净交易数 | 产品建议；须定义退货、赠品、称重商品和组合装规则。 |
| 转化率 | `sales transactions / store traffic` | Oracle 官方零售文档采用该逻辑。[S7] 门口重复计数、员工剔除、跨入口去重是数据质量前提。 |

### 3.2 第二层：商品与库存效率

| KPI | 建议定义 | 官方依据 / 注意事项 |
|---|---|---|
| 售罄率 | `sold units / (sold units + ending inventory units)` | Shopify 官方定义。[S6] 期间收货会影响分母，产品应显示数据日期和延迟。 |
| 库存可售天数 | `ending inventory units / units sold per day` | Shopify 官方定义。[S4][S6] 属于按当前速度估算，不是需求预测。 |
| 库存周转 | `COGS / average inventory at cost` | Oracle Retail Insights 官方指标定义。[S7] 必须保证成本口径一致。 |
| GMROI | 毛利与平均库存成本投入的关系 | Oracle 把 GMROI 列为商品生命周期指标。[S7] 产品需冻结本地公式和时间权重，不应只复用名称。 |
| 缺货天数 / 在库天数 | 日末库存为零 / 大于零的天数 | Shopify 官方字段提供 location 级天数。[S4] 账面有货不代表货架可售，需区分系统库存与货架可用。 |
| 调拨与报损 | 按原因汇总的库存事件数量和成本 | Square Inventory API 区分收货、销售、退货、报损与盘点。[S9] |

### 3.3 第三层：单店经济和资产决策

以下是本产品应自建的差异化指标。它们是基于公开经营实践的产品建议，不是 IFRS 或任何厂商强制定义：

- **门店贡献 I** = 净销售额 − COGS − 可归属促销/支付等变动费用；
- **门店贡献 II** = 门店贡献 I − 实际人工成本 − 经营占用成本 − 其他可控门店费用；
- **经营占用成本率** = 经营占用成本 / 净销售额；公开申报中的 OCR 采用“年化占用成本 / TTM 租户销售额”，但本产品必须版本化定义其分子是否含 CAM、税、抽成租金和公用事业费。[S12]
- **销售/面积、毛利/面积、贡献/面积** = 相应期间金额 / 有效营业面积；SAP 官方零售规划 KPI 也采用 `Sales at Retail / Selling Space` 的单位面积销售逻辑。[S24] 面积变更必须按生效日期处理，并明确使用售卖面积、租赁面积还是建筑面积；
- **销售/人工小时、毛利/人工小时、人工成本率** = 销售或毛利 / 实际工时，实际人工成本 / 净销售；
- **保本销售额** = 可避免固定成本 / 贡献毛利率；输入、情景和假设必须可追溯；
- **租赁承诺覆盖** = 预测可控贡献 / 未来租赁现金承诺；不得用 ROU 账面价值代替现金承诺；
- **续租/闭店决策价值** = 基准、续租、缩店、搬迁、闭店等情景的增量现金流、一次性成本、库存清理、人员成本和风险调整结果。

### 3.4 口径治理要求

每个 KPI 至少应存储：`metric_id`、显示名称、业务定义、公式、粒度、允许维度、时间口径、币种/税口径、数据源、质量门槛、版本、生效日、负责人、审批状态和示例。可比店、同店销售、占用成本、店级 EBITDA 类指标在不同企业间差异大，必须由客户政策定义，不应声称存在唯一行业公式。

## 四、门店、商品、库存、客流、排班和租赁的组合机会

| 组合 | 可回答的问题 | 数据要求 | 主要风险 |
|---|---|---|---|
| 销售 × 客流 × 时段 × 排班 | 下降来自客流、转化、客单，还是人员覆盖不足？ | 15/30/60 分钟粒度的客流、交易和实际工时；统一门店时区 | 客流漏计/重复计、员工未剔除、相关性被误判为因果 |
| SKU × 库存 × 门店 × 交易 | 低销售是需求弱，还是缺货/陈列/配货问题？ | SKU-location-day 的库存位置、销售、收货、调拨和报损 | 账面库存与货架库存不一致；迟到事件 |
| 品类 × 毛利 × 面积 | 哪些品类应扩/缩陈列，哪些仅带来销量不带来贡献？ | 品类层级、有效面积、毛利、关联购买 | 面积分配估算误差；联购带来的间接价值 |
| 门店 × 人工 × 客流 | 哪些时段需调整排班，如何兼顾服务和成本？ | 计划/实际班次、工资率、客流和交易 | 劳动法、最低编制、员工隐私和公平性 |
| 门店 × 租赁 × 经营贡献 | 哪些门店应续租、谈判、缩店、搬迁或退出？ | 未来租金/CAM/抽成、关键日期、贡献预测、一次性成本 | IFRS 口径与现金口径混淆；预测不确定性；不可逆决策 |
| 续租事件 × 情景 × 审批 | 何时启动谈判，底线租金和条件是什么？ | 选择权窗口、租约到期、商圈/门店趋势、情景假设 | Agent 过度承诺；谈判信息泄露；缺少责任人 |

### 客流与视觉分析的隐私底线

《个人信息保护法》要求处理目的明确、合理、直接相关，采用对个人权益影响最小的方式，并把收集限制在必要范围。[S20] 2025 年生效的《人脸识别技术应用安全管理办法》进一步要求特定目的和充分必要性、告知、严格保护、事前个人信息保护影响评估，并规定存在其他方式时不得把人脸识别作为唯一验证方式。[S21]

因此，产品默认只接入**匿名人数/区域聚合**，优先在边缘设备完成检测，不保存原始视频、人脸模板、身份或人口属性。人脸识别、跨店身份追踪、会员画像匹配不是 MVP 能力；如客户坚持采用，必须作为独立高风险项目，由法务、隐私、信息安全和业务共同评估，不能因“提高分析精度”自动获得授权。

## 五、AI Agent 能力范围与权限模型

### 5.1 推荐能力分级

| 级别 | 允许能力 | 典型输出/工具 | 默认审批 |
|---|---|---|---|
| L0 解释 | 查询已授权的指标、合同、门店和政策；解释口径并给出引用 | 指标查询、来源跳转、自然语言摘要 | 无写入；不需审批 |
| L1 分析 | 异常检测、驱动分解、对标、预测和情景模拟 | 诊断卡、证据表、假设、置信度、反事实情景 | 结果仅为建议；用户确认后保存分析 |
| L2 草稿 | 生成行动计划、补货/调拨建议、续租决策卡、审批材料、任务草稿 | draft task、draft scenario、draft decision memo | 创建草稿可自动；发布/分派需确认 |
| L3 受控执行 | 对内部、可逆、低金额动作调用写工具 | 更新任务状态、发起数据补录、提交审批流 | 策略引擎判断；超阈值人工审批 |
| L4 高影响动作 | 改价、采购/调拨、发布排班、外部通信、租约承诺/终止、财务过账 | 执行系统写 API | MVP 禁止自主执行；双人/职责分离审批，必要时仅提供操作链接 |

### 5.2 每个 Agent 工具必须具备的控制面

微软企业 Agent 指导与安全文档支持用户身份、受限系统身份、知识源和连接器策略、不可逆动作审批以及全链路审计。[S15][S16][S17] NIST 零信任架构强调围绕身份、资产和资源作逐请求的访问决策，而非因位于内网就默认信任。[S19] 据此，工具规范至少应包含：

1. **身份与范围**：默认使用当前用户身份；强制 `legal_entity_id / brand / region / store / data_classification` 范围；服务身份只绑定单一用途。
2. **最小权限**：读、建草稿、提交、批准、执行分开；Agent 不得因为能建议某动作就自动拥有该动作的执行权。
3. **确定性输入**：工具使用结构化 schema、枚举、金额/数量/期间上限和来源 ID；模型不得自由拼接 SQL 或目标 URL。
4. **预览与差异**：写操作先返回影响对象、旧值/新值、金额、期间、可撤销性和冲突；高影响动作必须显式确认。
5. **审批与职责分离**：申请者、复核者、批准者和执行者按风险分离；Agent 不能自批自己生成的建议。
6. **幂等与并发**：每次动作带 idempotency key、版本号和条件更新，防止重复执行或覆盖人工变更。
7. **证据与可追溯**：记录问题、检索数据快照、指标版本、模型/提示版本、工具参数、审批、结果、错误、成本和关联业务记录。
8. **可停止与可恢复**：超时、预算上限、取消、断点、重试上限、补偿/回滚、人工接管和 kill switch。
9. **上线评测**：离线黄金用例、越权与 prompt injection 测试、计算一致性、引用正确率、建议采纳率、业务结果和事故率；持续监控漂移和新风险。[S18]
10. **输出标识**：清楚区分系统事实、计算结果、预测、假设与 AI 建议；用户可覆盖并说明原因。

### 5.3 需要明确禁止的 Agent 行为

- 绕过正式指标层直接“解释”原始表；
- 在缺失 COGS、客流、租金组成或可比店政策时补猜数字；
- 使用超出当前用户权限的数据进行跨法人/跨门店对标；
- 把相关性诊断表述为确定因果；
- 把 AI 建议直接写入正式租约、排班、价格、采购、会计分录或对外消息；
- 读取或持久化并非当前任务必要的会员、员工或人脸数据；
- 隐藏数据延迟、质量告警、预测区间、模型限制或审批状态。

## 六、Build vs integrate 建议

### 6.1 必须自建，形成产品护城河

| 能力 | 原因 |
|---|---|
| 统一门店经营语义层 | 来源系统只拥有局部真相；跨销售、库存、人工、租赁的指标定义和版本是核心产品。 |
| 租赁—门店—面积—期间桥接 | 现有 IFRS 16 合同、付款、事件、关键日期和审批能力可直接复用，也是区别于通用 BI 的优势。 |
| 单店经济与决策引擎 | 店级贡献、占用成本、保本点、续租/闭店/搬迁情景需要一致、可审计、可复演的规则。 |
| 经营异常与驱动分解 | 需按“销售 = 客流 × 转化 × 客单”等驱动树结合库存、人工和租赁证据，而非只生成摘要。 |
| 决策卡、任务、审批和结果复盘 | 让洞察进入责任人、截止日、审批、执行结果和收益验证，形成闭环数据。 |
| Agent Gateway、策略、审计和评测 | 工具权限、审批、证据链、成本、模型版本和运行回放属于企业级核心控制。 |
| 数据质量与对账 | 跨源键映射、迟到数据、重复事件、缺失成本和口径变化必须由平台统一管理。 |

### 6.2 优先集成，不建议重造

| 能力 | 建议连接方式 | 一手资料支持 |
|---|---|---|
| POS / OMS / 电商 | API + 历史批量回灌 + 订单/退货 Webhook + 每日对账 | Square Orders、Shopify Bulk/Webhooks。[S9][S10] |
| 商品 / 库存 / WMS | Catalog/Inventory API、库存事件、周期快照与盘点差异 | Square Catalog/Inventory；GS1 EPCIS 可作事件语义参考。[S3][S9] |
| 排班 / 考勤 / HR | 员工/岗位主数据、计划班次、实际工时和工资成本 API；默认只取分析所需字段 | Square Team/Labor API。[S8] |
| 客流设备 | 只接匿名聚合计数；事件含设备、门店、入口、时段、质量状态 | Oracle 客流指标；微软边缘足迹检测参考架构。[S7][S13] |
| ERP / 总账 / 预算 | 期间事实、成本中心、凭证/预算/预测接口；保持总账为正式账源 | 产品推断；本产品不应成为通用 ERP。 |
| CRM / 忠诚度 | 最小必要会员键、首购/复购、同意状态；敏感属性按用途隔离 | 微软零售场景、PIPL。[S2][S20] |
| 基础大模型 / OCR / 预测库 | 可插拔供应商；模型层不直接持有业务写权限 | NIST AI RMF 和企业 Agent 权限实践。[S15][S18] |
| BI / 数据湖 | 提供标准数据集/API/导出；客户已有平台时共存 | 微软零售数据模型定位为可选实体、可扩展的分析基础。[S1] |

### 6.3 推荐连接器设计

1. 建立 source adapter，将来源字段映射为 canonical entity/event；
2. 初次接入运行可断点的历史批量回灌；Shopify 官方提供异步 bulk query 以处理大量数据。[S10]
3. 增量数据优先使用 Webhook/CDC，但事件必须去重、排序容错和可重放；
4. 周期对账“来源系统总量/余额 vs 平台总量/余额”；Shopify 官方明确警告 Webhook 可能遗漏，需 reconciliation job。[S10]
5. 保存原始载荷哈希、API 版本、抓取时间、来源更新时间和转换版本；
6. 连接器权限按只读默认，只有经批准的执行用例才配置写 scope；
7. 对 API 限流、版本退役和许可证依赖设置健康检查。Square 的旧 Shift 端点已退役并迁移到 Timecard，说明版本演进必须纳入连接器运维。[S8]

## 七、产品可行性判断及验证门槛

### 已被外部资料支持的判断

- 零售企业需要统一 POS、供应链、忠诚度、商品、库存、人员和门店运营数据以做分析和行动。[S1][S2]
- 销售、毛利、客单、库存效率、客流转化和人工是主流零售分析域，且可从官方 API 或报表获得。[S4]-[S9]
- 租金/占用成本和销售、面积的结合具有实际经营意义；IFRS 16 数据可成为底座，但不能替代经营现金口径。[S11][S12]
- Agent 可用于门店报告摘要、库存查询和运营协助，但生成内容可能错误，必须有用户权限、审批、审计和持续风险管理。[S14]-[S19]
- Build-vs-integrate 的技术路径可行；主流平台提供 API、批量导出、Webhooks 和权限 scopes。[S8]-[S10]

### 尚未被这些资料证明的商业假设

- 中国线下零售客户是否愿意为“经营分析工作站”单独付费；
- 首个最有支付意愿的垂直行业是服饰、美妆、餐饮、便利店还是综合零售；
- 客户 POS/ERP/WFM 的真实接口开放度、实施周期和数据质量；
- 店长、区域经理、经营分析、财务 BP、租赁会计中谁是主用户和预算所有者；
- “租赁切入”相对通用 BI、FP&A、零售 SaaS 和客户自建数据平台的可持续竞争优势；
- 建议带来的增量销售、毛利、库存下降或租金谈判收益能否被可靠归因。

因此，可行性结论应表述为：**产品与技术方向成立，具备利用现有租赁/审计资产形成差异化的机会；是否形成真实市场需求仍无法从现有资料得出。** 当前没有设计伙伴或深访条件，应先用固定 seed 的 Golden Dataset、角色化任务、故障注入和权限攻击完成内部模拟验证。该验证只能支持技术与产品一致性结论，不能替代未来客户发现、真实数据接入和量化价值验证。

### 当前内部模拟验证门槛

- 模拟数据覆盖门店日销售、毛利、交易、客流、人工、预算、承租现金和合同关键日期；
- Golden Dataset 可由固定 seed 重建，所有关键指标与预期结果 100% 对数；
- 100% 首发指标有版本化定义、负责人和来源血缘；
- Agent 回答必须显示指标版本、期间、范围、引用和数据质量；高影响写工具保持关闭；
- 预设异常可形成可追踪的内部行动草稿，并区分平台建议、人工决策和模拟结果；
- 完成权限穿透、跨租户越权、提示注入、重复执行和审计回放测试。

## 八、研究局限

1. 微软、Shopify、Square 和 Oracle 文档是厂商对自身产品能力的第一方描述，可验证“能力存在”和“接口可用”，不能作为独立 ROI 证明。
2. Shopify/Square 更偏商户和中小零售生态，Oracle/Microsoft 更偏大型企业；真实目标客户的系统组合可能完全不同。
3. 公开申报中的 occupancy cost ratio 是特定公司、特定资产组合的非 GAAP/管理指标，只能证明该联结方式存在，不能把其数值当作零售行业基准。[S12]
4. KPI 名称并不保证跨系统同义；文中公式应作为起始模板，落地时必须经客户的经营、财务和数据负责人批准。
5. 中国个人信息、客流和生成式 AI 法规的适用性取决于部署方式、数据内容、服务对象和地域；本文不是法律意见，应由专业法律顾问确认。[S20]-[S22]
6. NIST AI RMF 和零信任架构是通用、自愿框架，不是中国监管合规的替代品；其价值在于建立工程控制和审计语言。[S18][S19]
7. 本研究未完成竞争格局、市场规模、价格、采购流程和客户访谈，不能单独支持商业投资决策。
