## RT1-A：上下文预算的可观测面

### 为什么

C1 spec 的契约变更清单写着：

> | 新增可观测指标 | **token 用量与上下文预算占用** |

User Story 6 讲了它存在的理由：

> 我想有一个可观测的 token 用量指标，**以便「观察到真实溢出」这个条件真的可被观察**

**实测：这条没做。** 装配器今天只有事件面（`run_events` 的 `context_compacted`、消息行的 `measured_tokens`），`ops/prometheus/` 下没有任何 token 或预算占用指标。

这件事的形状值得说清楚：ADR-0022 当初把压缩推迟到「观察到真实溢出」，而 C1 立项的核心论证正是**「没有计数就没有可观测量，那个条件永远不会被满足」**。现在计数、预算、压缩都建好了，AF1 四项缺陷也修好验过了——**可观测量仍然没有**。同一个死结换了个位置继续存在。

连带后果：装配器至今**没有在生产流量上跑过一次**。没有指标就不敢开，不开就永远拿不到真实数据。

Story 2（「上下文接近上限时收到提示」）同样是空的：唯一的事件 `context_compacted` 在**压缩发生之后**才发，撞墙前没有任何信号。

### 要做的

**1. 指标本体。** 沿用既有形状：`agenttools.RuntimeMetrics` 的累积 + `Prometheus(now)` 文本渲染 + `GET /agent/metrics/prometheus` 暴露（权限门照旧）。新指标是并列的一组，不要另起一套暴露机制。至少要能回答：一次回合占用了预算的多少、其中多少实测多少估算、压缩发没发生及丢了多少。

**2. 核心验收：实测与估算必须分开，不得合并成一个数。** `Prompt` 已经同时带 `Tokens` 与 `EstimatedTokens`，指标必须把两者分开暴露。

理由是 AF1-a 的教训：那次就是「类型上是 token 数、语义上是猜测」的值混进了计算，而且单测因为输入语义与生产不一致而照不出来。一个把实测与估算加总成单一数字的仪表盘，会让人以为自己在看测量结果——**这比没有仪表盘更糟，因为它会被用来做决策**。

**3. 标签纪律（硬约束）。** 禁止把 `legal_entity_id` / `user_id` / `session_id` 放进指标标签。两个理由任一独立成立：基数爆炸；`agentcontext.ContextKey` 特意不实现 `String()` 就是为了防止租户与用户标识被 `%v` 撒进日志（`key.go` D-C11 注释），指标标签是同一类出口，同一条纪律。按 `model` 打标签合理（预算几何本来就按模型配置）。其余维度动手前说明理由。

**4. Story 2：撞墙前的信号。** 占用率越过阈值时要有信号，且**必须发生在压缩之前**。阈值是配置还是常量、信号走事件还是指标还是两者，由你提案。**不要做成把 `context_compacted` 改个名**——那是事后记录，本条要的是事前预警，两者都要存在。

**5. 建议的形状：计数与压缩解耦（先提案再做）。** 现在 `CONTEXT_ASSEMBLER_ENABLED` 一个开关管两件事：算不算，和压不压。建议拆成两级，允许「只计数、只上报、不压缩」——这样能先在生产流量上收集真实占用数据，再拿数据决定压缩阈值与何时启用，而不是像现在这样必须先承担行为变更才能拿到第一个数据点。这正是 Story 6 那句「以便条件真的可被观察」的直接兑现。

但它改变现有开关语义，**动手前把方案抛回来**：两级怎么表达、默认值是什么、与 AF1-c 的启动期模型校验怎么配合（只计数模式是否仍要求预算几何——我的看法是要，因为占用率需要分母，但你可以反驳）。

**6. 告警规则。** `ops/prometheus/lease-agent.rules.yml` 补规则，形状照既有的 `LeaseAgentTool*` 两条。至少一条：占用率持续高位。阈值给出理由。

### RT1-A 验收

- 指标出现在 `GET /agent/metrics/prometheus`，实测与估算分开，权限门与既有指标一致
- **反向测试**：把实测与估算合并成一个数，测试必须变红
- **标签纪律测试**：断言渲染输出里不含法人 / 用户 / 会话标识——删掉纪律必须变红
- 撞墙前信号有测试证明它在压缩**之前**发生
- 若采纳两级开关：只计数模式下断言 prompt 内容**逐字节不变**
- 全量 `go test ./...` + `go vet` 绿；`make test-integration` 实跑非 SKIP

### RT1-A 不在范围

**不要打开装配器开关。** 本部分交付可观测面；开不开、什么时候开，是拿到指标之后的运营决策，不由这一单决定。也不动 AF1 已验证的计数语义（基线 + 尾部估算）——本部分是把已有的数暴露出来，不是重算。

## RT1-B：G9 剩余两平面接线（到期日 2026-09-30）

### 现状

SI1 Part B 把 **chat 平面**接上了 `sessionmanager`。索引 G9 现为「部分解决」，并写明：**2026-09-30 前完成剩余两平面接线或正式裁决废弃，逾期转入 `agentcore` 同款「死代码」审计口径**。

### 实测的范围

比看起来小，因为两个平面其实是一条路径：

- `handlers/agent_gateway_sessions.go:61` 的 `h.sessions.CreateSession(ctx, session)` —— gateway 平面自己的创建入口，绕过 `sessionmanager`
- `agentrunner` **不直接拥有会话生命周期**：`http_gateway.go:214` 的 `CreateSession` 是经 HTTP 调 gateway 的 API。**所以接好 gateway 入口，runner 平面很可能一并覆盖**——先证实这一点再决定要不要单独处理 runner，不要预设两套工作量。

### 一并处理的既有缺口

`repository/agent_run_queue.go` 的 `GetClaimedRun(runID, workerID, leaseToken)`（:201）与 `GetClaimedRunCheckpoint`（:316）**没有法人轴**，只按 `worker_id + lease_token` 绑定。

这是另一套信任模型（机器身份 + 租约），不是 SI2 修的那类跨法人用户问题，所以当时没纳入。但它是 runner 平面唯一的归属判据，**接线时必须明确回答**：worker 拿到的 run 是否可能跨法人、租约签发时法人是否已被约束、需不需要补第三条轴。**这一条动手前抛方案。**

### RT1-B 要求

- 归属语义照 `sessionmanager.PostgresStore.Load`，不另发明（SI1/SI2 都是照它做的，三处一致）
- 边界取自已解析的 scope，不接受调用方传入（D-C4）
- **机器断言 + 反向对照**：照 SI1 Part B 的 `SessionOwnerKind()` 做法，把接线退回去必须变红，否则断言恒真
- 跨法人拒绝保持 `scope_denied` 不软化
- 完成后更新索引 G9 状态

## RT1-C：streaming 边界窗口的如实登记

`handlers/ai_chat_runtime.go` 的 `StreamRunEvents` 非 worker 分支，`listEvents` 闭包在建流那一刻捕获 `entity`。SI2 的登记写的是「长连接期间权限变更不改变归属……不构成问题」。

**准确说法是：存在一个受连接寿命限制的暴露窗口**——scope 中途被收回的用户会继续收到事件直到重连。方向是安全的（不会跨到别人的法人），窗口也有界，但把它写成「不构成问题」是在断言一件没被证明的事。

另有一处描述低估了代码：登记说「每帧不重复检查」，实际 `listEvents` 每帧都把 `entity` 传进 `ListRunEvents`，是每帧都校验。

要做的：把这两处登记改成如实描述。**只改注释与交付登记，不改行为**——除非你认为该窗口需要收窄，那要单独提案，不要顺手改。

## RT1-D：两套治理链合一（依赖 RT1-B）

ACORE-2 的九个控制现在有两套实现：

- `agentkernel/governance`（15 处 `denyWith` 拒绝点）——chat 平面在跑
- `agentcore/hooks`（2 处 `Block: true` + 走 error 路径的策略拒绝）——**所有未汇流平面**的守卫

RC1 那一单被迫两边都改。每多一单碰治理链就多付一次利息。

**但现在不能合并**：未汇流的平面还靠旧链守着，此刻拆掉它等于拆掉唯一在跑的守卫。**RT1-B 让剩余平面都过新链之后，条件才成熟。**

RT1-B 验收通过后再规划本部分，届时单独提案：哪些控制可以直接删旧实现、哪些语义有分歧需要先对齐（RC1 已经暴露过一处：旧链的策略拒绝走 error 路径经 `policyErrorCode` 分型，新链走 `HookDecision` 经 `RejectSink` 带码，两条路径的错误码语义现在一致，合并时不要退化）。
