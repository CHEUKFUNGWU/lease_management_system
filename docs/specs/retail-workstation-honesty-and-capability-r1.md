## Problem Statement

站在集团 FP&A、大区财务 BP、门店经营分析师三类使用者的位置上，这个工作站目前有三类问题，严重性依次递减。

**第一类，界面在说假话。** `/performance` 的同群对标表里有一列叫「同群平均坪效达成率」，它渲染的是设备综合效率 `oee_pct`（取不到就退到产能利用率 `utilization_pct`）。这两个数与坪效没有任何关系。同一张表的门店副标题在字段为空时会兜底显示「核心商圈 · 标杆同群」，而底层字段是工厂代码与产线代码。使用者读到的是一个看起来完全合理的零售指标，实际上是工业制造字段换了个中文标题。这比"专业性硬伤"严重一个量级：它违反的是本仓最核心的一条纪律——**缺失数据显示「—」，不用 0、不用别的数字冒充**。

**第二类，做出来的能力没被看见。** 建议书判定「货」与「人」两个支柱严重缺位，代码实测推翻了大部分：

| 建议书判定 | 代码实测 |
|---|---|
| 品类只有静态只读占比图，无法下钻 | `services/margindecomposition` 已实现量/结构/价三效应逐品类拆解，接了 handler，`/store-360` 有 `CategoryCompositionPanel` 在消费 |
| 无进销存数据 | `services/inventorymetrics` 已实现 DOI 与周转率（含零分母返回 nil 的正确语义），`/store-360` 有 `InventoryTurnoverPanel` |
| 缺商圈竞对分析 | `services/competitorreference` + `/store-360` 的 `CompetitorBenchmarkPanel` 已在跑 |
| 人效只有一个总人工成本数字 | `retail-kpi-v1` 已定义 `sales_per_labor_hour` 与 `labor_hours_per_transaction`，含零分母 null 规则与必需字段声明；事实层 `retail_store_day_facts` 已有 `labor_hours` 与 `headcount` 两列。**只是 `retailstore360` 的 `summaryCodes` / `benchmarkCodes` 没把它们列进去，所以前端拿不到** |
| 促销无法衡量真实拉动 | `services/promotionattribution` 已实现基线 run-rate、增量营收、增量毛利、ROI，且基线不可得时返回 `baseline_unavailable` 而不是编一个数 |
| 科目树不可自定义，要手改 JSON | `finmodel/template` 已有完整公式 DSL：词法/语法分析、`lag(x,n)` 跨期引用、比较与条件、同期循环引用检测；`POST /api/v1/financial-model/templates` 已开放。**缺的是可视化编辑器，不是引擎** |

代价是真实的：BP 每天在 Excel 里手算已经在系统里跑着的东西，而这批能力的口径纪律（零分母、覆盖率、降级声明）恰恰是 Excel 给不了的。

**第三类，才是真缺口。** 去掉上面那些之后，剩下五项是代码里确实没有的：促销投前的保本增量销售额测算、新店可行性的业务侧测算（爬坡/回本期/IRR）、利润差异的因子归因、滚动预测的历史期自动滚入、公式与科目树的可视化编辑器。

## Solution

按三类问题的严重性倒序解决，不打包成一个大重构。

**止血**：把冒充的指标改成诚实呈现。设备口径的数据要么明确标为设备口径，要么在零售语境下显示「—」并说明原因。移除所有硬编码兜底文案。

**上架**：把已经算好但没露出的能力接到界面上，并为每一个补口径说明——使用者需要知道这个数是怎么算的、什么时候不可信。人效走 `retail-kpi-v1` 既有语义，一行公式都不新写。

**补齐**：五项真缺口按「是否需要新后端」分成两组。不需要的先做，需要的排在后面并明确各自的降级行为。

**全程贯穿一条纪律**：所有改动都是叠加。不删路由、不删 API、不删表、不摘导航项。`/performance` 与 `/operating-pulse` 的重叠是已知的产品问题，2026-08-22 已决定本轮不合并——本 spec 不碰它，只在两页各加一句互相指路的说明。

## User Stories

### 诚实性

1. 作为门店经营分析师，我希望「坪效」这一列显示的确实是坪效，这样我不会拿一个设备效率数字去跟店长开会。
2. 作为大区财务 BP，我希望系统在拿不到某个指标时明确显示「—」并告诉我为什么，这样我知道该去补哪份数据，而不是把一个假数字写进报告。
3. 作为集团 FP&A，我希望界面上不出现任何我无法追到来源的数字，这样我签字的时候知道自己在签什么。
4. 作为审计视角的使用者，我希望设备口径的数据如果要展示，就明确标为设备口径，这样零售分析与制造分析不会被混为一谈。
5. 作为任何一类使用者，我希望字段为空时不要用一个听起来合理的词（如「核心商圈」）填上去，这样我能分辨"没数据"和"数据是这个值"。

### 人效

6. 作为门店经营分析师，我希望在门店 360 看到销售人效（每工时产出多少销售额），这样我能判断这家店是不是人排多了。
7. 作为门店经营分析师，我希望看到单均工时（一笔交易平均占用多少工时），这样我能分辨是"人太多"还是"单太难成交"。
8. 作为门店经营分析师，我希望人效指标同样进同群对标，这样我知道 42 元/工时到底是好是坏。
9. 作为门店经营分析师，我希望在工时数据缺失时看到「—」而不是一个由人工成本倒推出来的估计值，这样我不会基于估计值去调排班。
10. 作为门店经营分析师，我希望系统明确告诉我时段级排班分析目前做不了以及为什么，这样我不会一直等一个不会来的功能。

### 已有能力的可见性

11. 作为大区财务 BP，我希望品类毛利拆解能告诉我这个品类的毛利变化里多少来自卖得多了、多少来自结构变了、多少来自毛利率变了，这样我知道该找采购还是找运营。
12. 作为大区财务 BP，我希望每个分析面板都带一句口径说明，说清分子分母是什么、什么情况下会降级，这样我不用去翻代码。
13. 作为门店经营分析师，我希望库存周转的 DOI 在销货成本为零时显示「—」而不是无穷大，这样表格不会出现看不懂的数。
14. 作为大区财务 BP，我希望竞对对标在样本不足时明确降级并说明样本数，这样我不会拿两家店的均值当商圈水平。
15. 作为店长，我希望门店利润流向桑基图继续存在并且能点开人工节点看全职/兼职构成，这样我不用懂财务也能看懂钱去哪了。
16. 作为店长，我希望桑基图上那行「平衡状态 · 未归因金额 · 公式版本」一直在，这样我知道这张图有没有藏东西。

### 促销

17. 作为大区财务 BP，我希望在活动申请阶段就能算出「这次活动至少要多卖多少才不亏」，这样我能在批之前给业务一个数。
18. 作为大区财务 BP，我希望保本测算的输入是我手上有的东西（折扣率、推广费、基线销售额、基线毛利率），这样我不用先去凑一堆数据。
19. 作为大区财务 BP，我希望投前测算和投后复盘用的是同一套毛利口径，这样两个数能对上。
20. 作为经营分析师，我希望投后复盘在找不到可比基线时明确说找不到，而不是拿活动期自己当基线，这样我不会得出"活动增量 100%"的荒谬结论。

### 新店测算

21. 作为大区财务 BP，我希望新店测算的输入包含商圈客流、进店率、转化率、客单价、营业天数，这样销售额预测是推导出来的而不是拍出来的。
22. 作为大区财务 BP，我希望能输入装修与设备的一次性投入、首批铺货资金、免租期和开业爬坡月数，这样测算贴合真实开店节奏。
23. 作为大区财务 BP，我希望自动得到静态回本期、动态回本期、内部收益率、净现值和盈亏平衡销售额，这样立项报告不用我在 Excel 里再算一遍。
24. 作为大区财务 BP，我希望新店测算里的租金部分和 IFRS 16 那边算出来的是同一个数，这样两份报告不会打架。
25. 作为大区财务 BP，我希望在折现率没确定时系统拒绝给出 IRR 和 NPV 并告诉我缺什么，而不是用一个默认值算出来，这样我不会拿默认值去做投资决策。
26. 作为大区财务 BP，我希望测算结果能一键存成一份带输入假设的底稿，这样三个月后有人问起我能复现。

### 因子归因

27. 作为集团财务总监，我希望门店利润下滑时能在一屏内看到是客流、客单价、毛利率还是费用造成的，这样我不用等下属查两天。
28. 作为经营分析师，我希望归因结果以瀑布图呈现且各因子加起来等于总差异，这样我知道没有东西被漏掉。
29. 作为经营分析师，我希望分解方法（连环替代的替代顺序）在界面上写明，因为换个顺序数字就变了，这样我能向别人解释为什么是这个数。
30. 作为经营分析师，我希望无法归因的部分显式列为「残差」而不是被摊进某个因子，这样我知道这个解释有多完整。
31. 作为经营分析师，我希望任一因子所需的事实缺失时，整个归因降级为不可用并指出缺哪一项，这样我不会拿半个解释去汇报。

### 滚动预测

32. 作为集团 FP&A，我希望设定实际数截止期后，截止期之前的行自动读真实事实、之后的行才跑假设，这样我不用每月手工搬数。
33. 作为集团 FP&A，我希望同屏对比实际、最新预测、原始预算、去年同期四条线并自动算出差异额与达成率，这样月度会不用做四份表。
34. 作为集团 FP&A，我希望审批过的预测版本能打快照锁死，这样后面没人能悄悄改掉已经上报的数。
35. 作为集团 FP&A，我希望模拟数据的 run 不能被发布为计划版本，这样演示数据不会混进正式预算。

### 公式与科目树编辑

36. 作为集团 FP&A，我希望在界面上点选科目、拼公式，而不是手写 JSON，这样我不用为了改一行预测逻辑去找工程。
37. 作为集团 FP&A，我希望公式写错时在保存前就报错并指出错在哪个位置，而不是提交后 run 失败，这样我改得快。
38. 作为集团 FP&A，我希望循环引用被当场拒绝并显示引用链路，这样我知道该断哪一环。
39. 作为集团 FP&A，我希望能引用上一期的值（如上期期末存货），这样存货、应收应付这类滚存科目能建模。

### 文案

40. 作为任何一类使用者，我希望界面上不出现后端枚举值（`queued`、`insufficient_peers`、`production`），这样我不用猜它是什么意思。
41. 作为任何一类使用者，我希望百分比变动明确区分「百分点」和「百分比」，这样毛利率从 30% 到 31% 不会被写成 +3.33%。
42. 作为任何一类使用者，我希望界面文案不出现内部路线图词汇（批次号、阶段号、模块代号），这样我读到的是业务语言。
43. 作为任何一类使用者，我希望每个数字旁边都能查到它的口径说明，这样我不用猜「经营占用成本」包不包含物业费。

### 增量叠加纪律

44. 作为这个仓库的维护者，我希望所有既有路由在本批次之后仍然可访问，这样不会有人的书签失效。
45. 作为这个仓库的维护者，我希望 `/roi` 这类定位不清的页面得到一句明确的定位说明而不是被偷偷删掉，这样后来的人知道它为什么在这儿。
46. 作为这个仓库的维护者，我希望 `/performance` 与 `/operating-pulse` 的重叠在两页都有一句说明指向对方，这样使用者知道该去哪一页，而合并决策仍然可以以后再做。

## Implementation Decisions

### D-R1：设备口径数据的处理方式是"标注"，不是"删除"

`equipment_assets` / `equipment_operating_facts` 两张表、`access_scope_sql.go` 的工厂/产线/设备三层权限过滤、`fpna_plan_lines` 的 `plant_code` / `production_line_code` / `equipment_id` 三列都在被使用，且 [AI 文档索引 §0](../AI_文档索引与现行决策.md) 已定「制造/设备维度保留供将来评估，不进排期、不作为架构约束」。删除会牵动权限层与 FP&A 计划行，收益却只是移除一个没人访问的页签。

因此本批次只改**展示层**：`/performance` 的同群对标表在零售语境下不再渲染 `oee_pct` / `utilization_pct`，改为按门店口径展示真实可得的对标指标；若该数据源当前只有设备事实，则整块降级为具名空态并说明「本期无门店同群对标数据」。表结构、API 契约、权限过滤一律不动。

### D-R2：人效上架靠扩列表，不写新算法

在 `retailstore360` 的 `summaryCodes` 追加 `sales_per_labor_hour`、`labor_hours_per_transaction`、`headcount`；在 `benchmarkCodes` 追加 `sales_per_labor_hour`。同步在同文件的 `labels` 映射补中文名（与 `retailkpi` 的 `零售指标中文名` 表保持一致，不另起译名）。

零分母与缺失语义完全复用 `retail-kpi-v1`：`labor_hours` 为 0 或缺失时 `sales_per_labor_hour` 返回 nil，前端渲染「—」。**不得从 `labor_cost` 除以某个时薪反推工时**——那会造出一个看起来是事实的估计值。

时段级排班分析不在本批次：事实层粒度是 store-day，`AGENTS.md` 明令新增经营指标一律走 store-day 事实。这一点要在人效面板上写成一句面向用户的说明，不是留白。

### D-R3：促销投前测算是纯函数，进 `promotionattribution` 同包

保本增量销售额的定义在本 spec 内钉死，避免实现时各写各的：

```
设：
  baseline_revenue      活动期若无活动的预计销售额（沿用投后复盘的同一 run-rate 基线口径）
  baseline_margin_rate  基线综合毛利率
  promo_margin_rate     活动期实际边际毛利率（= 折后毛利 / 折后销售额）
  fixed_marketing_cost  活动固定投入（推广费、物料、平台服务费）

保本增量销售额 =
  ( fixed_marketing_cost + baseline_revenue × (baseline_margin_rate − promo_margin_rate) )
  ÷ promo_margin_rate
```

分子第二项是"原有销量因让利而少赚的毛利"，分母是"每多卖一元能赚回的毛利"。`promo_margin_rate ≤ 0` 时返回 `unachievable`——让利后边际毛利非正意味着卖得越多亏得越多，此时不存在保本点，**不能返回一个巨大的数字假装有解**。

基线口径必须与 `promotionattribution.Attribute` 使用的 run-rate 同源，否则投前投后两个数对不上（User Story 19）。

### D-R4：新店可行性测算是新服务，但租金部分只做只读投影

新增 `services/newstorefeasibility`（纯函数 + Ports，照 `finmodel` 的形状）。

输入分三组：业务侧（商圈客流、进店率、转化率、客单价、营业天数、综合毛利率）、投资侧（装修设备一次性投入、首批铺货、爬坡月数与各月爬坡系数）、租约侧（基本租金、抽成扣率、免租期、租期）。

输出：逐月经营现金流、静态回本期、动态回本期、IRR、NPV、盈亏平衡销售额。

**租金与 IFRS 16 影响不自算。** 与 `finmodel` 同纪律：`newstorefeasibility` 禁止 import `ifrs16`，租赁侧数字通过 Port 从 `measurement_results` 只读投影取。这条要有 import guard 测试，照 `finmodel/importguard_test.go` 的写法（遍历全部子包，不只根包）。

**折现率缺失时 fail-closed。** IRR / NPV / 动态回本期三项返回具名 Gap，不使用任何默认折现率。这是 `AGENTS.md`「AI 不得猜测折现率」纪律在测算侧的对应物（User Story 25）。

### D-R5：因子归因用连环替代法，替代顺序写进契约

分解链固定为：`销售额 = 客流 × 转化率 × 客单价`，`毛利 = 销售额 × 毛利率`，`门店经营利润 = 毛利 − 人工 − 经营占用 − 其他可控`。

替代顺序固定为 **客流 → 转化率 → 客单价 → 毛利率 → 人工 → 经营占用 → 其他可控**，顺序作为响应字段 `decomposition_order` 返回，前端必须展示。连环替代法的结果依赖顺序，不声明顺序的归因数字无法被复核（User Story 29）。

各因子之和与总差异的差额显式返回为 `residual`，**不摊进任何因子**。`residual` 与总差异之比超过阈值时，响应带 `residual_material = true`，前端据此提示解释完整度不足。

> **更正（2026-08-23，实现时发现本节原有一处概念错误）**
>
> 本节原先同时要求两件互斥的事：用连环替代法（因此必须声明替代顺序），以及让 `residual` 承载有意义的高阶交叉项。**这两者不能同时成立。**
>
> 精确连环替代下，各步贡献是望远镜和：`C₁ = S₁ − S₀`、`C₂ = S₂ − S₁`、…、`C₇ = S₇ − S₆`，求和后中间项全部抵消，得 `S₇ − S₀`，**恒等于总差异**。所以 `residual ≡ 0`，只承载浮点噪声。手算验证：基期利润 4000、当期 2900、总差异 −1100，七步贡献 `+600, −660, +1485, −2475, −200, +100, +50` 之和精确等于 −1100，残差 0。
>
> 残差只在**隔离替代法**（每个因子单独从基期变动、其余保持基期）下才非零，而那种方法的结果与顺序无关、也就不需要声明顺序。两种方法二选一。
>
> **本 spec 选连环替代**，因此：
> - `residual` 字段**保留**，但它是构造性质而非检查对象，取值恒为浮点噪声级别；
> - `residual_material` 仍然保留并测试，它防的是将来有人把实现换成近似解法而不改契约；
> - **真正的验证对象是逐步替换的中间值序列与顺序敏感性**，不是守恒等式。守恒等式在此实现下恒真，按 `AGENTS.md` 风险红线 12 属于「拿定义式倒减自己」，不得作为检查。

任一必需事实（客流、转化率、客单价、毛利率、三项费用）在基期或当期缺失，整个归因返回 `unavailable` 并列出缺失项，不做部分归因。

复用 `services/margindecomposition` 已有的量/结构/价三效应实现作为品类层的下钻，不重写。

### D-R6：滚动预测的自动滚入复用 `ActualCutoffPeriod`，不新建概念

`finmodel` 的引擎已经在按 `def.ActualCutoffPeriod` 区分冻结线左右（左侧声明了 `actual_source` 的行读事实、右侧跑驱动公式）。滚动预测不是新机制，是**在 `/fpna-workbench` 上把这个已有字段暴露成可操作的滚动动作**：选定新的截止期 → 生成新版本定义 → 承继假设 → 跑 run。

四线对比（实际 / 最新预测 / 原始预算 / 去年同期）走 `fpna_plan_versions` 已有的 prior 谱系与 `scenario_type`。快照锁定复用既有 publish 路径，**`data_classification` 为 `simulated` 或 `mixed` 的 run 不得 publish**（底线 2，已有约束，不得绕过）。

### D-R7：公式编辑器是前端，引擎不动

`finmodel/template` 的 DSL 引擎已完整（词法、语法、`lag(x,n)`、比较与条件、同期循环引用检测 `validateNoCycles`）。本批次只做编辑器 UI：科目行点选插入引用、公式实时校验、错误定位、循环引用链路展示。

**校验必须调后端。** 前端不复刻一套解析器——两套解析器必然分叉，届时"界面说没问题、保存时报错"会比现在更难查。做法是新增一个 dry-run 校验端点（`POST /api/v1/financial-model/templates/validate`），复用 `template.Compile` 的同一条路径，返回错误类型、位置与循环链路。

这与「公式行与小计行由后端同一 AST 求值，前端不得重算任何模型行」是同一条纪律的延伸。

### D-R8：两页重叠只加互指说明

`/performance` 与 `/operating-pulse` 各加一条 `Alert`（`type="info"`，不是警告色），说明本页侧重什么、另一页侧重什么、以及"两页数据来自不同后端，数值口径可能存在差异"。不合并、不下线、不改后端调用（2026-08-22 决定）。

`/roi` 加同类说明：这是一个内部的系统投入产出测算工具，不是门店经营分析；并补一条守卫测试断言它不在导航项里（现状即如此，测试是防回归）。

### D-R9：文案层的机器可强制约束

三条守卫，都要能被 CI 跑：

1. **枚举不裸奔**：源码级断言，禁止 `{x.status}` / `{x.kind}` / `{x.*_status}` 形态直接出现在 JSX。映射表用 `Record<联合类型, i18n键>`，漏一个后端值 TypeScript 编不过。这条已在 `/financial-model` 有先例（`page-enums.test.ts`），本批次推广到 `/performance`、`/promotions`、`/store-360`。
2. **pp 与 % 不混用**：断言凡渲染 `ChangeType === "percentage_point"` 的值必走 `pp` 后缀格式化函数。
3. **内部词汇不外泄**：对 i18n 值做黑名单断言（批次号形态、阶段号、模块代号）。

## Testing Decisions

### 什么算好测试

只测外部可观察行为：给定输入，函数/端点/组件产出什么。不测私有函数名、不测调用次数、不测中间状态。

本仓已确立的自检句沿用：**把被测行为改错或删掉，这条测试会不会红？不会红就是没写对。** `AGENTS.md` GUARD-001 对替换类改动的要求同样适用——只证明旧行为消失不算数，必须证明新行为生效。

### 反向测试要求

因子归因的守恒断言（各因子 + residual = 总差异）**在连环替代下恒真**，见 D-R5 的更正说明：望远镜和使它成为构造性质，不是检查。按 `AGENTS.md` 风险红线 12 的要求，它**已降级为构造断言**并在此注明。

替代它的检查是两条，都必须先红后绿：

1. **中间值序列逐格锁定**：固定 fixture，每一步替换后的中间利润与手算值逐格比对。把累计替代改成隔离替代（`prev = now` 去掉），这条立即红。
2. **顺序敏感性**：换一个替代顺序，同一因子的贡献值必须随之改变，且 `decomposition_order` 回显新顺序。这条独立于第 1 条，防的是「顺序字段只是装饰、实现根本没用它」。

## 交付后的决策与遗留（2026-08-23，R 批次收口）

### 已决

**IRR 与 NPV 保持月率口径，不加年化换算层。** 现状：后端字段 `irr_monthly`，界面标签「内部收益率（月）」/ `IRR (monthly)`，盈亏平衡销售额同样标「（月）」；NPV 不带期间限定，因为它是绝对金额不是比率。

理由：月率 IRR 年化不是乘 12，是 `(1+r)^12 − 1`。加一层换算就多一个会写错的地方，而写错的年化 IRR 比诚实的月率 IRR 危险得多——前者看起来像个可以直接拿去比较的行业标准数字，后者的标签逼着读者去想口径。当前命名自带口径声明，读者不会误读。

财务侧若确实按年化习惯汇报，重新进入条件是：先确定年化定义（几何年化还是简单年化）并写进本节，再加换算层，且两个数并列显示而不是替换。

## Further Notes

**建议书的排期不可用。** 它按 2026-Q3 起算「阶段 0 一周」，但今天已是 2026-08-22，Q3 剩不到六周；且团队是一位人类 + AI 协作者（`docs/AI_文档索引与现行决策.md` §6），没有可并行的第二条人力线。本 spec 不给日期排期，只给依赖顺序：诚实性止血 → 人效上架与口径说明 → 需新后端的四项（彼此独立，可任意顺序）→ 公式编辑器（依赖校验端点）。

**建议书的两份副本要合并。** 仓库根目录与 `docs/` 下各有一份同名文件（`UIUX与产品能力全面改善建议书.md`），内容重复。保留 `docs/` 下那份，根目录那份删除——这是文档去重，不属于「不得删除既有功能」的范围。

**杜邦这个词在建议书里用得不准。** 杜邦分析是把净资产收益率拆成利润率 × 周转率 × 权益乘数，是资本回报的分解。建议书 §5.2 描述的是门店利润差异的因子分解（客流 / 转化 / 客单价 / 毛利率 / 费用），那是连环替代法的差异分析，不是杜邦。界面文案统一叫「利润差异归因」，不叫杜邦——用户里有真的懂杜邦的人，叫错会失去信任。同理，建议书标题说「五因素」但公式列了六项加残差，本 spec 按七因子 + 残差定义。

**保留桑基图这条不需要争论。** 建议书 §2.4 把它单列为"核心资产保护纪律"，实际上「不得删除既有功能」已经覆盖了。它的三项增强（节点下钻、跨页复用、异动唤起 AI）是真需求，但优先级低于本 spec 的前三类问题——放在能力补齐之后。

**关于 IFRS 16 的定位表述。** 建议书通篇把清理租赁模块作为"回归零售"的手段。这个方向与 `docs/AI_文档索引与现行决策.md` §0 一致（IFRS 16 是次要 value-added 模块），但手段不一致——那份文档同时写明「IFRS 16 在 AI 设计中的角色是被保护对象。保护它，不是围绕它做产品」。降权 ≠ 拆解。本 spec 对租赁侧零改动。

**验证状态措辞不得放松。** 本批次全部能力仍只有固定 seed 的内部验证，无真实 POS/ERP 联调、无客户验证。任何交付报告与对外表述保持 `unvalidated`；IFRS 16 回归标准答案仍为 `pending_third_party_review`，不得表述为审计背书。
