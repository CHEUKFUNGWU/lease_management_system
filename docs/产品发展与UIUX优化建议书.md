## 0. 执行摘要

**一句话总评:骨架已是产品,皮肉还是作品。控制框架和 AI 入口已达到可售卖的差异化水位,但披露、外币、demo 最后一公里三处短板,会分别在审计师、CFO、销售演示三个关键场景穿帮。**

四视角各一句话判断:

| 视角 | 判断 |
|------|------|
| **财务核算/审计** | 三级审批 + SoD + 期间锁 + Working/Official 双模式已达审计级控制框架,同类工具中罕见;但**披露附注缺失、外币记账断链、分录无红冲**三项硬伤,使系统尚不能独立支撑一次真实年审 |
| **财务 BP** | BP 要的是"贴着业务出数":门店级租赁成本、租售比、有效租金、陪谈判的情景测算——目前系统**连面积字段都没有**,业务切片(品牌/区域)权限模型已备但无成品报告,BP 拿到数据仍要回 Excel 二次加工 |
| **FP&A** | 日级计量底座和付款成分模型是优质数据资产,但产品停在"子账"层——**没有预算/实际对比、没有续租决策模型、现金流预测未折现**,从"记账工具"到"预测决策工具"是客单价跃迁点 |
| **产品经理** | AI 对话式入口是真差异化资产(SSE 流式、草稿卡片、人机协同红线),但**仪表盘趋势图永久空白、全局搜索是摆设、通知铃铛不通、i18n 半成品**——这些"最后一公里"缺陷会在 15 分钟 demo 内被发现,严重稀释前面 90% 的工程质量 |

**若只能做三件事**:① 修复 demo 穿帮点(死 UI 三件套 + 金额化仪表盘,约 1–2 周);② 做出 IFRS 16 披露附注报表(数据已全在 `measurement_results`,只差打包,审计价值极高);③ 把 20 用例回归报告送第三方会计师复核,拿掉 `pending_third_party_review` 水印。

## 2. 财务核算与审计视角 — 合规与审计就绪度

> 视角说明(v1.2 更正):合规、分录、披露、审计应对是**财务核算(Controller)与审计条线**的关注点,不是财务 BP 的本职——BP 贴着业务做决策支持,其视角见第 3 章。本章内容保留不变,仅归位。

评审方法:模拟年审场景,按"审计师会怎么问"逐项检验。控制框架(SoD、锁账、审计日志)已经过关,以下是会被问倒的地方,按严重度排序。

**先明确一个定位定性:月结与分录不是可选功能,而是 IFRS 16 定位的交付物本身。** 没有分录,计量结果只是计算器输出(财务用户每月真正拿走的是可入账的三笔分录);没有月结,数字就没有"定版"概念(审计师问的是"3 月 31 日报出去的数、谁批的、之后改没改过"),Working/Official、期间锁、SoD 这套控制叙事全部挂在月结流程上。同时守住边界——本系统是**租赁子账(subledger),不是总账**:

| 属于本系统(租赁子账) | 不属于本系统(客户的 ERP/总账) |
|---|---|
| 生成租赁相关分录(利息/折旧/付款/豁免费用/事件调整) | 记全公司的账 |
| 租赁期间的锁定与红冲 | 总账层面的结账 |
| 分录导出 + 凭证号回写 | 试算平衡、财报合并 |
| 租赁科目的映射配置 | 维护完整科目体系 |

对运营/地产买家,月结模块应保持不可见——他们用合同库和提醒,不应被会计流程打扰。

### 2.1 缺 IFRS 16 披露附注(最高优先)

**审计师会问**:"给我租赁负债的到期分析(maturity analysis)、当期短期/低价值豁免费用总额、变量租金费用、ROU 按资产类别的期初期末调节表。"

**现状**:全部答不出成品。具体断点:

- 无按时间带(1 年内 / 1–5 年 / 5 年以上)的**未折现租赁承诺表**。`/reports/cashflow-forecast` 是按到期日分组的未折现现金流,离披露口径只差"时间带分组 + 与账面负债的折现调节"一步。
- `/reports/liability-rolling` **名不副实**——返回的是合同列表而非期初/期末滚动调节。真正的滚动数据在 `/reports/amortization` 和 `measurement_results` 里已经齐全,只是没有打包成披露件。
- 范围闸门做了豁免费用的**计量**(引擎已单列豁免费用、变量租金、非租赁费用三列),但没有做豁免费用的**披露汇总**——这恰是 5 月方案 A.4 明确要求的"又一个客户买单理由",做了上半场没做下半场。

**建议动作**:新增"披露报表"模块(`reports.go` 新 endpoint + 前端报表页新 Tab),产出五张表:① 负债到期分析(含未折现→折现调节);② ROU 按资产类别期初期末调节;③ 负债滚动调节(期初 + 新增 + 利息 − 付款 ± 重计量 = 期末);④ 费用分解(折旧/利息/短期豁免/低价值豁免/变量租金);⑤ 现金流出总额。**数据零缺口,纯打包工作,是全项目投入产出比最高的一项。**

到期分析的分带口径:**默认出细带——1 年内 / 1–2 年 / 2–3 年 / 3–4 年 / 4–5 年 / 5 年以上**,不出"1–5 年"粗带。理由:① 细带聚合成粗带是无损加法,用户需要"1–5 年"口径自行合并即可,反之不可逆;② IFRS 16 本身不规定分带(交管理层判断),而 **ASC 842 要求未来五年逐年披露 + 之后合计**——细带口径一份数据同时满足两套准则,与多准则产品线呼应;③ 日级引擎切任意时间带零成本。

配套交付一份**可导出的验证底稿 Excel**(复用前端已有 xlsx 能力),三层结构:合同级明细(每份合同 × 每个时间带的未折现现金流)→ 时间带汇总 → 调节表(未折现总额 − 未确认融资费用 = 账面租赁负债)。定位不是"数据导出"而是**审计底稿**:让每个披露数字都能下钻到合同——"披露可下钻"正是 Excel 作坊做不到的,底稿本身即售前材料。

### 2.2 外币记账是断链的(高优先)

**审计师会问**:"这份美元租约的分录为什么是 CNY?期末负债用什么汇率重估?折算差异进哪个科目?"

**现状**:`currency` 字段贯穿合同/付款/分录/法人主体,但只是"存了没用"——计量引擎不换算;**`monthly_closing.go` 生成分录时币种硬编码 `"CNY"`**,外币租约会直接出错账;无汇率表、无期末重估、无折算损益;报表层仅有一个手工传入 `exchange_rate` 参数的平乘。回归清单里的 TC-17(多币种)也因此没做。

**建议动作**(分两步):第一步(止血)月结分录币种改为跟随合同币种,外币合同在月结时给出"本系统暂按原币出具,折算由总账处理"的明示,避免错账;第二步(闭环)增加 `exchange_rates` 表 + 期末负债按收盘价重估 + 折算损益分录,并补 TC-17 回归用例。目标客户若含港资/外资连锁(zh-HK 语言包暗示了这一点),此项会从 P1 升级为 P0。

### 2.3 过账后无红冲/更正路径(高优先)

**审计师会问**:"上月过账后发现一笔分录错了,系统里怎么更正?"

**现状**:schema 定义了 `reversed` 状态但**无红冲端点**;前端月结页"驳回分录 / 红冲"按钮是 `coming soon` 占位。目前唯一路径是解锁期间重新生成——这会破坏"锁账不可变"的控制叙事,审计师最反感的就是"改错靠解锁重跑"。

**建议动作**:实现分录红冲端点(生成一笔反向分录并关联原分录,原分录标记 `reversed`,双双留痕),前端按钮接通。工作量不大,但它是控制故事的完整性拼图。

### 2.4 重计量不会推导修订付款流(中优先)

**现状**:`event.go` 的重计量逻辑中 `revisedPayments := payments` **原样复用现有付款计划**——只有 renewal/early_termination 会调整租期终点;rent_change、index_update、area_adjustment 等事件虽被正确分类为 modification 并生成调整分录,但**修订后的付款流需要用户先手工改付款计划**,系统不会从事件参数自动推导。`is_index_adjusted` 字段和 `index_update` 事件类型都存在,但没有自动指数重算引擎。

**为什么重要**:零售租约最常见的变更就是"每年按 CPI/固定比例调租"。目前的操作路径(先手工改付款计划、再录事件、再重算)既繁琐又易错——两步之间没有一致性校验,改了付款没录事件、或录了事件没改付款,都会产生错误重计量。

**建议动作**:事件录入时让事件携带结构化参数(如"自 X 日起租金 +5%"/"CPI 指数从 a 到 b"),由系统生成修订付款流草稿供确认,替代手工改表;这同样是 AI 录入的好落点(landlord notice 解析 → 事件草稿 → 付款流草稿已在需求文档 3.1 的链路清单里)。同步补充:重计量目前只计 P&L gain 不计 loss(`PnLLoss` 字段未被引擎赋值),需补全。

### 2.5 折现率治理偏薄(中优先)

**现状**:单一年化平价;解析优先级为 覆盖参数 → **全局设置** → 合同自带利率 → 最近计量结果 → 硬编码 0.05。两个问题:① 全局设置优先于合同利率的顺序值得商榷(合同层的具体 IBR 通常应优先于集团缺省价);② 0.05 兜底与"AI 不得猜折现率"的红线精神相悖——引擎侧不应有静默缺省。建议:合同利率优先、去掉硬编码兜底(缺失即阻断并走 `discount_rate_missing` 流程,与 AI 侧口径拉齐);中期再考虑按租期期限分层的 IBR 利率表(版本化、留痕),这也是审计师核折现率时的标准问法。

### 2.6 其他合规清单

| 项 | 现状 | 建议 |
|----|------|------|
| 过渡方法 | 无(仅 go-forward 新租赁) | P3。新客户导入存量租约组合时必须有修正追溯支持,做平台化销售前补 |
| 回归覆盖 | 20/25 用例,缺多币种、转租等 | 随 2.2/2.4 落地同步补 TC-17、TC-23 |

| CORS | ai-service `allow_origins=["*"]` | 生产部署前加固,连同 JWT 存储方式一起处理(见 4.6) |

## 3. 财务 BP 与 FP&A 视角 — 从子账到业务决策支持

现状定性:**这是一个做得不错的"后视镜"(记账、合规、追溯),但业务侧财务要的是"挡风玻璃"(预算、预测、决策)。** 日级引擎 + 付款成分模型 + 事件驱动架构意味着底座完全够格支撑决策层,缺的是产品面。这是抬高客单价、把买家从财务经理升级到 CFO 的关键路径。

本章覆盖两个相邻但不同的角色:**FP&A 管计划口径**(预算、预测、差异,3.1 / 3.3 / 3.5),**财务 BP 管业务口径**(陪业务做续租/开店/谈判决策、按业务视角出数,3.2 / 3.4 / 3.6–3.8)。BP 视角对产品有一个独特要求:输出必须是**业务语言**(这家店贵不贵、该不该续、谈到什么价合适),而不是会计语言(负债、ROU、折现)。

### 3.1 预算/实际对比(Budget vs Actual)— FP&A 第一刚需

租赁费用通常是零售企业第二大成本项。FP&A 每月要回答:"租赁成本比预算高/低多少,为什么?"目前系统只有"实际",没有"预算"概念。

**建议**:最小版本不需要完整预算模块——把某时点的计量快照(如年初锁定的 forward schedule)固化为"预算版本",每月月结后自动出"预算 vs 实际"差异,并利用事件驱动架构自动归因:差异 = 新签合同 + 续租/终止 + 租金变更 + 汇率 + 其他。**事件驱动引擎让"差异自动归因"成为可能,这是 Excel 和多数竞品做不到的**,应作为 FP&A 卖点主打。

### 3.2 续租决策支持 — 把关键日期从"提醒"升级为"决策"

平台化的最高价值卖点是关键日期预警(不错过续租/break 窗口)。但提醒之后呢?业务真正要做的决策是"续不续、按什么条件续"。

**建议**:在关键日期触达时附带一张"续租决策卡":当前租约剩余承诺、续租情景 vs 不续租情景的现金流与 P&L 影响对比(复用敏感性分析引擎,把冲击变量从折现率扩展到租期/租金)、该门店的租金占坪效比重(需接入或手工录入门店营收)。这把系统从"财务合规工具"推进到"地产团队谈判工具",直接服务 5 月方案定义的第二类买家。

### 3.3 现金流预测升级

现状 `/reports/cashflow-forecast` 是未折现、按到期日分组的租金流水。FP&A 口径需要:① 与资金管理对接的**十三周/月度滚动现金流出**视图;② 与 2.1 披露件共用的**到期阶梯**(1 年内/1–5 年/5 年+);③ 情景叠加——"若 30% 到期店续租、10% 关店"的组合级现金流(把敏感性从单合同扩展到组合,是现成引擎的循环调用)。

### 3.4 新租赁预演(Pipeline)

拓展团队谈新店时,财务要回答"这个租约签下来对报表的影响"。现状必须建正式合同草稿才能算。**建议**:提供"模拟合同"轻量入口(不进台账、不进审批,仅计量预览),或在 AI Chat 中直接支持"帮我算一下这组条款的首年费用与负债"——工具已齐(计量引擎 + AI 解析),只差一个不落库的调用路径。这也是 demo 中打动 CFO 的高光环节。

### 3.5 管理报表输出

CSV 对 FP&A 是"半成品"——最终都要贴进 Excel/PPT 汇报。建议:① 报表导出补 XLSX(前端已引入 `xlsx` 库,摊销表已有 Excel 导出,补齐其余报表即可);② 中期做"月度租赁管理报告包"一键导出(KPI + 滚动 + 差异归因 + 到期预警,PDF/PPT),这类"CFO 拿去就能汇报"的成品是订阅续费黏性的重要来源。

### 3.6 门店/资产级租赁成本视图与租售比 — BP 的日常语言

BP 陪业务复盘时的第一个问题永远是:"**这家店的租金贵不贵?**"回答需要两个分母:面积(每平米月租)和营收(租售比 rent-to-sales)。现状是两个分母都没有:

- **schema 里没有面积字段**——`stores` 表只有 code/name/brand/region/address,`lease_contracts` 也无面积。5 月方案组合分析里"每平米成本"的愿景,目前缺数据前提,组合分析页只能按合同总额说话。
- **没有营收数据**——租售比是零售租赁决策的第一指标(健康线通常 15%–20% 以内,超线即警示),系统完全无从计算。

**建议动作**(分两步):第一步加 `area_sqm` 字段(stores 或合同层,含 AI 解析时顺带抽取——租赁面积几乎每份合同都写),组合分析和门店视图即可输出每平米月租、同品牌/同区域单价对比,**改动极小,BP 价值立现**;第二步开营收接入通道(先手工月度上传 Excel 即可,不必等 API 集成),点亮租售比与"租金侵蚀毛利"预警。

### 3.7 有效租金与谈判支持 — 陪 BP 上谈判桌

业务拿到两个报价:A 方案免租 6 个月但年递增 5%,B 方案无免租平租——哪个划算?这是 BP 最常被抓去算的账,也是 Excel 最容易算错的账。而系统的计量引擎天然会算:把任意条款组合折算成**有效租金(effective rent)**——直线化月均租金、每平米有效单价、全租期现金流现值。

**建议动作**:做一个轻量"条款比价"工具(可作为 3.4 模拟合同的一个视图,或 AI Chat 的一个技能):输入 2–3 组报价条款 → 输出有效租金对比表 + 现值差异 + 一句话结论。配合 3.6 的同商圈/同品牌单价基准,BP 从"回去算算"变成"当场给答案"。**这是把会计引擎翻译成业务语言的最短路径,也是对地产/拓展买家最锋利的单点卖点。**

### 3.8 业务汇报出数 — 按业务口径一键成品

BP 的隐性痛点:每次经营分析会,都要把财务系统的数据按**业务口径**(品牌、区域、事业部)重切一遍,再手工做成对比页。系统其实已备了一半:`user_data_scopes` 权限模型支持品牌/区域切片,报表有 store/tag 视图。差的是"成品化":

**建议动作**:在报告包(3.5)中增加"业务视角"模板——按品牌/区域的租赁成本汇总与同比环比、Top 10 高租金门店、租金占比异常清单(3.6 落地后)、即将到期需业务表态的合同清单。让 BP 开会前 5 分钟出一份能直接投屏的东西,这是 BP 角色对工具产生日常依赖的方式。

## 4. 产品经理视角 — UIUX 评审与优化

总评:**工程质量高于产品完成度。** AI Chat、审批流、骨架屏这些"难的"做得好;死 UI、i18n、批量操作这些"简单的"反而拖后腿。以下按"对 demo/采纳的伤害程度"排序。

### 4.1 死 UI 三件套(P0,demo 会穿帮)

| 问题 | 现状 | 建议 |
|------|------|------|
| 仪表盘"负债趋势"图 | 永久空占位(`DashboardCharts.tsx` 硬编码 Empty,从未接数据),占仪表盘 2/3 宽的黄金位置 | 接 `/reports/amortization`(月度粒度、summary 视图)画负债+ROU 双线趋势;数据现成,半天工作量 |
| 顶栏全局搜索(⌘K) | 纯装饰,无任何 handler | 最小实现:搜合同名/门店/出租方,跳转合同详情;中期升级为命令面板(搜页面+搜合同+快捷动作) |
| 通知铃铛 | 静态红点,无下拉、无数据 | **这不是小事**:critical_dates 预警是平台化定位的最高价值卖点,后端 `/lease-admin/critical-dates/upcoming` 已存在,铃铛不通等于把核心卖点藏起来。接通:下拉列表(逾期红/临近黄)+ 跳转合同,后续再加邮件/站内信触达 |

**这三项是"卖点已建成、临门一脚没踢"的典型,合计约 1–2 周工作量,建议最先做。**

### 4.2 仪表盘金额化(P0)

现状 4 个 KPI 卡全是合同**数量**(总数/已批/待批/草稿)。财务系统的首屏应该说钱:建议改为 总租赁负债、总 ROU、本月租赁费用(利息+折旧)、未来 12 个月现金流出,数量类指标降级为次行小字。配合 4.1 的趋势图,首屏才成立"这是给 CFO 看的系统"。

### 4.3 信息架构:从"按功能分页"到"按任务收敛"(P1)

现状 12+ 个侧栏入口按功能切分,审批散落在合同详情、事件、月结各处。两个收敛建议:

- **"我的待办"**:审批角色(reviewer/approver)登录后应一眼看到"有几件在等我"——待审合同、待审事件、待批分录、临近关键日期,收敛为一个待办页(或仪表盘首屏模块)。审批类系统的日活入口就是待办,现状用户要逐页翻找。
- **报表导航收敛**:reports / cashflow-forecast / portfolio / sensitivity / standards / roi 六个并列入口太散,建议收敛为"报表中心"一个入口 + 内部页签,给披露报表(2.1)预留位置。

### 4.4 表单与录入体验(P1)

- **新建合同**:15 字段单页长表单,无分组向导、无草稿保存。建议:要么做 3 步向导(基本信息 → 租金与折现率 → 范围判定),要么顺应自身产品哲学——**把 AI Chat 入口在新建页顶部显性化**("上传合同,让 AI 帮你填"),让手工表单降级为兜底路径。后者更符合"AI 录入为入口"的定位,成本也更低。
- **合同详情页**:1000 行组件 + 10 个 modal,是最大的维护负担和交互负债。建议按 Tab 拆分子组件(纯重构不改交互),把"计算"从按钮触发改为进入 Tab 自动加载。
- **ERP 回写**:裸 CSV 粘贴框改为文件上传 + 解析预览 + 错误行标注,与系统其他部分的品质拉齐。

### 4.5 i18n 与设计系统治理(P1,二选一策略)

**i18n 现状**:924 keys × 3 语言的框架是认真做的,但 portfolio/sensitivity/standards/roi 四页、多个 modal、部分导航项硬编码简体中文——切到 English 的用户会看到中英混杂页面,比没有英文更伤害可信度。**建议二选一并给出推荐**:

- **方案 A(推荐)**:短期收敛——语言切换器暂只保留 zh-CN,把 demo 打磨到单语言完美;待有明确海外/港资客户线索再一次性补全 en/zh-HK。理由:i18n 补全是纯体力活,在无英文买家验证前是过早投资。
- 方案 B:立即补全三语。仅当近期 demo 对象含外资/港资时选此项。

**设计系统现状**:单色 monochrome 体系(tokens/theme)设计意图清晰,但未贯彻——分析页 Recharts 用彩色、inline hex 遍地、admin 是另一套红黑 shell。建议:① 明确色彩策略(推荐:UI 骨架保持单色,**数据可视化允许一个受控的强调色系**并写进 tokens——纯灰图表在财务汇报场景辨识度确实不足);② 新代码禁止 inline hex,改用 token(可加 lint 约束);③ admin shell 与主应用统一,保留角色徽标区分即可。dark mode 不建议投入(B 端财务场景优先级低)。

### 4.6 工程型体验债(P1–P2)

- **路由守卫**:纯客户端保护导致未登录闪现内容;JWT 存 localStorage 有 XSS 面。建议迁移到 Next.js middleware + httpOnly cookie,一次性解决闪现与安全两个问题。
- **列表能力**:合同列表全量拉取 + 客户端分页,合同数上百后会劣化(与"面向上百上千份租约的租约密集型企业"的定位冲突);API 已支持查询参数,改服务端分页即可。同步补:行选择 + 批量提交/导出。
- **移动端**:不建议做完整响应式。建议只定义一个轻移动场景——"提醒 + 待办审批"(关键日期推送 → 手机上看合同摘要 → 批准/驳回),这与 4.1/4.3 是同一条产品线,其余页面明确桌面 only。

### 4.7 值得保持的优点(不要在重构中丢掉)

AI Chat 的流式体验与草稿确认卡片(这是产品的"演示时刻");审批流的状态可视化与驳回理由留痕;列表页骨架屏;Framer Motion 转场的克制使用。

## 5. AI 产品线 — 从 Runbook 到真 Agent

现状定性:**体验层(前端)已经是 agent,执行层(后端)还是 runbook。** `buildAgentRunbook` 按关键词选择预制流程,真正的 function-calling 仅 `parse_contract_batch` / `parse_payment_schedule` 两个;大部分"工具"是描述性计划步骤。安全边界(Assist Mode、置信度门槛、审批不可绕过)是资产,升级中必须保持。

**建议路径(按序)**:

1. **补齐已有 schema 的产品面**:artifact 类型里 `monthly_close_blockers`、`data_quality_issue_list`、`audit_pack` 已建表但产品闭环未完成。优先做"AI 月结助手":月结前让 agent 扫描 close population,产出阻塞清单(缺折现率、付款计划断档、待审事件),这与 CONTEXT.md 里已经设计得很完整的 Close Exception 领域模型直接对齐——领域设计已经想清楚了,就差实现。
2. **真 function-calling 化**:把 `core.contract_repository`、`lease.term_reviewer` 等从描述性步骤升级为可被 LLM 实际调用的工具(查询类工具先行,零风险;写入类维持草稿+确认)。收益:问答从"预制上下文注入"升级为"按需取数",能回答跨合同的开放问题("哪些合同下季度到期且没设续租提醒?")。
3. **事件链路补全**:landlord notice / 补充协议解析 → 事件草稿 → 修订付款流草稿(与 2.4 联动)。需求文档 3.1 早已列出该链路,是 AI 录入价值第二曲线(第一曲线是新合同录入,已完成)。

## 6. 商业化评审

对照 5 月方案的判断——"商业债多于技术债"——两个月过去,**工程侧进展显著,商业侧三项关键动作仍未启动**:

### 6.1 第三方复核背书(P0,零开发量)

回归报告全 PASS 但每条用例仍标 `pending_third_party_review`。这份报告是售前核心资产,差的是商务动作:找一位执业会计师/审计师(事务所在职或退休合伙人皆可)对 20 条用例的标准答案出具书面复核意见。**建议立即启动,与开发并行**——它是"敢过审计"叙事的最后一块拼图,也是定价权的来源。

### 6.2 标准 Demo 脚本(P0)

现有功能已足够支撑一个 15 分钟的强 demo,但需要设计与彩排:

> ① AI Chat 拖入一份 PDF 租约 → 流式解析出草稿卡片(高光时刻一)→ ② 逐字段确认、折现率缺失被系统拦截(展示控制力)→ ③ 提交审批、换角色审批(展示 SoD)→ ④ 跑月结、出分录、锁账(高光时刻二)→ ⑤ 报表中心看负债滚动与披露件 → ⑥ 回到仪表盘:金额 KPI + 趋势图 + 关键日期预警(高光时刻三)。

注意:⑥ 依赖 4.1/4.2 的修复——**这就是为什么死 UI 是 P0**:demo 动线的收尾落在仪表盘,而仪表盘现在是空趋势图 + 数量 KPI。

### 6.3 真实 ERP 集成(P1→P2)

维持 5 月方案判断:选金蝶单点打通"分录推送 + 凭证号回写"。补充一个低成本中间态:先把导出文件对齐金蝶/用友的标准引入格式并出《对接说明书》,"文件级集成"在国内中型客户处往往已可落地,API 级集成留给标杆客户共建。

### 6.4 定价与买家叙事(建议)

- **分层锚点**:按合同份数分层订阅(如 ≤100 / ≤500 / 不限),**FP&A 决策层(第 3 章)和披露报表包放进高档位**——合规是入场券,决策支持才是溢价来源。
- **两类买家两个着陆页**:财务买家(关键词:过审计、SoD、披露、省人天)与地产/运营买家(关键词:不错过续租窗口、合同单一事实源、续租决策卡)。ROI 页现状只算"省工时",建议加上"避免一次错过 break clause 的损失"情景——后者数字大得多,也更打动运营买家。
- **多组织 SaaS 化**(organization 层、集团合并视角)在拿到 2–3 家单集团客户后再投入,现阶段 legal_entity 隔离够用。

### 6.5 定位与命名 — 承租方向必须显性化

**问题**:"租赁管理系统"在中文语境有方向歧义,且歧义偏向不利的一边——这个词的既有心智被出租方工具(公寓/物业/园区招商运营)和租赁运营商工具(融资租赁、设备出租)占据,而本产品是第三类:**承租方(lessee)管理自己租来的资产**。英文行业品类 Lease Administration / Lease Accounting 本身就是承租方视角,但中译后"出租/承租"的方向性丢失。对财务买家,"IFRS 16"三个字母自带方向信号(IFRS 16 本就是承租人准则);会误解的是不懂准则的地产/运营买家。

**修正原则:不改产品名(5 月底刚改过一次,再改迁移成本大于收益),改限定词与第一屏叙事。**

1. **通用表述用资产枚举,不锁行业**:"管好企业**租来的**门店、仓库、厂房与设备——合同、关键日期、IFRS 16 计量,一个平台。""租来的 + 资产清单"既消除房东工具误解,又不把制造业等非零售客户挡在门外。
2. **英文名对齐品类词**:对外用 **Lease Administration & Accounting Platform**(承租方品类词,可蹭品类搜索),不用直译的 Lease Management System。
3. **任何单独出现"租赁管理"四字的场合(登录页、官网、README、销售物料),都补方向词**。真正决定理解的不是名词,而是第一句话站在谁的立场说话。

**双细分滩头策略**:"谁能用"与"先打谁"是两个问题。产品能力射程覆盖所有承租密集型企业(`asset_type` 已预留 real_estate/vehicle/it_equipment/machinery),但两类客户痛点结构不同:

| | 连锁零售/餐饮 | 制造业 |
|---|---|---|
| 租约画像 | 几百份门店租约,金额中等,续租/退租高频 | 十几份厂房仓库(金额大、租期长)+ 一批设备租约 |
| 最痛的点 | 错过续租/break 窗口;录入工作量大 | IFRS 16 合规本身 + 设备租约散落无人管 |
| 最打动的功能 | 关键日期预警、AI 批量录入、组合分析 | 计量正确性、审计背书、分录/ERP 集成 |
| 主买家 | 财务 + 地产拓展 | 基本只有财务 |

落地:官网/README 用资产枚举版通用表述;销售材料做两个案例页(连锁版讲"不错过续租窗口",制造版讲"过审计 + 设备租约收口");滩头不必现在拍板——**哪边先出现愿意真实跑一个财年的标杆客户,就把那一边打透**。

**一个措辞红线**:在预算/实际对比、预测、决策支持层(第 3 章)落地之前,对外不要自称"FP&A 系统"——demo 拿不出 budget vs actual 会透支信任。现阶段稳妥说法是"租赁合同管理与 IFRS 16 计量平台,正在向租赁 FP&A 延伸"。

## 8. 总结

这个项目已经跨过了"能不能做出来"的阶段,当前的真问题是**三个"最后一公里"**:

1. **审计的最后一公里**:数据都算对了,披露件没打包;控制都建好了,红冲没接上;报告都 PASS 了,第三方没签字。
2. **体验的最后一公里**:最难的 AI 流式体验做完了,最简单的趋势图和铃铛却空着——demo 里先穿帮的恰是后者。
3. **商业的最后一公里**:产品哲学("勇敢在前门,严格在账本")已经在代码里兑现,但还没有一个能讲给客户听的 15 分钟版本。

三者共同的特征是:**投入小、杠杆大、全部可在一个季度内完成。** 建议按第 7 章路线图执行,P0 三项并行启动。
