# 后端 / AI 能力与前端触达差距审计（2026-08-27）

> 目的：回答「后端和 AI 服务有多少能力已经做了、但前端没有办法实现/触达」。方法全部机械抽取 + 运行时枚举，不凭文档数字：
> 1. HTTP 层：`cmd/api/main.go` 260 处注册 → 207 个唯一 method+path，与 `web/app/**` 全部 `/api/v1` 字面量做归一化差集，每个候选再人工反查动态拼接；
> 2. Agent 工具层：临时测试挂进生产 wiring 跑 `Runtime.Describe`（68 个工具，AGENTS.md 口径「工具数只能运行时枚举」），与 `agentskill/testdata/skill-contracts.v1.json` 的 AllowedTools 全集（50 个）做双向差集；
> 3. 配置层：盘点 env 门控的默认关闭能力。
> 口径说明：「有 api.ts 包装函数」不算被触达——包装只有被页面组件调用才构成用户路径。

## 一句话结论

HTTP 能力的前端触达率约 **96%**（207 中约 8 个零消费）；Agent 工具的技能绑定率 **74%**（68 中 18 个无任何 skill 绑定 = 自然语言问不到），其中**写类 9 个全部不可达是最大的暗能力**；另有 4 个默认关的配置型能力。总体结论与前两轮 FP&A 反馈一致：**缺口主要不在代码量，而在「最后一个接线动作」与演示数据。**

## B. Agent Tool 层：技能绑定差集（核心发现）

运行时枚举（生产 wiring，admin 权限视角）：**68 个工具**。7 个 skill 的 AllowedTools 合计覆盖 50 个，**零幽灵绑定**（skill 引用的工具都存在）——但反过来：

**18 个工具没有任何 skill 绑定，自然语言问句无法命中它们**（技能选择是工具可达的唯一门）。这与反馈 §7.4.11 的「意图路由遮蔽」互相印证且更进一步：不止权重遮蔽，这些工具根本不在任何 skill 的白名单里。

## D. 汇总口径

| 层 | 总量 | 可达 | 不可达 | 备注 |
|---|---|---|---|---|
| HTTP 路由 | 207 | ~199 | 8 零消费者 + 4 断最后一厘米 | 触达率 ≈96%；多数是「服务端先行」的有意暂存 |

## E. 建议的处理顺序

1. **P1**：Agent 白名单补绑（B 表 18 项逐一定 skill 归属；一行改动一个工具，配套 `skill-contracts.v1.json` 同步）；`/financial-model/group` 页面或明示隐藏。
2. **P2**：四个「断最后一厘米」的 api.ts 函数各找一个自然宿主页（close-pack/export → 月结页导出菜单；deal compare → pre-deal；storeDecisionEventDraft → 情景台行动区；storePromotionROI → promotions 报告版）。
3. **P2**：dead-candidates 处置：`/gl/trial-balances` 补读视图或先删包装；`coa-editor` 的注释改真。
4. **不做**：`/my-permissions`、`/contracts-by-status` 在有真实诉求前保持暂存状态是合理的——登记即可，不必为接线而接线。

## F. 附录：Agent 真实性判定（2026-08-27 补充，沿生产请求路径逐环验证）

**结论：是真 Agent 内核 + 双执行路径；「AI 含量」随分支而变。**

| 环节 | 判定 | 证据 |
|---|---|---|
| 循环内核 | ✅ 真 | `agentcore/loop.go`：模型驱动 StreamFunc、模型决定终止、hook 全链、事件序契约；纯度由 importguard 钉死 |
| 治理链 | ✅ 活的 | `chatexec` 每轮新装配九控制；BudgetGuard=48 次/轮在生产口径上真实计数；审计写失败会 fail 整个 run |
| LLM 客户端 | ✅ 真 | `llm.Client` 直连 DeepSeek/OpenAI 兼容 `/chat/completions`；无 key 时返回 `ErrNotConfigured`（聊天路径降级为数据摘要模板） |
| 会话记忆 | ✅ 真 | 历史按 user+entity+session 隔离键入库并回灌 prompt；压缩留事件证据；global 键拒绝（记忆不跨法人） |
| 流式 | ✅ 已注册 | `/ai/chat/runs/:id/stream` 与 `/agent/runs/:id/stream` 均挂 `StreamRunEvents` |

**三分支路由决定 AI 含量**（`executeChatRequest` 入口）：

1. Skill 命中 `retail_operations` → `executeRetailOperations`：关键词意图分类 + 确定性服务取数（`Model: retailDeterministicModel`），**不经 LLM**——最常用的零售问答恰恰是唯一无模型参与的主分支；
2. 文件上传带结构化 S1 底稿块 / 零售底稿请求 → 确定性路由工具（注释明说 "no LLM guessing, no discount-rate invention"——会计安全上正确）；
3. **其余全部走 `callLLM` / `callLLMWithTools`**：真调模型，function calling 让模型选文件解析工具。

**两个明确的能力上限：**

- `callLLMWithTools` 是**单轮** function-calling：注释自认 "multi-round looping belongs to the agentcore loop (C wave) and is deliberately not built here"。模型不能连续多步推理（查 A→依结果查 B）；agentcore 多轮内核存在但未接生产域逻辑。
- skill 白名单缺 18 个工具（见 §B）：即使模型想用也无资格。

**pagefill 现状**：协议完整（payload/suggestions 分离、deep_link、I5 prefill-永不-commit 不变量），但全站只有 1 个生产者（`retail.store_days.import.preview`）↔ 1 个消费者（`/retail-data-import?fill=`），且该生产者在无绑定名单里——管线两端造好了、中间锁死。
