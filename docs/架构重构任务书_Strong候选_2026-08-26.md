## 总约束（每个候选都适用）

1. **行为保持型重构**：HTTP JSON 契约、Agent Tool 名与数量、错误码、审计语义全部不变。这不是重写，是搬家。
2. **五条底线不动**。C3 直接踩在底线 4（幂等）上，C1 踩在治理链单实现约束上，各自的红线在任务内写明。
3. **工具名不许顺手改**。15 个挂错命名空间的工具有独立专项与到期日（AGENTS.md 已登记），本次重构一个都不碰。
4. **先钉后动**：每个候选第一步是把现状行为固化成锚（golden 快照 / 运行时基线）。锚不绿，不动刀。
5. **GUARD-001**：替换类改动必须证明 B 生效——删掉 B 测试要红，只证明 A 消失不算数。
6. **一候选一串 PR，禁止捆绑**；每步全绿才进下一步。三个候选代码面不相交，可并行，但 PR 永远不混。
7. 改完跑：

```bash
cd core-service && GOCACHE=$(pwd)/.gocache go test ./... && go vet ./...
cd ../web && npm run type-check && npm run build && npm test
```

## C2 · 合并签约前测算三包为一个深模块 【先做】

### 范围修正（相对评审原文）

评审说合五个包，经逐包核实调用面后，**只合三个**：

| 包 | 判定 | 依据 |
|---|---|---|
| `predeal` | ✅ 合 | 调用面全在谈判语境：`handlers/predeal.go`、`agenttools/tools/decision.go`、`workingpaper/s1`、`agentseval/invariants.go`、`renewaldecision` |
| `dealcompare` | ✅ 合 | 同上：`deal_compare.go`、`renewal_card.go`、decision tools、s1 底稿 |
| `renttosales` | ✅ 合 | `store_metrics.go`、`renewal_card.go` —— 租金占销比天花板是谈判指标 |
| `cashflow` | ❌ **剔除** | 包头自述是**组合级库务预测**（"what does the portfolio cost over the next few years"），消费方 `agentreaders/control.go` 是控制面读路径。塞进租约谈判模块违反领域边界 |
| `margindecomposition` | ❌ **剔除** | 服务 `/retail/category-facts/reconcile` 的品类毛利分解，属零售经营域，与租约无关 |

判定法（以后遇到类似问题照此）：**问这个包的数据属于哪个域，不问哪个页面调它**——与 AGENTS.md 工具命名空间判定法同一条。

### 步骤

1. **锚**：对受影响入口抓 golden——HTTP 层 `deals/compare`、`deals/briefing`、`reports/rent-to-sales`、pre-deal evaluate 用固定 seed 数据存响应快照；`agenttools/tools/decision.go` 与 `agentseval/invariants.go` 的现有测试本身就是锚，确认它们绿。
2. **纯移动**：建 `internal/services/leasescenario/`，把三包代码原样搬入（不改一行逻辑，只改 import）。编译绿 + golden 绿才算这步完成。
3. **收接缝**：提炼统一的 Engine 接口，handler 与 tools 改走接缝。参考 `agenttools/tools/control.go` 的 `ControlReaders` 分组先例。
4. **删除测试**：旧三包物理删除，`ls internal/services/{predeal,dealcompare,renttosales}` 必须不存在。

### 验收

- golden 快照逐字节一致；
- `grep -rn "services/(predeal|dealcompare|renttosales)" --include="*.go"` 零命中；
- 运行时枚举的工具清单与开工基线 diff 为空（枚举方法见 C1 步骤 1）；
- GUARD-001：把 leasescenario 接口改坏一个签名，编译必须红。

## C3 · 收拢 store-day 摄取编排为一个 IngestBatch 接缝

### 范围修正（相对评审原文）

评审要把五个包吞进一个引擎，其中两个**不能吞**：

| 包 | 判定 | 依据 |
|---|---|---|
| `sourceenvelope` | ❌ **保留独立** | 它已经是深模块：10+ 消费者横跨读写（`retailpulse` / `retailscenario` / `store360` / `storepnl` / agenttools 读类）。吞进写路径引擎会把读写耦死 |
| `controlledintake` | ❌ **保留独立** | 它同时服务 `fpna_plan_import` 和 `trial_balance`（FP&A 域），不是 store-day 专属 |
| `sourcefeed` / `masterdataresolution` / `retailingest` | ✅ 收编 | 真正的碎片：编排逻辑散在 `handlers/retail_ingest.go`（22 个调用点） |

评审 Before 图画的线性管线（SF→MR→SE→CI→RI）**不是 import 事实**（已批注），实际编排点就是 handler 层——所以接缝建在编排处，不是包依赖处。

### 步骤

1. **锚**：`make test-integration` 先真跑一遍现有摄取集成测试并记录 RUN 数量——**skip 掉的不构成证据**（AGENTS.md 原话）。幂等与原子性的现有断言就是锚。
2. **立接缝**：新 deep seam `IngestBatch(ctx, payload) Result`，内部按序编排 validate → master data mapping → envelope → persist。handler 从 22 个调用点收敛为走这一个口。`sourceenvelope.Build` 继续作为信封构造的唯一来源，不复制。
3. **收 handler**：`retail_ingest.go` 的编排分支移进引擎，handler 剩参数解析 + 调用。

### 验收

- 重放同一批次两次，落库行数不变（集成测试对真实 PostgreSQL **RUN 过**，输出里贴 RUN 行为证）；
- 构造中途失败批次，零部分行落库；
- preview / commit HTTP 契约不变，golden 一致；
- envelope 字段（source_system / import_batch_id / as_of_at / version / data_classification）原样透传。

### 协同收益（顺手登记，不在本任务做）

T1 后续专项（四个端点接 envelope）直接消费本引擎产出的信封字段。C3 落地后那个专项的施工面会小一圈——这是先做 C3 的第二个理由。

## C1 · 拆解 Agent 单体与巨型构造函数 【最后做】

### 已核实现状（2026-08-26）

- `internal/aiagent/agent.go` **3205 行**且仍在涨（评审时 2926）；
- 构造函数实为 **17 固定参数 + variadic**（比评审说的 15 更糟），`main.go:188` 调用点将 retailKPIRepo / fpnaGovernanceRepo / operatingFactsRepo **各传两遍**；
- 「47 Tool Registrations」不可 grep 验证——**工具数只能运行时枚举**（AGENTS.md），最近一次枚举总数 55（2026-08-23）。

### 步骤（顺序固定，不得跳步）

1. **记基线**：构造生产配置 registry 后调 `Runtime.Describe`，全量工具清单落盘存档。这是整个 C1 的对照物。
2. **Tool Provider**：把注册按既有三命名空间（lease / fpna / retail）拆成域 bundle，`agent.go` 只组装 bundle。注册失败 fail-fast 语义（`registerCollector` panic 带工具名）原样保留；`aiagent/registration_completeness_test.go`（尝试数 == 成功数）原样绿。
3. **抽纯函数**：Context Assembler、Result Projector 这类无 IO 的部分先走——纯函数搬家风险最低。
4. **收敛构造函数**：仿 `ControlReaders`（`agenttools/tools/control.go:17`）的分组 struct 先例，把 17 参数归组；消灭 main.go 三处重复传参；`With*` builder 已存在，续用，**不新建机制**。

### 红线

- **治理链只有一套实现：`agentkernel/governance`**（RT1-D-2）。拆分中不得在 `agentcore` 或任何新包长出第二套控制；未装 guard 回落 `Evaluate` 的双路径错误码一致性由 `governance/dualpath_rc1_test.go` 钉住，语义不许动。
- 工具 Descriptor 内容（名、权限、schema）一个字节都不改。

### 验收

- 开工时的 Runtime.Describe 清单与完工后 diff 为空；
- `registration_completeness_test.go`、`dualpath_rc1_test.go` 原样绿（没改过这两个文件的断言）;
- `main.go:188` 无重复传参，构造参数归组后可读；
- Planner / Executor 有独立单元测试（GUARD-001：mock 一个坏 planner，executor 测试要能独立红）；
- `go test ./... && go vet ./...` 全绿。

### 明确不做

行数不是 KPI——**接缝才是**。别为减行数而减：如果某个抽取让调用方变复杂，那就不该抽。

## 附：三个候选的共同验收底线

任何一个 PR 若出现以下情况，立即停止并回报，不要自行发挥：

1. golden 快照出现非空 diff（哪怕是"明显等价"的字段顺序变化——JSON 键序变了就是契约变了）；
2. 工具枚举数量变化；
3. 集成测试 SKIP 数量比开工时多了；
4. 需要改动 AGENTS.md 登记过的任何守卫测试断言才能通过。
