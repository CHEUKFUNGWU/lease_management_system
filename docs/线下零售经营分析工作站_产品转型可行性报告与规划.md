# 线下零售经营分析工作站：产品转型可行性报告与规划

> 版本：Draft v1.1  
> 日期：2026-08-12  
> 决策对象：产品负责人、经营分析负责人、技术负责人  
> 评审范围：当前仓库实现、运行数据库、既有产品文档、外部一手产品/标准资料  
> 结论置信度：**技术判断高；市场与客户价值无法在当前条件下验证，只进行内部模拟验证**
> 产品边界：**连锁零售承租方经营分析；不进入地产开发、招商、选址、物业资产经营或房东管理**

## Executive Summary

- **建议转型，但不是“从租赁跳到通用零售 BI”，而是进行有边界的相邻扩张。** 新定位建议为“线下零售经营决策工作站（Retail Performance Workstation）”：连接门店销售、毛利、客流、库存、人工、促销、占用成本、预算和行动，完成“发现问题—解释原因—模拟方案—分派行动—验证收益”的闭环。IFRS 16 应从产品中心下沉为可选的租赁会计与合规模块。

- **现有项目具备较高的技术复用价值。** 当前仓库已经有多租户与数据范围、Working/Official、版本化事实、预算/预测、门店四墙、租售比、行动兑现、决策备忘录、报告包，以及受 Review Gate、Capability Token 和审计约束的 Agent Gateway。仓库审阅识别到 67 张初始化表、166 条受保护 API 路由、39 个 `lease.*` Agent 工具，其中 16 张表已属于经营事实和 FP&A 决策域。这意味着转型不是重写，而是重新确定产品主语、数据粒度和用户工作流。

- **最大风险不是 AI 或计算引擎，而是零售数据供给与产品验证。** 当前运行库有 29 份租赁合同，但门店经营事实、设备经营事实、计划版本、行动、决策备忘录和经营报告包均为 0 条；现有 `store_operating_facts` 以月为粒度，尚不足以支持日营运、周报、同店、时段、SKU、库存和排班分析。因此目前只能证明“平台能承接”，不能证明“客户会持续使用”。

- **第一条产品切入线应是“门店经济性 + 承租方占用成本”，而不是从销售大盘开始复制 BI。** 通用零售平台通常已经覆盖交易、商品、库存和客户；本项目的差异化是把本集团作为承租方承担的租约、面积、固定租金、服务费、turnover rent、关键日期和选择权，与销售、毛利、客流和人工连接，形成四墙利润、占用成本率，以及合同继续、续签或终止的经营与会计影响分析。

- **建议用 12–16 周完成有停止条件的内部模拟验证。** 通过固定 seed 的 Golden Dataset、角色化任务脚本、权限攻击、故障注入和性能规模包，验证日/周口径、核心经营问题和完整行动闭环。在获得真实客户或数据条件之前，不应继续扩展制造场景、完整 EPM、SKU 级预测或 Agent 自动执行，也不得把模拟结果表述为客户采用、真实 ROI 或产品市场匹配。

## 一、转型判断：Conditional Go

### 1.1 建议的新产品定义

**产品名称建议**

- 中文：线下零售经营决策工作站
- 英文：Retail Performance Workstation
- 对外短语：从门店经营信号到可验证行动

**一句话定义**

> 面向连锁零售经营团队、FP&A、Finance BP 和租赁会计团队，把分散在 POS、ERP、库存、客流、排班和承租合同中的事实连接起来，用确定性指标和受控 AI Agent 快速定位门店问题、解释驱动、模拟方案、形成行动并验证收益。

**核心产品对象从“合同”调整为“经营单元”**

```text
法人 / 品牌
  └── 区域
      └── 门店 / 经营位置
          ├── 日期 / 财务周 / 时段
          ├── 商品 / 品类 / SKU
          ├── 交易 / 客流 / 库存 / 排班 / 促销事实
          ├── 预算 / 预测 / 场景 / 行动
          └── 租赁合同 / 面积 / 占用成本 / 关键日期
```

合同不再是所有分析的根对象，而是门店经济性的一类重要约束和成本来源。

### 1.2 为什么不是“通用 BI”

Microsoft 的零售行业数据模型把数据碎片化、检索耗时、口径不一致和治理不足列为零售分析的主要问题，并允许按用例选取模型子集；这支持建设一个跨源、受治理的经营决策层，而不是复制所有源系统。[Microsoft Retail industry data model](https://learn.microsoft.com/en-gb/industry/retail/retail-data-solutions/overview-retail-industry-data-model)

Shopify 的官方对象模型已经覆盖订单、行项目、门店位置和多状态库存；Oracle Retail Insights 也覆盖销售、库存、价格、促销、客流和商品表现。因此重新建设 POS、库存主账或全量零售数据仓库不是本项目的优势。[Shopify Order](https://shopify.dev/docs/api/admin-graphql/latest/objects/Order)、[Shopify InventoryLevel](https://shopify.dev/docs/api/admin-graphql/latest/queries/InventoryLevel)、[Oracle Retail Insights User Guide](https://docs.oracle.com/en/industries/retail/retail-insights-cloud/24.2.401.0/rinug/G17657_02.pdf)

本项目应该竞争的不是“谁有更多图表”，而是：

1. 是否能把门店问题定位到可信证据；
2. 是否能把销售、毛利、库存、人工和占用成本串成可解释驱动；
3. 是否能把结论变成有负责人、截止日期和收益验证的行动；
4. 是否能在不破坏权限、版本、审批和审计的前提下使用 AI。

### 1.3 可行性评分

评分采用 1–5 级内部评审量表：1 为尚未具备，3 为可试点，5 为已形成可复制产品。该评分是基于代码与运行数据的专家判断，不是客户调研结果。

| 维度 | 评分 | 证据 | 判断 |
|---|---:|---|---|
| 平台与架构复用 | 4.5 | Core Service、RBAC、Agent Gateway、版本、审计、草稿与审批均已存在 | 可直接作为新产品控制平面 |
| 财务与占用成本差异化 | 4.5 | 租赁现金、IFRS 16、事件、续租、报价、面积与门店已连接 | 是最有壁垒的切入点 |
| 零售经营指标能力 | 2.8 | 已有营收、毛利、交易数、客流、人工、四墙、租售比和 cohort | 指标雏形存在，但粒度与覆盖不足 |
| 数据接入与语义治理 | 2.0 | 有批次、映射、版本、质量状态和 CSV/XLSX；无真实 POS/ERP 联调 | 是试点第一阻塞项 |
| 任务型产品工作流 | 2.5 | 有经营驾驶舱、行动、情景和报告 API；前端仍以功能页拼接 | Capability Complete，尚非 Buyer Ready |
| 客户与商业验证 | 1.0 | 运行库经营域为 0 条，且当前无客户验证条件 | 模拟验证不能替代商业验证，不允许宣布转型成功 |

**综合判断：Conditional Go。** 可以投入一个有边界的内部验证周期；不建议现在就扩编或对外宣称完整零售经营平台。产品壳和导航可以调整，但底层大规模物理重命名应等内部技术门槛通过后再决定。

### 2.3 必须正视的结构性缺口

#### 缺口一：数据粒度仍是“月度财务”，不是“零售营运”

当前 `store_operating_facts.period` 固定为 `YYYY-MM`。这适合月度四墙和 FP&A，但不足以回答：

- 昨天哪些门店销售掉队；
- 哪个时段客流正常但转化下跌；
- 周末促销带来的增量毛利是否覆盖折扣和额外人工；
- 缺货是否造成交易和毛利损失；
- 本周排班是否匹配客流峰值；
- 同店增长是否来自交易数、客单价还是新旧店组合。

新模型至少需要 `store_day`，客流/排班可选 `store_hour`，商品分析需要 `store_day_sku` 或 `store_day_category`。

#### 缺口二：当前宽表适合 MVP，不适合高体量零售分析

PostgreSQL 可以继续承担控制平面、工作流、版本和审计，但若进入数百门店 × 日 × SKU × 交易行的规模，不应把所有分析事实继续塞进当前宽表。建议采用：

- PostgreSQL：组织、权限、指标定义、计划、行动、审批、决策工件；
- MinIO/Object Storage：原始文件、增量快照、可复演输入；
- 分析引擎：试点可用 DuckDB/Parquet；规模化优先连接客户 Snowflake/BigQuery/Fabric，或部署 ClickHouse；
- Core Service：只暴露稳定的语义指标和确定性决策服务；
- Agent：只调用 Core Tool，不直接查询原始仓库。

#### 缺口三：用户界面仍然是“功能模块集合”

当前首页、合同、月结、报表、敏感性、多准则等页面继续表达租赁系统心智；经营能力被集中在一个大型 `/performance` 页。转型后应按用户任务重组，而不是继续增加 Tab。

#### 缺口四：角色模型仍偏会计审批

现有 admin/editor/reviewer/approver/auditor/readonly 无法准确表达区域经理、门店经理、经营分析师、财务 BP、租赁会计和数据管理员。需要把“角色”与“数据范围/动作权限”解耦。

#### 缺口五：经营口径与 IFRS 16 口径尚未成为一等公民

IFRS Foundation 说明，与未来销售或使用挂钩的真正可变租赁付款通常不纳入租赁资产和负债初始计量；但经营分析必须把当期 turnover rent 计入门店占用成本。因此不能用 IFRS 16 负债/折旧直接代替门店经营租金。[IFRS 16 Project Summary](https://www.ifrs.org/content/dam/ifrs/project/leases/ifrs/published-documents/ifrs16-project-summary.pdf?la=en)

建议并列维护：

| 口径 | 内容 | 使用场景 |
|---|---|---|
| 财务报告口径 | ROU、负债、利息、折旧、重估和披露 | 月结、财报、审计 |
| 经营占用口径 | 基本租金、服务费、物业/营销/公用成本、当期变量租金 | 门店四墙、预算、WBR |
| 决策经济口径 | 可避免成本、合同继续/终止成本、机会成本、NPV | 承租合同继续、续签或终止情景 |

## 三、目标产品蓝图

### 3.1 首选 ICP 与买家

**优先 ICP 假设**

- 50–500 家线下门店；
- 门店租金和占用成本对利润有显著影响；
- 已有 POS/ERP/BI，但门店经营解释和行动仍主要依赖 Excel、邮件和会议；
- 财务、运营和租赁会计团队对同一门店使用不同口径；
- 承租合同继续/终止、促销或人工安排的经营影响缺少统一证据包。

**优先买家与用户**

- 经济买家：CFO、COO、Head of Retail；
- 业务 Sponsor：FP&A Head、Retail Finance BP、Lease Accounting Lead；
- 高频用户：经营分析师、区域经理、门店运营、财务分析师、租赁会计；
- 治理用户：数据管理员、审计、系统管理员。

该 ICP 仍是假设。当前只能通过模拟角色任务检查产品内部一致性，不能验证真实购买者、使用频率或付费意愿；这些结论必须保持 `unvalidated`。

### 3.2 六个产品工作台

#### A. 今日经营脉搏

- 昨日/本周销售、毛利、交易数、客流、转化、客单价、人工和占用成本；
- Actual vs Budget vs Forecast vs Prior Year；
- 数据截至时间、覆盖率、异常和缺失；
- 按影响金额、可行动性和时效排序的 Top Issues；
- 一键进入证据下钻或创建行动。

#### B. 门店网络与单店 360

- 品牌/区域/店型/成熟度 cohort；
- 同店与全店分开；
- 四墙 EBITDA、占用成本率、销售/㎡、毛利/㎡、盈亏平衡销售；
- 客流 × 转化 × 客单价驱动树；
- 门店历史、合同、关键日期、行动和决策记录。

#### C. 销售、商品与库存

- 品类/SKU 销售、毛利、折扣、退货、售罄；
- 在手、可售、在途、预留、缺货、库存天数；
- 库存周转、GMROI、滞销和 markdown；
- 促销前后、对照门店/商品和增量毛利分析。

该工作台应在第二轮验证后进入路线图，避免第一阶段范围失控。

#### D. 客流与劳动效率

- 进店客流、转化率、分时客流、峰谷；
- 计划工时、实际工时、人工成本率、销售/工时、毛利/工时；
- 客流与排班错配；
- 只输出建议和草稿，不直接修改班表。

#### E. 承租方占用成本与合同情景

- 基本租金、变量租金、服务费、其他占用成本；
- 合同继续、续签假设或终止的经营、现金和会计影响；
- break/renewal notice、到期和租金复核窗口；
- 方案的现金、P&L、EBITDA、NPV、IFRS 16 影响分层展示；
- 经人工确认后生成租赁事件草稿。

这是首个版本的核心差异化工作台，但它只服务本集团作为承租方的经营与财务决策，不包含选址、商圈、物业估值、市场租金预测、招商、出租率或房东资产管理。

#### F. 计划、会议与行动中心

- Budget/Forecast/Scenario 版本；
- WBR/MBR/QBR 报告包；
- 根因、行动、Owner、Due Date、Expected Benefit；
- 后续 Actual 验证 Realized Benefit；
- 会议前简报、会议中问答、会议后行动草稿。

## 四、零售数据与指标规划

### 4.1 最小数据主干

GS1 通过 GTIN、GLN 等标识产品和地点，并用标准化事件支持跨系统共享。项目不必完整实现 GS1，但应允许保存 GTIN/GLN/外部 ID，避免商品与门店映射锁死在单一 POS。[GS1 standards](https://www.gs1.org/standards/how-gs1-standards-work)、[GS1 Global Traceability Standard](https://www.gs1.org/standards/gs1-global-traceability-standard/current-standard)

| 数据域 | 最小事实粒度 | 第一阶段 | 后续扩展 |
|---|---|---|---|
| 门店主数据 | store/location effective-dated | 门店、品牌、区域、面积、开闭店日 | 店型、气候区、可比店资格 |
| 销售交易 | store-day；保留来源可下钻到 transaction/line | 净销售、交易数、销量、折扣、退货 | SKU、渠道、时段、支付方式 |
| 毛利/成本 | store-day 或 store-week | 毛利额、毛利率 | 标准/实际成本、品类、供应商 |
| 客流 | store-day/hour | 进店客流 | pass-by、员工剔除、停留、区域访问 |
| 库存 | store-day-SKU snapshot/event | 暂不作为首发阻塞 | 在手、可售、预留、在途、收货、调拨、损耗 |
| 劳动力 | store-day/hour | 实际工时、人工成本 | 计划班次、岗位、技能、加班、缺勤 |
| 促销 | campaign-store-product-day | 活动成本和活动窗口 | 对照组、优惠、markdown、媒体成本 |
| 租赁/占用 | contract/store-period/event | 基本租金、变量租金、服务费、面积、关键日期 | 完整 occupancy cost policy |
| 计划与行动 | metric-store-period-version | Budget/Forecast/Target、行动和收益 | 驱动式预测、跨门店方案 |

### 4.2 首发指标树

```text
门店贡献
├── 净销售额
│   ├── 有效客流
│   ├── 转化率 = 交易数 / 有效客流
│   └── 客单价 = 净销售额 / 交易数
├── 毛利额 = 净销售额 - 销售成本
├── 可控门店成本
│   ├── 人工
│   ├── 占用成本
│   └── 其他可控成本
└── 四墙 EBITDA
```

首发必须有明确版本定义的指标：

1. 净销售额；
2. 毛利额与毛利率；
3. 交易数、客单价；
4. 客流与转化率；
5. 同店销售与同店毛利；
6. 人工成本率、销售/工时；
7. 占用成本率；
8. 销售/㎡、毛利/㎡；
9. 四墙 EBITDA 与盈亏平衡销售；
10. Actual vs Budget/Forecast/Prior Year 的确定性差异桥。

所有比率必须保留 numerator、denominator、范围、日历、货币、税、退款、渠道归属和排除项。不能只存最终百分比。

### 4.3 集成原则

Shopify 官方文档说明 webhook 事件可能乱序或漏交付，因此连接器必须采用“增量事件 + 周期回补 + 日终对账”，不能把 webhook 当作账本。[Shopify Webhooks](https://shopify.dev/docs/apps/build/webhooks)

所有连接器应遵守：

- 源游标、事件 ID 和幂等键；
- 原始输入不可变保存；
- 迟到数据和重述版本；
- 门店/商品/期间映射；
- accepted/rejected/quarantined 行隔离；
- source total 与平台 total 对账；
- freshness、coverage、mapping、reconciliation 四类状态分开；
- 失败回补不能覆盖已发布 Official/Management Snapshot。

## 五、AI Agent 能力范围规划

### 5.1 Agent 产品原则

AI 不应是一个能任意查询数据库和调用外部系统的超级助手，而应是多个可审计 Skill 共用一个受控 Runtime：

> LLM 负责理解问题、选择工具和组织解释；指标服务负责算数；权限服务负责范围；工作流负责审批；人负责重大判断和正式动作。

NIST AI RMF 将治理、映射、衡量和管理作为持续风险管理函数，并强调文档、人工复核、测试和生命周期管理。现有 Tool Registry、Scope Guard、Review Gate、Run Trace 和 Capability Token 与这一方向一致，应保留为新产品的核心差异化控制。[NIST AI RMF Core](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/)、[NIST Generative AI Profile](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf)

### 5.2 能力等级

| 等级 | 能力 | 示例 | 默认策略 |
|---|---|---|---|
| L0：解释与导航 | 解释指标、找到页面、展示口径 | “占用成本率怎么算？” | 可直接响应，引用指标版本 |
| L1：只读调查 | 查询、下钻、对比、异常定位 | “哪些店客流正常但转化下降？” | 默认开放，严格数据范围 |
| L2：确定性模拟 | 调用规则/统计服务，不产生副作用 | 合同继续/终止、租金、人工、促销情景 | 显示假设、版本、残差和敏感性 |
| L3：草稿生成 | 创建解释、行动、情景、报告和备忘录草稿 | 生成区域经理行动清单 | 必须 Review Gate 与幂等 |
| L4：受控执行 | 经批准执行低风险、可逆动作 | 分派行动、发送内部提醒、刷新报告 | 白名单、审批、撤销、限额、审计 |
| L5：正式/不可逆决策 | 改价格、改班表、下采购单、终止门店经营、签署/终止合同、过账 | 任何自动正式决策 | 默认禁止；不进入近期路线图 |

### 5.3 建议的 Agent Skill 组合

| Skill | 核心问题 | 读取工具 | 可生成对象 | 阶段 |
|---|---|---|---|---|
| Daily Retail Brief | 昨天/本周最重要的经营变化是什么 | 销售、毛利、客流、人工、占用、计划、质量 | 日报草稿、关注清单 | P0/P1 |
| Variance Investigator | 为什么偏离预算/预测/去年 | 指标树、事件、促销、库存、人工、租赁 | 解释草稿、残差、调查问题 | P0/P1 |
| Store Performance Coach | 哪些门店需要什么行动 | 门店 360、peer/cohort、历史行动 | 门店行动草稿 | P1 |
| Data Quality Steward | 哪些数据不能用于决策 | freshness、mapping、reconciliation、coverage | 数据修复任务 | P0 |
| Occupancy & Lease Advisor | 承租合同继续、续签或终止会产生什么影响 | 门店经济性、租约、关键日期、情景服务 | 决策备忘录、事件草稿 | P1/P2 |
| Planning & Scenario Copilot | 假设变化如何影响销售、利润和现金 | 计划版本、假设库、确定性模型 | Scenario 草稿、Forecast 建议 | P2 |
| Promotion Review Agent | 促销是否创造增量毛利 | 活动、销售、毛利、租金、人工、对照 | 复盘草稿、行动 | P2/P3 |
| Inventory & Margin Agent | 缺货、积压和 markdown 如何影响毛利 | SKU 销售、库存、价格、促销 | 调拨/补货建议草稿 | P3 |
| Meeting & Action Agent | 会前、会中、会后如何闭环 | 报告包、决策、行动、纪要 | 议程、纪要、行动草稿 | P2 |

不建议为每个 Skill 部署独立模型或独立权限系统；应复用同一 Tool Runtime、语义层和审计协议。

### 5.4 每次 Agent 输出的强制信封

每一个经营结论至少包含：

- `scope`：法人、品牌、区域、门店、商品范围；
- `as_of`：数据截至时间和时区；
- `basis`：Actual / Budget / Forecast / Scenario / Working / Official；
- `metric_definition_version`；
- `data_version` 与 `source_references`；
- `coverage`、`freshness`、`mapping`、`reconciliation`；
- `facts`：系统事实；
- `deterministic_calculations`：规则或统计计算；
- `human_inputs`：人工假设或确认；
- `ai_inference`：AI 推断/建议；
- `residual_or_unknown`：无法解释部分；
- `recommended_action` 与 `review_required`。

这可以直接复用当前 `fpna_decision_memos` 中事实、计算、人类输入和 AI 叙事分层的设计。

### 5.5 绝对禁止和阶段性禁止

**绝对禁止**

- Agent 绕过 Core Service 直接访问 PostgreSQL、MinIO Admin、Shell 或任意 HTTP；
- 用 LLM 生成或补齐正式金额、货币、折现率、库存、客流或销量；
- 越权读取其他法人、区域、门店、员工或客户明细；
- 以 AI Signal 代替正式控制结论；
- 自动审批合同、正式 Forecast、会计分录或关账；
- 隐藏数据缺失、映射失败、迟到数据或未解释残差。

**近期阶段禁止**

- 自动改价或发布促销；
- 自动修改门店班表、员工工时或绩效结论；
- 自动补货、调拨、下采购单或核销库存；
- 自动作出闭店决定、签署/终止合同或发送房东承诺；
- 自动向外部人员发送经营材料。

### 5.6 Agent 命名空间与权限重构

当前 39 个 Agent 工具全部使用 `lease.*`。建议进行版本化迁移：

- 新工具：`retail.performance.*`、`retail.store.*`、`retail.inventory.*`、`retail.workforce.*`、`retail.occupancy.*`、`retail.action.*`；
- 原 `lease.*` 工具保留兼容别名和固定版本，避免已有 Run Replay 失效；
- `fpna_copilot` 拆为多个可组合 Skill；
- Tool 描述与权限资源不再借用 `reports:read` 表达所有经营读取；
- 新权限资源至少包括 `retail_performance`、`store_financials`、`inventory_metrics`、`workforce_metrics`、`occupancy_decisions`、`retail_actions`、`metric_governance`；
- 员工、客户和交易明细默认聚合，按最小必要权限开放。

### 5.7 Agent 成功与安全指标

| 类别 | 指标 |
|---|---|
| 可信度 | Source Coverage、无证据回答率、计算服务一致率、残差保留率 |
| 权限安全 | 越权读取成功次数必须为 0、跨范围攻击拒绝率、敏感字段泄露次数 |
| 人机协作 | 建议采纳率、人工修改率、草稿一次复核通过率、升级人工率 |
| 经营价值 | 问题到结论时间、行动创建率、按期完成率、收益兑现率 |
| 运行效率 | Tool 成功率、P95 延迟、每个已采纳结论成本、重试/恢复率 |
| 模型质量 | 确定性测试集通过率、反事实/缺失证据拒答率、提示注入抵抗率 |

## 六、产品路线图

### Phase 0：可审计模拟验证（0–6 周）

**目标：在没有设计伙伴、客户访谈和真实 POS/ERP 数据的条件下，证明产品定义、零售数据模型、指标、权限和纵向工作流在内部是自洽、可复演和可测试的。该阶段不能证明市场需求或付费意愿。**

交付：

1. 冻结承租方零售经营产品边界和角色矩阵；
2. 建立固定 seed 的模拟数据生成器：60 家门店、24 个月 store-day、预算、租赁合同、占用成本和行动；
3. 建立覆盖正常、异常、缺失、重复、迟到、租金阶梯、变量租金和权限攻击的 Golden Dataset；
4. 建立门店、财务日历、外部 ID 和首发指标注册表；
5. 将事实模型扩展到 store-day/store-week，保留月度聚合兼容层；
6. 上线数据质量、控制总额对账和模拟数据标识；
7. 打通“经营脉搏 → 门店 360 → 占用成本 → 情景 → 行动 → 后续 Actual 验证”；
8. 用经营分析、区域运营、财务 BP、租赁会计、数据管理员五种模拟角色执行内部 UAT。

退出门槛：

- 相同 seed 生成相同数据和文件哈希，环境可从空库重建；
- 100% 模拟门店可唯一映射，故意设置的异常全部进入 quarantine 或 blocked；
- 首发核心指标、四墙贡献和差异桥与 Golden Expected Outputs 100% 对数；
- 5 条角色化端到端任务均可完成并产生审计链；
- 跨法人/区域/门店越权成功次数为 0；
- 所有页面、API、导出和 Agent 回答均能识别 `SIMULATED`；
- 对外材料明确“内部技术验证，不代表客户采用或真实 ROI”。

停止或返工条件：

- 事实模型无法从日粒度稳定聚合到周/月；
- 经营、租赁现金和 IFRS 16 三口径无法分层；
- Agent 仍可绕过工具或 Review Gate 产生正式写入；
- 纵向工作流仍需手工改库、手工拼接页面或隐藏数据质量问题。

### Phase 1：零售经营 MVP（6–16 周）

**目标：形成 Daily/Weekly 的最小经营闭环。**

交付：

- 昨日/本周经营脉搏；
- 门店网络和单店 360；
- 销售、毛利、交易、客流、转化、客单价、人工、占用成本；
- Actual/Budget/Forecast/Prior Year 对比；
- 门店/cohort/区域差异桥；
- 数据质量、异常、行动和收益验证；
- Daily Brief、Variance Investigator、Data Quality Steward 三个 Agent Skill；
- WBR 管理包和行动回写；
- 租赁与 IFRS 16 移至可选模块导航。

阶段门槛：

- Golden Dataset 上经营报告、指标和行动结果可重复生成且不漂移；
- 100% 确定性金额与指标服务一致，≥95% Agent 结论带完整来源和覆盖状态；
- 无证据场景均拒答或明确降级，越权成功次数为 0；
- 预设高影响异常均可转为有 Owner、Due Date 和证据的行动草稿；
- 60 店基准包常用查询 P95 <1.5 秒，500 店压力包 P95 <3 秒。

### Phase 2：门店决策与会议闭环（3–6 个月）

**目标：从“解释发生了什么”升级到“决定下一步做什么”。**

交付：

- 承租合同继续、续签或终止情景；
- 门店盈亏平衡、NPV、现金、P&L、IFRS 16 影响分层；
- 促销 ROI 的受控试点；
- Forecast 情景与假设库；
- 决策备忘录审批；
- MBR/QBR、会议行动和后续兑现；
- Occupancy Advisor、Planning Copilot、Meeting Agent。

阶段门槛：

- 预设承租合同场景的经营贡献、现金和 IFRS 16 影响全部通过 Golden 对数；
- 决策材料可由固定输入稳定重建，且三种口径不混用；
- 模拟行动在连续 2 个周期中可追踪 expected、realized 和 residual；
- 重大假设均可追溯到人、版本和证据；
- 不包含市场租金预测、选址、搬迁地点、房东画像或物业估值。

### Phase 3：商品、库存与劳动力（6–12 个月）

**目标：补齐门店利润的核心经营驱动，但不成为源系统。**

交付：

- 商品/SKU/品类语义与 GTIN/外部 ID；
- 日库存快照与库存事件；
- 库存周转、GMROI、缺货、滞销、markdown、售罄；
- 排班/考勤聚合数据、销售/工时、峰时覆盖；
- 促销/商品/库存的增量分析；
- Inventory & Margin Agent；
- 经批准的低风险任务写回试点。

### Phase 4：主动经营与有限自动化（12 个月以后）

前提是数据覆盖、映射、对账、指标治理和历史长度达到客户约定阈值。

交付：

- 统计/机器学习基线预测；
- 可解释异常检测和 Forecast Risk；
- 主动每日/每周监控；
- 低风险、可撤销、审批后的通知/任务/报告刷新；
- 持续 Agent 评测、漂移监控和成本治理。

### 明确降级的路线

- **制造 Finance BP 暂停作为主路线。** 现有设备与制造代码保留为未来插件，不继续与零售主产品并行争夺资源；
- 不建设完整 EPM、总账、POS、WMS、WFM 或支付系统；
- 不在 Phase 0/1 建设复杂 ML；
- 不以更多页面和更多 AI Prompt 代替真实数据与工作流验证。

### 7.3 不建议立刻做全仓库重命名

2. API 新增 `/api/v1/retail/*`，内部可暂时调用现有服务；

4. 数据库表名不在试点前做大规模物理重命名；

这样可以避免“先花数周改名，后发现产品假设不成立”。

## 八、产品包装假设（尚未商业验证）

### 8.1 产品包

| 产品包 | 核心能力 | 主要买家 |
|---|---|---|
| Retail Performance Core | 数据接入、门店 360、指标、计划、行动、WBR | COO、FP&A、Head of Retail |
| Occupancy Intelligence | 承租方占用成本、关键日期、合同继续/续签/终止情景 | Finance BP、租赁会计、CFO |
| Lease Accounting | 合同、事件、IFRS 16、月结、分录、披露 | Controller、Lease Accounting |
| AI Decision Copilot | Brief、调查、情景、材料、行动草稿 | 跨角色增购模块 |

### 8.2 首个销售故事

不建议以“AI 自动分析一切”开场，建议用一个具体闭环：

> 每周自动发现最影响利润的门店 → 解释是客流、转化、毛利、人工还是承租占用成本 → 生成区域经理行动 → 在下个周期验证是否兑现 → 对临近合同选择权或到期日的门店进入继续、续签或终止情景。

该故事同时体现零售价值、租赁差异化和 Agent 控制能力。

当前没有客户访谈或设计伙伴，该包装只能作为内部产品假设，不能据此确定买家、价格、销售周期或付费意愿。

### 8.3 North Star Metric

> 从经营问题出现，到形成一份有证据、可解释、可分派并能在后续 Actual 中验证的行动，所需的中位时间。

不把“接入多少表”“生成多少 AI 回答”“合同数量”作为主成功指标。

## 九、主要风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 范围从租赁扩张到所有零售 | 团队失焦、长期无可售版本 | 以占用成本+门店经济性为楔子，Phase Gate 控制 |
| 数据无法稳定接入 | 所有经营结论失真 | 只读接入、批次/游标、回补、对账、质量状态 |
| 指标口径争议 | AI 和用户给出不同答案 | 版本化指标定义、Owner、公式、日历、币种和排除项 |
| 当前 Postgres 模型承载不足 | SKU/交易规模下性能和维护风险 | 控制平面与分析事实分离，优先客户仓库/Parquet |
| AI 叙事超过证据 | 失去财务和经营信任 | 强制输出信封、deterministic tools、residual、评测 |
| 角色和数据越权 | 商业敏感数据泄露 | 细粒度范围、聚合默认、not-found 语义、攻击测试 |
| 经营动作误执行 | 人员、价格、库存或合同损失 | L1/L2 先行、L3 草稿、L4 白名单，L5 禁止 |
| 已有 BI 客户认为功能重复 | 无法形成预算 | 竞争点放在跨域归因、行动闭环、占用成本和 Agent 治理 |
| 会计与经营口径混淆 | 错误门店判断或财报风险 | 三口径分层，输出明确 basis 和 metric version |

## 十、未来 30 天建议

1. **冻结边界。** 书面确认承租方零售经营定位、地产不做清单和制造路线降级。
2. **建立模拟数据规格。** 定义 60 家门店、24 个月日数据、预算、合同、占用成本、行动和异常注入规则。
3. **开发固定 seed 生成器与 Golden Dataset。** 确保任意环境可以从空库重建相同结果。
4. **冻结首发指标。** 锁定销售、毛利、交易、客流、转化、客单、人工、占用成本、四墙贡献和销售/㎡的公式及版本。
5. **补齐 store-day/store-week。** 保留现有月度兼容层，完成迟到数据和版本重算设计。
6. **制作纵向原型。** 从“异常门店 → 驱动解释 → 占用成本 → 情景 → 行动 → 下期验证”打通一条模拟但可审计的链路。
7. **建立角色化 UAT。** 用经营分析、区域运营、财务 BP、租赁会计、数据管理员五种角色执行固定任务。
8. **先做兼容层。** 引入新导航、`retail.*` API/Agent aliases；不立即做数据库全量重命名。
9. **补齐统一测试入口。** Go、Python、Web、迁移、Golden 指标、Agent Eval 和安全测试一键运行。
10. **按任务清单验收。** 使用配套《转型实施任务清单与验收标准》管理 P0/P1 范围和阶段门槛。

## 十一、进一步问题

以下问题无法通过模拟得到真实答案，因此应作为未来商业验证登记项，而不是阻塞内部技术验证：

1. 真实用户最痛的是日报/WBR、门店四墙、库存、人工，还是承租合同决策？
2. 真实预算 Owner 是 CFO、COO、FP&A 还是租赁会计负责人？
3. 客户已有 BI 的成熟度如何；平台应替代报表、补充决策，还是作为 Agent/行动层？
4. 客户实际能提供交易行/SKU，还是只能提供门店日汇总？
5. 真实组织如何治理同店、线上订单归属、退货、税和汇率口径？
6. 承租方占用成本包含哪些非租赁费用，权威源在哪里？
7. 区域经理和门店经理可以看到哪些财务和人工数据？
8. 哪些低风险动作允许审批后写回？
9. 部署形态是私有化、本地工作站、单租户云，还是多租户 SaaS？
10. 是否存在独立付费意愿、价格区间和可重复销售路径？

这些问题在获得真实客户接触之前统一标记 `unvalidated`，不得用内部人员偏好或模拟任务完成率代替答案。

## 十二、假设、局限与验证说明

- 本报告审阅了当前仓库、运行容器与数据库，但没有客户访谈、设计伙伴、竞争价格调研或市场规模测算；商业判断属于待验证产品假设，模拟验证不能替代这些证据。
- 运行数据库经营域为空，因此未能验证指标在真实门店数据上的完整性、性能、口径一致性和用户价值。
- Go 全量测试与 Web 类型检查已于 2026-08-11 通过。AI Service 宿主环境缺少 Python 依赖，容器镜像未包含测试目录，因此本次未能重跑 Python 测试；这不等同于测试失败，但属于交付前需补齐的验证缺口。
- 现有第三方会计复核仍未完成；IFRS 16 应保留 `pending_third_party_review` 状态，不能因为产品转型而弱化。
- 外部厂商文档用于验证数据域、接口和产品边界，不构成这些厂商效果或 ROI 的独立证明。
- 可行性评分是基于显式量表的内部评审，用于排序风险，不应作为对外宣传数字。

## 十三、最终建议

**做这次转型，但要改变的是“产品中心”，不是丢掉现有资产。**

建议将现有系统重构为：

> 以门店经营单元为中心、以销售/毛利/客流/人工/库存/占用成本为事实、以计划和行动为工作流、以租赁与 IFRS 16 为差异化插件、以受控 AI Agent 为交互与调查层的线下零售经营决策工作站。

同时坚持三个战略纪律：

1. **不做通用 BI。** 聚焦跨域经营归因、门店决策和行动兑现；
2. **不先做大而全。** 先用固定 seed 的 Golden Dataset 和角色化 UAT 验证“承租占用成本 + 门店经济性”的产品与技术闭环；
3. **不让 AI 成为事实源。** AI 只能调用受控工具、组织证据、生成草稿和建议，正式经营与会计动作继续由人和工作流负责。

完成 12–16 周内部模拟验证后，只能说明系统已具备可演示、可回归和可部署的经营工作站形态。它是否比“纯租赁合同管理 + IFRS 16”拥有更高使用频率、更广买家范围或更强付费意愿，仍需未来真实市场证据。
